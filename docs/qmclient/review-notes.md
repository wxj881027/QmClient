# QmClient 重构白话版说明

这份文档给后续 AI 看。目标只有一句话：不是修补旧 QmClient，而是用 DDNet 20.0 做底座，重新搭一套更清楚、更好拆、更好测的 Qm 客户端。

## 一句话理解整套结构

可以把它想成四层：

1. 底层引擎/平台：窗口、输入、图形后端、配置加载。
2. 组合根 `CQmRuntime`：负责把各个功能接起来，但不自己吞掉所有业务。
3. 功能层：每个功能自己管自己的状态、逻辑、测试。
4. UI / 渲染层：只负责把功能“画出来”。

## 每一层到底管什么

- 底层只管“能不能跑”：窗口、输入、图形、配置、文件。
- 功能层只管“是什么”：比如玩家指示器、诊断、TC/BC 的某个能力。
- UI 层只管“怎么摆出来”：页面、卡片、搜索、排序、折叠、主题。
- 渲染层只管“怎么画”：把已经准备好的状态画成屏幕上的东西。

## 现在最重要的几条原则

- 不再用 `TClient` 字段当新状态仓库。
- `CQmRuntime` 只做接线，不做万能管理器。
- UI 只读 model，不直接管业务。
- 功能和渲染分开，平台和功能分开。
- 性能看 1% low、文本、图标、内存、后端日志，不能只看“能不能跑”。

## 这版架构里我认为最对的地方

- `CQmRuntime` 是组合根，不是大杂烩。
- 卡片模型和业务状态分开了。
- 诊断日志自动落盘，这对后续性能优化很关键。
- 旧配置迁移已经有明确版本闸门，不是无限兼容。

## 现在已经定下来的做法

- 旧配置迁移要覆盖 `CONFIG_FILE` 和 `autoexec`。
- 旧值迁移后，非法或太长的命令不能悄悄丢掉，要保留。
- 诊断日志自动落盘，不靠手工复制。
- UI 卡片注册后要冻结，避免运行中乱改。
- 目前的渲染入口先走明确 slot，不把所有东西堆进一个 switch。

## 需要特别盯住的风险

- `CQmRuntime` 不能越长越大。
- `IGameClient` 不能继续加很多 Qm 专用钩子。
- UI model 不能把搜索、页面、卡片注册又绕回业务对象里。
- 图形后端事件监听已使用 source 生命周期 token，避免以后重启/切换时旧回调继续生效；若未来需要物理移除 listener，再引入带句柄的官方接口。
- SDL3 相关改动要放在平台层，不要和功能层绑死。

## SDL3 放在哪里

SDL3 更像“地基材料”，不是功能本身。  
它应该主要放在窗口、输入、事件、图形初始化这些地方。  
Qm 功能不应该直接知道 SDL3 细节。

官方 SDL3 文档把 video subsystem 讲成“窗口管理 + 事件 + OpenGL/渲染入口”，并且事件一般通过 `SDL_PollEvent()` 在主循环里轮询处理；这说明它适合放在平台层，而不是功能层。

## 渲染 / UI / 功能怎么分

一个简单例子：

- 功能层算出“谁该显示”；
- UI 层决定“卡片怎么排”；
- 渲染层负责“画成什么样”；
- 底层只负责“把图像送到屏幕上”。

字体和图标也一样：字体资源应该缓存，别每次打开页面都重新做。Godot 的文档就明确把字体资源和字形缓存、字体图集绑定在一起，这和我们现在的“图标 atlas + 稳定 ID + 冻结注册表”方向一致。

## 后面怎么继续

1. 先把每个功能切成独立模块。
2. 再把 TC、BC 的功能按同样方式迁进来。
3. 再把 UI 的页面、搜索、排序、卡片描述补完整。
4. SDL3 / 图形后端只放平台层，不和功能层搅在一起。
5. 渲染槽位再拆细一点，别让一个 `ENTITY_OVERLAY` 扛太多东西。

## 给后续 AI 的提醒

如果看到代码里开始出现“什么都能塞进去”的趋势，先停。  
如果看到功能开始直接读底层私有字段，先停。  
如果看到 UI 开始直接改业务状态，先停。
