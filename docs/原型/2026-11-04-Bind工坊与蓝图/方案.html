六条结论

  1. wt-1 已完成主干迁移，但只迁了“编辑器本体”。绑定编辑卡与一览卡已从栖梦页迁入控制页 Bind 子页签，卡片归属 bind → controls，并新增了幂等修复 RepairLegacyBindTab。剩下的迁移对象是功能页的 qm:key_binds（8 条硬编码快捷绑定），以及 4 张栖梦卡里的“裸按键行”。
  2. 现有编辑器只能“追加 / 删除”，不能表达结构。命令链以竖向节点展示（bind_settings.cpp:398-443），但没有排序、分组、条件、模式语义，也没有“这个键还被谁用”的反馈。
  3. NM 的可借鉴点有三处，不是一处。动作卡（标题+说明+键位+模式+选项）、模式徽标（执行一次 / 按住 / 一键切换）、页首“键位占用”。三者分别解决“看不懂”“猜不到”“不敢改”。
  4. “蓝图”在 DDNet 里必须收敛为状态机图。控制台没有 sleep、没有 if、没有循环；唯一的分支表达是 toggle 类状态量与“自改绑”（bind 内再 bind）。因此图的边只能是“同帧顺序边”和“状态迁移边”，任何延时节点都必须显式标注为不可编译，或走新增调度命令（P3，需评审）。
  5. 工坊的落地关键不是画布，是编译器。节点图只是输入方式；真正的工程价值在于 图 → 命令串 → 校验 → 必要时降级为 cfg 这条管线，以及可回滚的应用流程。只要编译器可靠，画布可以迭代。
  6. 建议四期推进。P0 迁移收尾 + 键位占用（低风险、立刻减少入口分裂）；P1 动作卡 + 预设应用/回滚；P2 工坊画布 + 编译器；P3 可选时序扩展。P0 与 P1 不依赖任何新引擎能力。

1.3 五条硬约束

存储：32 × 512 槽，无条数上限

binds.h:52 的 m_aapKeyBindings[32][512] 决定“一个键+修饰组合只有一条命令”。所谓冲突不是“存不下”，而是同一物理键在不同修饰下的遮蔽关系。

行宽：单条绑定 16 KiB

MAX_CONFIG_LINE_BYTES = 16384（bind_editor.h:15），等于控制台 CONSOLE_MAX_STR_LENGTH。超限的图必须降级为 exec cfg。

时序：没有 sleep / if / 循环

绑定卡 model tab 是 controls，但 navigationTab="bind"。别名卡只有声明 navigationStableId 才跟随承载卡位置。

5.1 信息架构：从五处分散入口到一处入口、三层深度

一个命令只有一个编辑点；所有写入经统一校验与快照。

5.3 六条设计原则

  1. 一命令一编辑点。任何命令只能在一处被编辑，其余位置只读展示 + 跳转。这是消除 4 条写入路径的前提。
  2. 模式是推断结果，不是用户输入。徽标由命令串解析得出；用户若强行改模式，等价于改命令，必须显式预览。
  3. 图必须可编译。画布上任何不可编译的节点（延时、条件分支）在添加时就被标记为不支持，而不是等到应用失败。
  4. 超限自动降级。超过 16 KiB 或嵌套层数上限时，自动改写为 exec qmclient/binds/<id>.cfg，并在检视器里显示降级原因。
  5. 应用可回滚。每次应用记录受影响槽位的前值，支持单次撤销；不做全量配置快照。
  6. 数据与代码分离。预设是数据（JSON），编译规则是代码；新增预设不需要改 C++。

产品边界“流程图”在本方案里被限定为状态机。真正的顺序流程（先跳、等 100ms、再钩）在 DDNet 控制台无法表达。若产品坚持要时序，唯一路径是新增客户端调度命令（P3），这会引入自动化公平性争议，需要单独评审。

13.1 为什么不能“直接放进去”

那 6 个文件不是 Wiki 的页面，而是三张卡片的 ⓘ 面板正文。直接加章节，实际效果是四个问题：

问题具体后果
藏在第三层路径是「设置 → 控制 → Bind → 某张卡 → ⓘ → 参考资料」。没有任何一级导航能到达，新用户不可能路过。
内容重复三份三个页面各存一份相同的三条链接。以后加第四篇，改一处漏两处，且没有编译期检查能发现。

语言只覆盖 2 个目录随包 Wiki 只有 english 与 simplified_chinese；其它语言走内置三段式文案，新增章节不会出现。

所以顺序应该是：先定 Wiki 的入口形态（13.3），再定这三条链接放在哪一页、以什么措辞出现（13.4）。

14.6 量完尺寸后要改的三处结论

部位原方案假设按真实尺寸的结论
工坊布局（对应 D1） 三栏工作台，画布是重点 1000px 内容区容不下三栏。190 + 210 两侧栏占掉 412，画布只剩 548×约 470，拖两个节点就满。把蓝图独立成一个页签只能解决“和卡片抢位置”，解决不了画布窄：要么让它申请「全宽例外」（脱离 1000 上限），要么把检视器改成抽屉、流程库改成下拉。
官方 Bind 页 键盘 + 右栏 + 键位占用可以挤在一张卡 挤不下。键盘 14 列在 1000 宽里每键只有约 40px，右栏再占 208，占用来必须另起一张卡。这也说明 wt-1 把「绑定」与「绑定一览」拆两张卡是对的，不该合并。
密度 卡片可以放 8–10 行绑定 一屏只放得下 7 行（行高 20 + 间距 5，加上标题 40 与内边距 28，可视高约 620）。超过就要滚动，所以「键位占用」首屏必须只显示冲突与当前键，其余折叠。

页签层级：蓝图是独立页签，也能从工坊进入

两层页签各管一件事：

  • 第一行「控制 / Bind」是设置页原有的两项，对应 menus_settings_controls.cpp 的 apTabLabels，不改语义。
  • 第二行「官方 / 指令工坊 / 蓝图」是 Bind 内部的三层深度：官方是键盘编辑器，工坊是预设卡，蓝图是流程画布。
  • 蓝图有两个入口：第二行页签直接进；在工坊里双击某张卡片或点「编辑流程」，带着那张卡的数据进同一个页面。页签进是空白画布或上次的流程，卡片进是带着上下文。

代价是 Bind 子页签需要再存一个子状态（m_BindSubTab），搜索跳转也要带上它——否则从设置搜索点进「绑定」只会落在官方页。这一点要在 P0 的归属修复里一起处理。

下一步原型已经按真实 token 对齐，可以直接拿去改。真要做，建议先只改 官方 Bind 这一屏（加子页签 + 占用来），因为它不动工坊布局，也不依赖 D1 的结论；工坊与蓝图等 D1 定了再动。
