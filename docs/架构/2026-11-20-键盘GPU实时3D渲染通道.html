1 · 为什么必须动引擎

先说结论：现有的 IGraphics 是纯 2D 屏幕空间光栅接口，无论怎么绕都做不出「可自由旋转 + 真实光照 + 键名贴在斜面」的键盘。这不是工作量问题，是接口形状问题。

需求现有能力原因
顶点做三维变换不支持顶点结构只有 vec2 pos（屏幕坐标）+ uv + rgba，没有 z、没有法线、没有 MVP
逐像素光照不支持没有法线与光源 uniform，现有的「光照」全是离线烤进顶点色或贴图的
遮挡关系伪没有深度缓冲，只能画家算法；大面（机身顶面）按质心排序会被误判到键帽之前，必须硬编码层序
键名贴到倾斜键帽不支持CFreeformItem 只有 4 个屏幕坐标，UV 是 QuadsSetSubset 的批次级状态，没有逐四边形 UV
任意视角可以做但会崩CPU 投影 + 画家算法能转，但每帧要重排上千个面，且遮挡错误在斜视角下会暴露

另一个方向——把 3D 场景离线渲染成贴图——已经验证过（见 tmp/kb3d/，产出 1800×660 PNG + 102 键四边形表）。它能做到产品图级质感，但相机固定、RGB 是静态的、换视角要重渲。这是「照片」，不是「三维」。

决策：新增一条 GPU 3D 几何通道。键盘只是第一个使用者，之后的自定义 HUD、皮肤展示、战绩看板都能复用同一条通道。

2 · 现状与实测依据

2.1 现有的「专用通道」范式已经存在

引擎里已经有若干条绕过通用 2D 管线的专用绘制通道，每一条都是「命令 + 参数结构 + 三后端各自实现」：

命令用途后端实现
SCommand_RenderRoundedRectSdf圆角矩形 SDF 填充/描边GL / GLES / Vulkan / Metal 均有
SCommand_RenderMediaIslandSdf灵动岛形变 + 背景采样同上
SCommand_RenderProceduralRing程序化圆环同上

这意味着「加一条新通道」在本项目里是有既定做法的，不是从零发明：

  • src/engine/client/graphics_threaded.h 里加 SCommand_* 结构与 IGraphics 虚函数；
  • graphics_threaded.cpp 里加 Begin/End 状态机与命令入队；
  • 各后端在 *_qm_pipelines*.cpp / backend_vulkan_qm_pipelines_impl.h 里注册 pipeline；
  • shader 放 data/shader/，Vulkan 走 .spv，Metal 走 shader manifest。

2.2 已经能复用的东西

能力位置说明
离屏渲染目标SCommand_RenderTarget_Create灵动岛的背景采样已经在用；3D 可以渲到独立 target 再当纹理贴回 UI
顶点缓冲与批量上传m_aVertices / QuadsEnd沿用现成的顶点预算与 flush 机制
着色器编译链glsl_shader_compiler.cpp + data/shader/vulkan/*.spvGL/Metal 运行时编译，Vulkan 预编译
文字图集CTextRender只能上屏，不能渲进任意纹理——所以键名要单独烤图集，见第 10 节

2.3 一个容易混淆的点

Vulkan 后端里已经有 CreateStandard3DGraphicsPipeline("prim3d.vert.spv" …)。这里的 3D 指「2D 数组纹理」（QuadsTex3DBegin，地图图层用），不是三维几何。新通道不要复用这套 pipeline，避免语义混淆。

3 · 目标与非目标

目标

  • 像素级正确的三维几何：深度缓冲、正确的遮挡与自遮挡；
  • 实时可交互视角：拖拽旋转、滚轮缩放、极角约束；
  • 真实的逐像素光照：方向主光 + 半球环境光 + 边缘光 + 高光；
  • 逐键 RGB：每个键独立颜色、独立亮度、可做呼吸/波浪动画；
  • 键名贴在键帽斜面上，随视角透视变形；
  • 鼠标拾取到具体按键，接现有 CBindSlot / CBinds；
  • 三后端（OpenGL、Vulkan、Metal）表现一致。

非目标

  • 不做 PBR 全流程（IBL 预过滤、多散射 GGX），首版只做 Lambert + Blinn-Phong + 半球环境；
  • 不做实时阴影贴图（用接触阴影 + 屏幕空间 AO 贴图替代）；
  • 不做景深 / 运动模糊 / 体积光；
  • 不改游戏世界渲染（地图、tee、粒子仍走原 2D 管线）；
  • 不做通用场景图/材质系统，通道只接受「一组三角形 + 若干 uniform」，业务层自己管模型。
  • 不做移动端。Android / iOS 不在本次范围，GLES 后端与移动 GPU 精度适配一律不碰；观战端维持现状。

4.1 为什么渲到离屏 target 再贴回 UI

方案优点缺点
直接画进主 framebuffer + scissor少一次 resolve，省内存深度状态要和 2D UI 共用一块区域；圆角裁剪做不了；3D 区域的背景模糊/发光无法叠加
离屏 target → 当纹理贴回3D 区域天然是一个 UI 元素（可圆角、可做 hover 光晕、可淡入淡出）；深度只存在于自己的 target 里，不可能泄漏到 2D UI多一次 resolve；多一块 RGBA + depth 的显存

选后者。理由不只是灵活：深度状态泄漏是这条通道最危险的事故——一旦 3D pass 结束后没关 depth test，整个菜单会变成空白。把 3D 关在自己的 target 里，这类事故从「必然发生」降级为「不可能发生」。

5 · 引擎接口设计

5.1 新增顶点格式

struct GL_SVertex3D
{
    vec3 m_Pos;        // 模型空间
    vec3 m_Normal;     // 模型空间单位法线
    vec2 m_UV;         // 键名图集坐标（无贴图时填 0）
    uint32_t m_Color;  // RGBA8 albedo
    float m_KeyIndex;  // 所属按键索引，-1 表示不属于任何键
};                     // 44 字节

m_KeyIndex 是关键设计：它让「每颗键的下压动画」和「逐键 RGB」都能在一次 draw call 里完成——shader 用这个索引去查两个 uniform 数组（uKeyPress[128]、uKeyColor[128]），把偏移加到顶点位置、把颜色加到自发光。否则 102 颗键就是 102 次 draw call。

5.2 新增接口

struct S3DView
{
    float m_aViewProj[16];   // 列主序
    vec3  m_CameraPos;
    vec3  m_LightDir;        // 指向光源
    vec3  m_LightColor;
    vec3  m_SkyColor;        // 半球光上半球
    vec3  m_GroundColor;     // 半球光下半球
    float m_Exposure;
    int   m_TargetId;        // 离屏 target，-1 表示主目标
    int   m_aKeyPress[128];  // 定点数，1/1024 单位
    uint32_t m_aKeyColor[128];
    int   m_KeyCount;
};

struct SMesh3D
{
    int   m_VertexBufferId;  // 静态 VAO/VBO，创建一次
    int   m_VertexCount;
};

virtual int  CreateMesh3D(const GL_SVertex3D *pVertices, int Num) = 0;
virtual void DeleteMesh3D(int Id) = 0;
virtual void Begin3D(const S3DView &View) = 0;
virtual void DrawMesh3D(int MeshId, const mat4 &Model) = 0;
virtual void End3D() = 0;

接口刻意保持窄：不做场景图、不做材质系统、不做实例化。业务层想画什么就自己组三角形。这样通道的维护成本与「一条 SDF 通道」同级，而不是「一个小 Unity」。

6 · 三后端实现

后端要加的东西难度
OpenGL 3.xVAO/VBO、glEnable(GL_DEPTH_TEST)、GLSL 330 着色器、深度附件（renderbuffer）低
Vulkan新 pipeline（顶点输入布局、深度附件格式、动态视口）、descriptor set（uniform buffer）、预编译 spv中高
Metal新 pipeline state、深度纹理、shader 加进 metal_shader_manifest.h中

Android 的 GLES 后端不在范围内，所以只需要三条路径。三条里 Vulkan 最费事：要新增一个 descriptor set（MVP + 光照 + 两个数组），还要为深度附件挑格式（D32_SFLOAT）。建议先做 GL，再 Metal，最后 Vulkan——GL 迭代最快，能把 shader 和参数调到满意，再照抄到另外两个。

7 · 深度与合成顺序

每帧的 3D 部分只有三步，且全部发生在自己的 target 内：

1) 绑定 3D target
2) clear(color=页面背景色, depth=1.0)
3) Begin3D(view)
   DrawMesh3D(body)            // 不透明：depth write on, 无混合
   DrawMesh3D(keycaps)         // 同上
   ── 透明阶段 ──
   DrawMesh3D(ledHalos)        // depth test on, write off, 加色混合
   End3D()
4) 解绑 target，作为纹理交给 2D UI 的圆角卡片绘制

不需要画家算法：深度缓冲负责遮挡，绘制顺序只剩「不透明→透明」两档。之前 CPU 方案里那些硬编码层序、大面排序的坑全部消失。

8 · 着色器与光照模型

// 顶点
vec3 worldPos = (uModel * vec4(aPos, 1.0)).xyz;
worldPos.z += uKeyPress[int(aKeyIndex + 0.5)] * uPressScale;  // 按键下压
vec3 n = normalize(mat3(uModel) * aNormal);
gl_Position = uViewProj * vec4(worldPos, 1.0);

// 片元
vec3 V = normalize(uCameraPos - worldPos);
float NdotL = max(dot(n, uLightDir), 0.0);
vec3 ambient = mix(uGroundColor, uSkyColor, n.y * 0.5 + 0.5) * 0.55;
vec3 diffuse = uLightColor * NdotL;
vec3 H = normalize(uLightDir + V);
float spec = pow(max(dot(n, H), 0.0), 48.0) * 0.35;
vec3 albedo = texture(uAtlas, vUV).rgb * vColor.rgb;
vec3 emissive = uKeyColor[keyIndex].rgb * uKeyBrightness;
vec3 color = albedo * (ambient + diffuse) + spec + emissive;
color = ACES(color * uExposure);

刻意不做 IBL：半球光 + 一个主光 + 一个 Blinn-Phong 高光，在这个视角范围内已经足够像金属和 PBT。真的需要环境反射时，再加一张 uEnvMap，接口不用改。

9 · 键盘模型

程序化生成，不导入 GLB——理由有三：体积（顶点比模型文件小）、可主题化（颜色走 uniform 不走贴图）、参数化（换布局只改一张 key 表）。

部件几何三角形
机身圆角矩形挤出 + 内凹定位板，2 层≈ 600
键帽 × 1024 环 loft（底→腰→肩→顶）+ 顶面碟面，圆角 4 段≈ 5 600
轴体（可选）可见键缝里的轴壳，只用 1 个方柱≈ 1 200
RGB 灯晕每键 1 个四边形，加色混合≈ 200
合计≈ 7 600

7 600 三角形对任何 GPU 都是噪声级别。真正的成本在 draw call 数——所以用 m_KeyIndex 把 102 颗键压成 1 个 mesh，全场景 3 个 draw call。

9.1 键位表从哪来

已经有现成的：tmp/kb3d/assets/keyboard_ui.json 里 102 个键的 KEY_* 映射，以及 KeyForge 的 keyboardLayouts.ts（code / label / x / y / w / h）。落地时把这张表转成 C++ 常量数组，模型生成器和拾取都用它。

10 · 键名贴图

这是整个方案里唯一「取巧」的地方，说清楚为什么：

  • CTextRender 只能把字形画到当前 framebuffer，画不进任意纹理；
  • 所以键名不能边画边生成，必须离线烤一张图集；
  • 图集：102 个键名 → 1024×512 RGBA，A8 或 RGBA4444 都够，约 0.5 MB；已确认可以新增进 data/；
  • 每个键帽顶面的 UV 在生成模型时直接写死成图集里对应的矩形，零运行时开销。

图集用现有的 Python 管线生成（tmp/kb3d/render.py 已经在做透视贴字，抽出来改写成图集即可），产物进 data/qmclient/keyboard/keycap_atlas.png。

备选：如果不想加图集资产，键名可以退化成「屏幕空间文字」，由 2D UI 在 3D 之后叠加。缺点是不随键帽倾斜，视角一斜就露馅。建议一步到位做图集。

11 · 拾取与交互

// 鼠标 → 世界射线 → 逐键 AABB 求交
vec2 ndc{ (MouseX / w) * 2 - 1, 1 - (MouseY / h) * 2 };
vec3 dir = normalize(inverse(uViewProj) * vec4(ndc, 1, 0) - cameraPos);
for (key : keys) if (RayHitsBox(cameraPos, dir, key.aabb)) → 最近的那个
  • 用 CPU 射线求交，不用深度回读——回读要等 GPU，会掉一帧。
  • 每颗键存一个轴对齐包围盒（模型空间 + 世界矩阵），102 次求交可以忽略。
  • 命中后转换成 CBindSlot(KEY_W, m_ModifierMask)，直接写进现有的 SBindEditorUiState.m_Selected——不新建选中状态，右侧编辑面板一行都不用改。
  • 悬停高亮：命中索引通过 uHoverKey 传给 shader，描边在片元里按 UV 到边缘的距离算。

12 · 页面入口与渲染模式

键盘不是一个独立的设置页，而是 Bind 编辑器工作区 的下半部分。入口、形态、渲染模式都按地图编辑器的既有做法来，不新造模式。

12.1 入口：右侧顶部导航栏

现在右侧导航是 CapsuleTabBar 的 5 个槽位（截图 / 录像 / 编辑器 / 设置 / 退出，menus.cpp 约 2925 行）。新增一个「Bind 编辑器」槽位，图标沿用笔形或键盘形，MobileSpectator 时不显示——和现在编辑器槽位在移动端的处理一致。

12.2 形态：独立工作区，全屏接管

右上角导航「Bind 编辑器」
┌─ 工具栏：打开 / 保存 / 撤销 / 应用 / 返回 ─────────────┐
│ 文件与入口键 │ CFG 引用画布（可缩放平移）│ 原文与诊断 │
│              ├──────────────────────────────────────┤
│              │ 3D 键盘（可收起，收起后画布铺满）      │
└──────────────────────────────────────────────────────┘

和 《Bind 编辑器：现状及改进方案》第 2 节的目标布局一致：键盘与画布共享同一个工程、同一个选中项、同一份草稿，点键高亮画布上的绑定，点画布上的绑定反向选中键，全程不切页。

12.3 渲染模式：打开时其他页面停止渲染

硬要求：工作区打开的期间，设置页、浏览器、主菜单一律不再绘制，也不做它们的布局与命中计算。

理由有两层：

  • 正确性：工作区是全屏的，底下页面没有任何可见区域。让它继续画，等于每帧白送一次完整的设置页开销——包括那张 104 键的键面。
  • 状态干净：设置页现在有一套交互趟 + 背景出图趟的双趟机制，如果两套 UI 同时跑，焦点、滚动、输入捕获会互相抢。

实现上不做新机制：编辑器本来就是 FeedbackPage 之外的全屏状态，进入时切走、退出时回到进入前的页面（返回按钮走的也是这条路）。3D 的离屏 target 在这一段生命周期内创建，退出时销毁——这也顺带满足第 7 节「深度状态不可能泄漏」的前提。

12.4 与现有绑定页的关系

「控制 → 绑定」那张平面键面保留，两个入口共享同一份 CBindSlot 选中状态：从绑定页点一颗键，再进工作区，选中的还是那颗；反过来也一样。等 3D 版本稳定后，再决定是否把平面键面降级成「快速选择」。

5逐键 RGB + 下压动画改配置能实时变色，按键有位移
6相机交互 + 拾取 + 接 CBinds点键能选中，右侧面板同步
7Vulkan + Metal 补齐，三后端对齐同一场景截图差异 < 2%
8接入右上角导航 + 独立工作区外壳（全屏接管、其他页面停止渲染、退出回到原页）进出 200 次无残留；关闭后原页面状态不丢
9与 CFG 画布联动（点键高亮绑定、反向选中）、键盘收起/展开双向定位原地完成，不切页

阶段 0–2 是决策点：如果 GL 上的画质或手感不能接受，此时停手的沉没成本最小。

16 · 风险与回退

风险后果对策
深度状态泄漏到 2D UI整个菜单空白，线上事故级3D 只在自己的 target 内；End3D() 后强制恢复「无深度、无剔除、混合开启」并加断言
三后端表现不一致某个平台颜色/高光不同同一份 shader 逻辑，参数集中；截图对比脚本纳入验证
Vulkan descriptor 绑定错误黑屏或验证层报错先跑 dbg_gfx 1 + Vulkan 验证层，零 VUID 再进阶段 1
与现有 blur/render target 通道冲突背景模糊串色target 生命周期独立，不复用 blur 的中间纹理
回退方案：配置项 qm_keyboard3d_mode（0=关闭走烘焙贴图，1=GPU 3D）。烘焙版资产已经在 tmp/kb3d/assets/ 验证过可用，页面结构（左导航 / 键盘画布 / 检查器）两者共用，切换只换中间那块绘制。

17 · 验收标准

  • 视觉：任意视角下无穿模、无 Z-fighting、键帽边缘无锯齿（开 MSAA 或 4x 超采样 target）；
  • 一致性：GL / Vulkan / Metal 同参数截图，逐像素差异 < 2%；
  • 性能：1080p 下整页渲染增量 < 2 ms；
  • 状态：进出页面 200 次，UI 无残留、无空白、显存不增长（render target 正确释放）；
  • 交互：102 键全部可点中，边缘不误判；与旧键面的选中状态双向同步；
  • 工程：run_cxx_tests + 现有 gate 全绿；新增的网格生成与拾取有单元测试（射线-包围盒、键位表映射）。

不做完不算完成的部分

  • 三个后端只要有一个没截图对齐，不能宣称「跨平台通过」；
  • 构建成功不等于渲染正确，必须有实机截图；

Bind 编辑器：现状及改进方案定义工作区布局、CFG 文件模型、蓝图与键盘的联动方式、实施顺序。本篇只补充「键盘这一块怎么渲染」。

3D 模型的来源

键盘模型与材质效果来自 KeyForge 3D（公开仓库，可直接 clone）：

  • github.com/wuqie-xuanzhao/Keyboards —— React + three.js，src/three/keyboardBuilder.ts 是参数化建模，keyboardMaterials.ts 是 PBR 材质，availableModels 支持 full104 / tkl80 / compact60 / pro75 / numpad21 / keypadLeft。
