1. 为什么单独立项

2026-11 的调研把客户端改进分成三层：已确认缺陷、每帧固定开销、结构性维护债。前两层中能安全落地的部分已经完成（见第 2 节）。剩下三项都不适合在共享工作树里随手做：

  • 改动面横跨 65–197 个文件，与并行会话必然冲突；
  • 收益不是"某个函数更快"，而是编译面、可测性和每帧成本的结构性变化，需要基准与对照；
  • 一旦中途半成品合入，会同时存在两套布局真值或两套注册表，比不改更糟。

因此本文只定义边界、顺序和验收，不承诺排期。任何一项开工前，应先在本文件追加"开工记录"，写明基线提交、独占槽位和预期对照数据。

3. 工作项 A：消除卡片内容声明重放

问题

CSettingsCardDeck::RenderInternal 每帧对所有未折叠卡片调用 m_ResolveContentLayout，以 DECLARE 趟回放整张卡内容并构造行字符串。布局缓存命中只能省掉布局对象，省不掉声明构建。按每页 20+ 卡、每卡 3–20 行估算，单帧可达数百次字符串构造；拖拽与几何变化帧约 3 倍。

为什么不能"屏幕外就不测"

deck 需要全部卡片高度来计算滚动范围，而跳过声明的目的恰恰是不算高度。唯一自洽的解法是把"测量"和"重放"拆开：屏幕外保留上一次的高度，只在卡片进入预加载边距时重新声明。这带来"屏幕外内容变化后高度滞后"的窗口，必须在设计里明确接受，否则会反复返工。

A1 视口延迟测量（先做）

  • 为每张卡保留"上次有效高度"，卡片矩形与视口加一屏预加载边距不相交时，跳过 m_ResolveContentLayout，用旧高度参与总高计算。
  • 以下情况仍强制重新声明：宽度变化、m_MeasureRevision 变化、卡片重新进入视口、存在待提交弹层、正在播放展开动画。
  • 页面首次进入没有缓存高度，仍全量测一次；可复用已有设置页 warmup 预算，不额外加帧。

风险：滚动条长度在页面刚进入时可能抖动一次。验证：基准对比"滚动一页"的 layout 用时与声明次数；客户端滚动到底部与快速上下翻页无空白卡。

A2 每卡依赖修订号（A1 之后）

  • SSettingsCardDefinition 增加声明修订号；UseDeclaredContent 接受"本卡依赖"回调。
  • 默认值表示"永远重放"，卡片逐张迁移，未迁移的卡行为完全不变。
  • 修订号由卡片实际读取的配置项组合而成（位掩码/整数混合），比要求每张卡自己维护缓存更便宜、更不容易漏。
  • 迁移顺序：行数多且无弹层的卡（hud、visual、ddnet）→ 带展开动画的卡（tee）→ 带弹层的卡（bind）。
  • 收尾条件：加一条静态合同测试，确认 BuildCard 链里每张卡都登记了修订号提供者，防止漏迁。

前置：先补 SettingsCardDeck 基准与 heap_allocs 真实赋值。没有对照数据，A2 不应开工。

4. 工作项 B：CQmClient 分域拆分

CQmClient 目前 333 行头、239 个方法、83 个成员，混合 WebSocket 实时服务、匿名表情、新闻/markdown、赞助列表、头衔鉴权、生命周期标记、游玩时长、DDNet 档案抓取、本地统计、开发者认证、地图标签等领域。HTTP/WS 任务与失败回滚交织，无法按服务注入 fake。

拆分顺序（离网络越远越先拆）

#域难点
1游玩时长 / 本地统计纯数据，无网络；先验证拆分手法本身
2新闻 / markdown缓存与刷新节流
3赞助列表、作者列表静态数据 + 失败回退
4头衔鉴权与中心服交互、失败保持旧状态
5DDNet 档案抓取、地图标签外部 HTTP、取消与代际
6匿名表情上传/下载任务
7WebSocket 实时服务最后做：重连、增量基线、关闭顺序

机械做法

  • 每个域抽成独立服务类，放在 components/qmclient/；CQmClient 保留同名转发方法，65 个 UI 文件一行不用改。
  • 每个域一个独立提交，可单独回退；同一时间只迁一个域。
  • 真正的难点是生命周期：谁拥有 job、谁负责 cancel、析构与 CJobPool::Shutdown 的顺序。每个域落地前先写这段说明，再写代码。

5. 工作项 C：卡片注册表统一与 CMenus 解耦

C1 单一 descriptor 表（先做）

新增一张卡目前要同步：默认注册表、页清单、BuildCard if 链、26 个搜索索引、Wiki 文案、布局适配 switch、模块特判。漏一处就出现"搜索有、页面没有"。

  1. 先把现有各表原样收进一张 descriptor 表，同时写 parity 测试：生成的页清单与搜索列表必须与旧表逐项相等。
  2. 逐个消费者切换（页清单 → 搜索 → Wiki → 布局适配），每切一个跑 parity。
  3. 删除旧表；descriptor 表成为唯一真值。

风险低、机械，但工作量在 163 张卡的数据搬迁上，适合独占槽位慢慢做。

C2 CMenus 解耦（最后做）

  • 引入卡片宿主接口（文本渲染、UI 上下文、配置访问、动画运行时），CMenus 实现它。
  • 卡片内容函数从 CMenus 成员改为接收宿主的自由函数，按页分批：TClient → hud → visual → bind → credits。
  • 收益是编译时间与可单测性，不是运行时性能；代价是 65 个文件的改动面。

7. 风险登记

风险影响缓解
A1 让屏幕外卡片高度滞后滚动条长度短暂不准进入预加载边距即重测；页面进入时全量测一次；接受该窗口并写入注释

8. 验收标准

工作项必要证据
A1基准：同一页滚动一帧的声明次数与用时前后对照；客户端滚动无空白、无跳变
A2基准：改一张卡的配置后，只有该卡重新声明；静态合同覆盖全部卡片
B每域：构建 + 全量 C++ 测试 + 冒烟；网络域补 fake 传输的取消/失败/重入测试
C1parity 测试在迁移前后逐项相等；搜索、Wiki、页清单三处结果一致
C2每批：构建 + 相关测试 + 设置页人工交互验收

"构建通过"不等于运行时、端到端、视觉或跨平台行为通过；性能结论以同场景前后数据为准，不以单次测量下结论。

9. 明确不做的事

  • 任何触碰网络协议、快照、输入时序、物理/预测、地图或 demo 格式的架构改动。
  • 没有同场景前后数据的"大重构"。
  • 性能报表的离线化：该报告已长期不用，按维护者决定放弃（2026-11-11）。
  • 为移动观战端单独引入架构约束；移动端只在改动确实落在其专有路径时才纳入评估。
