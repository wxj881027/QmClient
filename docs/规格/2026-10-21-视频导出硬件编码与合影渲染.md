## 第二期：硬件编码与 4K 自适应

### 编码器家族别名

新增三个别名：`h264`、`hevc`、`av1`。写别名时，运行时按「NVENC → QSV → AMF → VideoToolbox → 软件」的顺序取本机第一个真正可用的实现，而不是写死某个厂商。

解决的现实问题：旧预设把「高效高画质」写死成 `hevc_nvenc`，在没有 NVIDIA 显卡的机器上直接导出失败；有卡但驱动不支持的机器同样失败。用别名后预设可以跨机器复用，且不会出现「预设看起来能用、一点就报错」。

几个刻意的取舍：

- **别名只认本机探测可用的实现**。探测走已有的三层链（FFmpeg 是否编入 → 真实 `avcodec_open2` → 像素格式可协商），不是查表猜。
- **拼错的编码器名不会被当成可用**。`libx2640` 这类输入在解析阶段就被拒绝，避免导出跑到一半才以难懂的 FFmpeg 错误失败。
- **该家族完全不可用时就失败**，不回退到别的编解码器——静默换编解码器会让产物与用户选择不符。

### 4K 自动切硬件

`ShouldAutoPickHardware`：只有在**用户没有显式指定编码器**（配置为空，跟随封装器默认）**且输出高度 ≥ 2160** 时，才自动挑 HEVC 或 H.264 的硬件实现。

依据是实测：4K60 下 libx264 medium 只有约 38 fps，达不到录制帧率，导出会被编码拖成瓶颈；同场景 `av1_nvenc` 约 58 fps、`hevc_nvenc` 约 47 fps。1080p 下软件编码仍能跑满，所以不动——自动切硬件会引入硬件与软件的画质差异，没必要在不需要的场景里发生。

显式选择永远优先：用户写了具体编码器或别名时，这条逻辑完全不介入。

## 第三期：`.poses` 合影渲染

### 为什么走合成快照

MomentCap 让合影显示出来的机制，是**服务端把这些 pose 当成假客户端塞进快照**，客户端只是照常解析。所以这里不复刻渲染逻辑，而是把 pose 数据合成为一份快照，交给客户端已有的解析与绘制管线——皮肤、表情、武器、钩子、队伍颜色、名字牌全部免费复用。

新增三个组件：

`pose_file.h/.cpp`（解析层）
- 格式是 C++ 结构体裸 dump，**没有魔数、没有版本号**，每条固定 248 字节。
- 因此解析只做长度与字段合法性校验：长度必须严格等于 `8 + N×248`，坐标必须在 ±1000000 内，条数上限 4096。任何不一致都判失败，不猜布局继续读。
- 失败时**不修改输出**，调用方拿不到半份数据。

`pose_scene.h/.cpp`（合成层）
- 每名 Tee 生成四类对象：`CLIENTINFO` / `PLAYERINFO` / `DDNETPLAYER` / `CHARACTER`；另加一份 `GAMEINFO` 与 `SPECTATORINFO`。
- 没有 `GAMEINFO` 时客户端多处逻辑会整体跳过，所以它必须存在。
- 不挂钩时把钩子端点收敛到 Tee 自身，否则渲染器会从坐标原点拉一条斜线到场内。
- 速度置 0：合影是静止造型，有速度会让渲染器做朝向插值，造型会漂。
- 相机默认放在所有 Tee 的包围盒中心，也可显式指定。
- 上限 64 人，超出的部分不渲染，并在统计里如实报告人数。

`CClient::ApplySyntheticSnapshot`（注入层）
- 走与 `OnDemoPlayerSnapshot` 相同的落盘路径，只是不接受 delta。
- 需要连续应用两次：客户端要求同一角色在 `SNAP_PREV` 与 `SNAP_CURRENT` 都存在才会标记为 Active。

### 使用方式：和 demo 一样的多条路径

demo 有两种用法——游戏内回放观看、导出成文件。合影与之对齐，共三条入口：

| 命令 | 用途 | 对应 demo 的 |
| --- | --- | --- |
| `poses_open <poses>` | 游戏内观看，相机可自由移动 | 演示播放器播放 |
| `poses_render <poses> [名]` | 导出静态截图 PNG | —（合影特有） |
| `poses_video <poses> <名> [秒]` | 导出视频，走既有录制管线 | 渲染 demo 视频 |
| `poses_close` | 退出合影会话，恢复正常渲染 | 停止播放 |

三条入口共用 `EnterPoseSession`：读文件 → 解析 → 合成快照 → 连续应用两次 → 进入会话。差别只在于会话建立之后做什么。这也解决了原来每次都要重复一遍准备逻辑的问题。

`posesrender` 是 `poses_render` 的无下划线别名（部分输入方式打不出下划线）。

地图用当前已加载的那张——合影通常配固定背景图，先进入那张图再执行。demo 播放中会先暂停回放，否则播放器每 tick 推送的新快照会把合成快照覆盖掉。

截图落在 `screenshots/<名>_<时间戳>.png`（沿用客户端既有截图命名）。

### 视频导出的实现要点

`poses_video` 走 `StartVideo` 这条与 demo 相同的录制入口，但 demo 已经被暂停，时间轴不会自己走，录制管线拿不到新帧。因此主循环里为合影会话单开一条分支 `AdvancePoseVideo`：每帧重新应用一次合成快照（防止任何后续快照覆盖），再提交一帧给编码器，按 `VideoFrameCount(秒数, 帧率)` 决定何时收尾。

结束条件用**帧数**而不是浮点累减的秒数——后者会因精度问题提前或延后一帧。`VideoFrameCount` 向上取整，保证「录 0.001 秒」也至少产出 1 帧，而不是宣称录制成功却没有内容。

收尾顺序是先退出合影会话再停录，确保成片的最后一帧仍是合影画面，不会闪回原 demo。

## 实机验证记录（用户提供的 182 人 latest.poses）

- **发现并修复三个真实缺陷**，全部由用户原始文件实测暴露：
  1. **tick 固定导致每帧重复应用**：主循环里每帧用同一 tick 反复调用 `ApplySyntheticSnapshot`（同一帧内 7 次），客户端把相同 tick 当成同一份快照，`SNAP_PREV`/`SNAP_CURRENT` 永远形不成有效的角色对。修复：主循环重放分支删除（demo 暂停时无人覆盖快照），会话建立时两次应用 tick 递增，视频推进每帧 tick 递增。
  2. **相机不对准合影**：所有 Tee 都设为普通玩家时，demo 回放态下相机不使用 `SPECTATORINFO` 坐标。修复：合成快照默认把全部 Tee 放入旁观者队（`SSceneOptions::m_Team = -1`），客户端在旁观状态下才采用 `SPECTATORINFO` 坐标取景；旁观者同时不参与队伍染色，正是合影需要的效果。
  3. **坐标分散导致画面出框**：真实合影分布在 2700×2966 的世界里，默认缩放下一屏装不下。验证时用 `posescompact`（坐标向中心收缩 3 倍）确认了渲染正确；正式的「自动取景」（按包围盒调缩放）属后续 UI 工作。
- **验证证据**：`poses_open latest.poses`（182 人裁到 64 人上限）日志 `building snapshot for 64 tees`、`applied synthetic snapshot` ×2（tick 递增）；`posesopen posescompact.poses`（182 人全部）后截图确认：相机落在重定位后的合影中心、多个 Tee 渲染可见、名字牌正常显示。
- **测试**：C++ 全量 5820/5820；`QmPoseScene.VideoFrameCountCoversShortDurations` 覆盖帧数计算的边界（短时长、非法输入）。

## 第四期：照片卡圆角、皮肤加载与画质

### 照片卡四角与"卡片里没有照片"（已修复）

旧实现把成片当普通 quad 画进矩形裁剪区，放大/平移后图片铺满矩形四角，而那里正是底板圆角之外，于是露出方角。做法是让圆角 SDF 直接采样纹理：图片成为圆角容器的填充，四角按同一个圆角覆盖度裁掉。

这条纹理管线曾经只输出透明像素（照片卡只剩外框）。根因在 **Vulkan 描述符集号**：

- 纹理变体的管线布局是「set 0 = 图片采样器，set 1 = 参数 UBO」（与 media island SDF 同构），C++ 侧也确实把 UBO 绑到 set 1；
- 但 `rounded_rect_sdf.frag` 里参数块一直写着 `set = 0, binding = 1`（无纹理变体的布局）。纹理变体的 set 0 只有 binding 0，片元读到的是一块从未绑定过的内存（全 0）；
- 于是 `TexParams0.x`（启用纹理）读成 0，着色器跳过采样分支，而 `m_FillColor` 是 `vec4(0)`，输出 alpha 就是 0：照片整块透明，而同一命令里的边框（纯色变体）照常画出来，观感就是"卡片里什么都没有，只剩外框"。

修复：参数块在 `TW_ROUNDED_SDF_TEXTURED` 下声明为 `set = 1, binding = 1`，无纹理变体保持 `set = 0`。SPIR-V 反汇编确认 `gSdf: DescriptorSet 1 / Binding 1`、`gTextureSampler: DescriptorSet 0 / Binding 0`，与两套管线布局一致。

**OpenGL 侧未发现缺陷**：临时读回诊断显示纹理变体拿到的是 `gRoundedRectSdfData[15].x = 1`、采样器单元 0、0 号单元绑定到命令携带的贴图（`boundTex` 与命令里的 GPU 贴图一致），绘制正常。之前"GL 也全透明"的观察没有在修好后的构建里复现（当时读的是同一份数据目录，最可能是程序/数据不同步）。

配套改动：

- `SRoundedRectSdfParams` 由 15 个 vec4 扩到 17 个：`m_TextureParams0`（x=启用纹理，y/z=UV 缩放，w=UV 偏移 x）与 `m_TextureParams1`（x=UV 偏移 y，y=整张照片透明度）；
- 纹理走独立管线变体（OpenGL 独立 program，Vulkan 由 `cmake/BuildVulkanShaders.cmake` 生成 SPIR-V），既有圆角控件零改动；Metal 不实现该变体并返回 false，照片卡自动回退；
- 照片卡（`ui_effects.cpp` 的 `RenderScreenshotAnimation`）切回 `DrawRoundedImage`：UV 按"卡片像素 → 图片 UV"折算，边框和照片同一次绘制提交（同一套圆角覆盖度）；普通四边形 + 贴图预烘焙 alpha 保留为能力回退；
- 透明度必须走 shader：SDF 填充没有别的着色入口，`DrawRoundedImage` 把 `Image.m_Alpha` 写进 `TextureParams1.y`，片元乘在采样 alpha 上，卡片淡出时照片和边框一起消失。

**实机验证**（隔离 profile + PostMessage 注入按键 + 客户端自带截图，1280x720）：

- OpenGL 与 Vulkan 都把成片正确显示为圆角卡片，1 倍贴合下照片铺满卡片；
- 把看图视口临时强制放大 2 倍（验证后已删除）再截图：两个后端的卡片四角都是圆弧；角点像素仍是背景色、向内约 2px 才变成照片灰色，说明方角是被圆角覆盖度真实裁掉，而不是被别的色块盖住；
- `gfx/sdf` 临时诊断（OpenGL）：`shaderTexData=(1.000 0.00094 0.00167 0.500)`、`samplerUnit=0`、`boundTex=1084`，与命令携带的贴图一致。

**卡片投影已移除**：原来照片后面还有一张 `0.28` 黑、按 `2+8*Ease` 偏移的圆角矩形当投影，硬边且在浅色背景上会露出一条明显深色带，看着像多了一层底板。像素可以反推：深色带颜色 (89,92,79) 正好是背景 (123,128,110) 的 72%，即 28% 黑覆盖。现在只保留 1px 描边，不再画投影。

### 合影预览：鼠标跟随与状态栏（本次修复）

- **走自由旁观语义，不是"进预览就能推镜头"**：镜头只在 `SpectatorId == SPEC_FREEVIEW` 时跟随 `m_aMousePos`；跟随某个 Tee 时用会话取景。这正是玩家说的"按旁观 HUD → 选自由视角之后才能移动，跟游戏内和 demo 回放一样"。
- **自由视角在合影会话里原本选不出来**：`CSpectator::Spectate()` 在 DEMOPLAYBACK 下把 id 夹到 `[SPEC_FOLLOW, MAX_CLIENTS-1]`，`SPEC_FREEVIEW(-1)` 被夹成 0（跟随某个 Tee）——玩家点了自由视角也只是跟随角色，鼠标永远推不动镜头。现在合影会话放宽下界到 `SPEC_FREEVIEW`。
- **增量必须交给 CControls**：`m_vpInput` 里 menus 在 controls 之前，菜单返回 true 就吃掉了增量。合影预览改成只把增量换算成 UI 光标，然后返回 false，让 `CControls::OnCursorMove` 走和游戏内/demo 完全同一条累加路径。
- **暂停标志不能连累自由视角**：合影快照永远带 `GAMESTATEFLAG_PAUSED`（世界不推进），而 `CControls::OnCursorMove` 原本见到暂停就直接返回。合影会话里跳过这个早退，否则自由视角同样推不动。
- 灵敏度是**画面 1:1 跟随**：世界位移 = 光标增量 / 缩放。乘缩放是瞄准语义，取景一拉远（zoom < 1）光标走一大段画面几乎不动。
- **面板打开时不推镜头**：预览 HUD（拍一张/渲染/适配取景那张卡片）打开时，菜单层吃掉光标增量，镜头钉住不动——一边点按钮一边晃画面没法用；HUD 关掉才是取景状态。按住左键同理（光标归拖拽）。
- 抓帧那一帧也不再改镜头，成片与快门画面一致。
- **渲染阶段不能再改镜头**：`CCamera::OnRender()` 原本会在渲染前重算一次 `m_Center`（demo 镜头轨迹 / 自由视角平滑 / 快照 `SpecInfo.Position`），合影会话里这三条都会把画面钉在固定取景上——表现就是"相机状态在变、屏幕不动"。合影会话在该函数里直接返回，镜头只由会话取景与自由视角决定。
- **状态栏**：合影预览本身就是取景器，整个会话期间不画 tclient 状态栏（`PoseSessionActive()` 直接返回），否则它既挡在画面角落，也会被玩家自己的截图带进成片。

**看图窗口为何不套圆角**：独立的看图窗口（--qm-screenshot-viewer）是 SDL 软件渲染的**文件查看器**，用 SDL_RenderTexture 原样贴图。给它加圆角会让人看到「文件里并不存在的圆角」——用户刚渲染出的 PNG 有方角，查看器却显示圆角，这是显示保真度回退，不是统一。目标里的「统一走圆角纹理路径」按**游戏内展示面**理解：照片卡（ui_effects.cpp 的 RenderScreenshotAnimation）已走 DrawRoundedImage；文件查看器保持忠实显示。

### 社群皮肤在成片里退回 default（已修复）

根因不是缺某种皮肤数据通道（本仓库没有该机制），而是**时序竞态**：皮肤由 CSkins 按名字异步加载，m_ContainerUpdateTime 有最高 500 ms 节流，而抓帧只等 2 帧就开拍，此时社区皮肤仍是 PENDING，RefreshSkin 回退到 default。

修复分三处：

1. CSkins::PoseSkinsReady() 按快照里用到的皮肤名驱动加载并回报是否可绘制；终态（ERROR／NOT_FOUND）提前放行，避免永远等下去。判定抽成内联纯函数 PoseSkinWaitIsFutile 以便单测（testrunner 不编译 skins.cpp）。
2. CGameClient::PoseSkinsReady() 只收集**快照里真实存在的客户端**（m_Snap.m_aCharacters[i].m_Active）。m_aClients 是定长数组，未使用槽位也带默认名字，全算进来会让闸门永远在等一批不存在的皮肤——这是实现过程中真实踩到的坑。等待期间每帧调 UpdateForSettingsWarmup() 绕过节流。
3. CClient::PoseSkinsReadyForCapture() 是引擎侧闸门，必须放在**离屏帧开始之前**（否则该帧已经把 default 画进目标），并设 5 秒硬超时后降级放行。

**验证**：6 个引用不同社区皮肤的 Tee 各自渲染出正确皮肤；日志可见 pose skin pending → ready 的完整等待过程。

### 画质：超采样与锐化（分块渲染未采用）

**超采样已经到位**：poses_render 的 N 倍会创建 N 倍离屏目标，相机世界范围不变，因此世界几何、皮肤与文字都按目标像素**重新光栅化**，输出是真 N 倍而不是放大。默认按 8K（7680x4320）像素预算封顶。

客观判据（可复现）：把 1 倍成片双线性放大到 2 倍，与真实 2 倍成片比较高频能量（相邻像素梯度均值），真实 2 倍是放大版的 **1.46 倍**（0.2991 vs 0.2044），且 1 倍与 2 倍降采样后仅差 0.4% 像素——同构图、更高真实分辨率，不是插值放大。

**分块渲染经评估不采用**，理由（实测 + 读码得出，勿重复踩）：

1. 世界几何是「世界坐标 + 相机视图投影」直接画进目标的，Graphics()->MapScreen() 只作用于屏幕空间（UI／文字）。因此在投影上做块平移**对世界完全无效**：四个块会各画一整幅（实测 78% 像素与单帧基线不同，四个象限内容重复）。
2. 改用相机切块（qm_pose::TileView，缩放除以 N）则世界密度正确，但文字按逻辑屏高度光栅化，与「物理块只有窗口大」互斥：文字会随块缩小 N 倍，比现状更差。
3. 分块的唯一收益是把输出上限从 8K 像素预算往上抬；而单帧路径本来就给出真 N 倍画质，因此**实现分块是退步而非改进**，除非先重构世界／文字的投影换算。

保留的是其中正确且已单测的一层：IGraphics::BeginOffscreenTileFrame()（逻辑尺寸与物理尺寸分家）与 qm_pose::ComputeTile()（按比例取边界，整幅除不尽时不留缝、不越界）。它们目前**没有调用点**，接口注释里写明了世界要按块驱动相机、文字换算尚未解决。

**锐化**（poses_render 第 6 个参数，0-100，缺省 0 ＝ 不处理）：编码前对 CPU 侧像素做 unsharp mask。带**边缘闸门**——拉普拉斯响应低于阈值的像素整片跳过，否则缓变渐变（天空云层）会被放大成一层层等值线（40% 强度下实测可见）。跳过 alpha=0 的像素，避免透明区被邻域染出彩边。

**验证**：40% 强度下 PNG 体积 1.08 MB → 1.10 MB（无门控时为 2.38 MB，即云层噪声曾被放大），1.24% 像素变化集中在边缘，天空无等值线。

### 超采样耗时：先修计时，再看是谁在等

原来的两个分段计时器用 `time_get()`，而该函数在同一帧内返回缓存值（每帧只读一次时钟），所以「建目标」和「读回」永远打印 0.0 ms——看起来像"不耗时"，其实什么都没量到。改用 `CPerfTimer`（steady_clock，纳秒）后各段才有意义。

OpenGL、1280x720 窗口、2 倍（目标 2560x1440）实测：

- `offscreen target 2560x1440 ready in 0.00 ms`：建目标只是提交命令，主线程不等 GPU；
- `offscreen readback finished in 6.79 ms (ok=1)`：阻塞式读回是个位数毫秒；
- `screenshot handoff (texture upload + queue) took 0.09 ms`：贴图上传与排队可忽略；
- 从 `rendering the pose still` 到读回完成约 3 秒，但这 3 秒里日志一直在打皮肤 404：是**皮肤闸门在等 HTTP**，不是渲染或读回。没有皮肤等待时这一段是毫秒级。

结论：「4 倍慢」的耗时不在离屏分配/读回，计时修好之前看到 0.0 ms 只是假象。后续该优化的是皮肤闸门与离屏帧本身的渲染，不是读回路径。

**修完离屏缺陷后的实测（Vulkan 1.4，RTX 4060 Ti，1280x720 窗口）**：

- 2 倍（2560x1440）：读回 6.95 ms，贴图交接 0.09 ms；
- 4 倍（5120x2880）：读回 34.92 ms，贴图交接 0.17 ms（读回随像素线性增长，仍不是瓶颈）；
- OpenGL 同参数（4 倍 / 5120x2880）：读回 25.86 ms、贴图交接 0.10 ms，同样一帧内完成；
- `supersampled frame rendered in 0.46 ms`：主线程录制这一帧只花 0.46 ms；GPU 真正画完是在读回里同步等的，所以 4 倍的总代价看读回（23.44 ms），不是这 0.46 ms；
- 4 倍的完整链路（进会话 → 两帧热身 → 抓帧 → 落盘）在皮肤就绪后约 2 秒；皮肤闸门最多再等 5 秒，只在首次抓帧且皮肤还在下载时发生；成片尺寸实测 5120x2880（两个后端）。

**同轮修掉的两个离屏问题**（都会让超采样看起来"卡死"或"没生效"）：

1. **闸门重新武装导致离屏帧跨帧**：`PoseSkinsReadyForCapture()` 每次放行都把等待起点清零，而渲染前、渲染后各调用一次——渲染后那次于是重新开始等最多 5 秒，离屏目标一直保持活动。Vulkan 的 `Cmd_RenderTarget_Begin` 会结束交换链渲染通道，带着活动目标 `Swap`（`Cmd_Swap` → `NextFrame`）等于在渲染通道中间提交命令，图形线程卡死。现在闸门一次抓帧只判定一次（`m_PoseSkinsGatePassed`），渲染后的提交决策抽成纯函数 `qm_pose::DecideCaptureSubmit`（四种结果都有单元测试：WAIT_FOR_SKINS / SUBMIT_OFFSCREEN / DEFER_TO_NEXT_FRAME / SUBMIT_WINDOW），离屏帧在同一帧内必定读回收口；另有三处兜底（闸门仍未放行、新请求到达时目标还活动、`poses_close` 中途收会话），都会先 `EndOffscreenFrame` 丢弃再继续。
2. **超采样静默降级成 1 倍**：闸门若直到"渲染后"那次检查才首次放行，那一帧没有开过离屏帧，旧代码直接拿窗口帧缓冲截图——4 倍请求悄悄变成 1280x720（实测捕获文件尺寸 1280x720，日志无任何提示）。现在这种情况延到下一帧按超采样重拍，只有后端确实开不了离屏目标时才回退窗口截图。回归测试见 `QmPoseCapture.SupersampledRequestIsDeferredInsteadOfSilentlyDowngraded`、`ActiveOffscreenFrameIsAlwaysSubmittedInTheSameFrame`、`OffscreenFailureFallsBackToTheWindowFramebuffer`。

## 未覆盖与已知限制

- **超采样在 Vulkan 上曾卡死、已修复**：根因与修法见上节第 1、2 条。2 倍／4 倍现在都能在同一帧内读回并落盘，实测成片 2560x1440 / 5120x2880。
- **超采样分段耗时已换成可信计时**：原来两个计时器用 `time_get()`，该函数在同一帧内返回缓存值，段内耗时永远是 0.0 ms。改用 `CPerfTimer`（纳秒时钟）后才有意义，实测数据见上节「超采样耗时」。
- **描述符集号加了静态合同**：`QmNewUiMenuRenderSurfaceContract.ShaderBackendsKeepRoundedSurfaceComposition` 现在断言纹理变体 shader 的采样器在 `set 0 / binding 0`、参数块在 `set 1 / binding 1`，并核对 Vulkan 实现里的 `ParamSet = Textured ? 1u : 0u`——set 号写错只有实机才会暴露，编译期必须靠这条合同拦。
- **抓帧回调早于落盘**：1 倍抓帧的 `ScreenshotDirect` 先回调再排队写盘，所以卡片第一帧拿到的路径可能还不存在（现在只记 info，不再报 error；「查看截图」每帧用 HasPath 重新判定，等文件落盘自动点亮）。
- **保存到不存在的目录会整条失败（已修）**：`screenshot_save::Save` 原来直接 `io_open`，而 `io_open` 不会代建目录——`qm_screenshot_directory` 指到新目录、或第一次保存到新位置时必现，日志为 `png: failed to open file for writing`，成片直接丢。现在先按最终路径 `fs_makedir_rec_for` 补出上级目录（存档相对路径与绝对路径都适用），再由 4 个 `QmPoseCaptureSave.*` 集成测试守住：路径回传、回调晚于落盘、webp 按扩展名选编码器、后处理失败不留残文件。
- **分块渲染未接**：见上节理由，需先重构世界／文字的投影换算；当前输出上限受 8K 像素预算约束。
- **锐化默认关闭**：建议 15-25，属于观感决策，未替用户设定默认值。
- **窗口无焦点时截图被静默丢弃**：CGraphics_Threaded::ScreenshotDirect() 在 !WindowActive() 时直接清回调返回，既不写文件也不打日志（1 倍 poses_render 与普通 screenshot 都受影响）。这是既有缺陷，未在本次修改。
- **自动取景未做**：真实合影坐标跨度大，需要按包围盒自动调整缩放才能一屏放下全部 Tee；当前需用户手动缩放或用紧凑化数据。
- **`poses_video` 未实机验证**：代码路径已实现（复用 `StartVideo` 与主循环的 `AdvancePoseVideo`），但没跑出过成片。
- **UI 入口未做**：目前只有控制台命令。i 图标/wiki 的接线由并行 UI 会话负责。
- **硬件编码的实机导出来自 CLI 实测**，客户端整链路只用 libx264 验证过；NVENC 的真实导出仍需要人工确认。
- **非 ASCII 名字显示为乱码**：`.poses` 的打包格式（每字节 +128）在写入端对 UTF-8 多字节名字就已溢出丢位，客户端按替换字符显示是预期行为，不是解析缺陷。
