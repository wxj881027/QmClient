# 移动端崩溃报告生成与导出

状态：Android 已落地（含数量上限、模块偏移、系统退出记录）；iOS 未接入。

## 问题

手机端闪退后没有任何可供用户取用的现场信息，两条原因叠加：

- `src/base/crashdump.cpp` 的实质实现全部在 `CONF_FAMILY_WINDOWS` 分支内，非 Windows 平台是空桩（`crashdump_init_if_available` 直接丢弃参数）。
- 客户端工作目录由 `InitAndroid()` 改到 `SDL_GetAndroidExternalStoragePath()`，即 `Android/data/<pkg>/files`，Android 11+ 的文件管理器不可见。即使写了报告，用户也拿不到。

## 约束

崩溃瞬间不能直接写公共「下载」目录，三条都不是工程层面能绕开的：

1. `ContentResolver.insert` 走 binder IPC，`JNIEnv->CallVoidMethod` 也不是 async-signal-safe。SIGSEGV 处理中调 Java 层大概率二次崩溃，报告一起丢。
2. Android 10+ 的 W^X / SELinux 禁止从应用数据目录执行二进制，Windows 的 `--qm-crash-reporter` 子进程方案（`crashdump_launch_reporter_if_available`）无法照搬。
3. 分块复制耗时，进程随时被系统回收，只会留下 0 字节的 `IS_PENDING` 残留。

## 实现（两段式）

### 一、崩溃时只写沙盒

`crashdump.cpp` 新增 `CONF_PLATFORM_ANDROID` 分支，安装 `SIGSEGV` / `SIGABRT` / `SIGBUS` / `SIGFPE` / `SIGILL` 处理器（`SA_SIGINFO | SA_ONSTACK`，配 64 KiB 独立信号栈，栈溢出时仍能执行）。

写入顺序刻意分成两步：

1. 先把信号、`si_code`、故障地址、pc/lr/sp/fp 写入报告并 `fsync`；
2. 再沿 frame pointer 链收集返回地址。回溯可能读到坏内存，重入即 `_exit` —— 此时核心现场已经落盘。

报告路径沿用桌面命名 `dumps/QmClient_Crash/..._fatal_report.txt`（不是主日志的 `.RTP`，否则文件管理器按二进制打开），另建同名 `.pending` 空标记。写完恢复默认处理并 `raise`，系统 tombstone 与崩溃统计不受影响。

初始化阶段（进程健康）读 `/proc/self/maps` 缓存可执行模块范围，处理器只做纯内存查表，把裸地址输出成 `libDDNet.so+0x1234`，回报问题时可直接 `addr2line`。

32 位 ARM 不回溯：AAPCS 的 frame pointer 布局随编译选项变化，错栈比没有栈更有害。报告里写一行说明而不是留空。

### 二、下次启动搬到下载目录

`CClient::Run()` 开头依次调用两个函数：

- `ExportPendingQmMobileCrashReports`：只处理带 `.pending` 的报告，因此开关打开后不会把历史报告成批倒出来；经 `ExportAndroidMediaFile` → `ClientActivity.exportToDownloads` → `QmMediaExporter.copyToDownloads`，即 `MediaStore.Downloads` + `RELATIVE_PATH = Download/QmClient` + `IS_PENDING` 两阶段提交，API 29+ 不需要任何存储权限。成功后写 `.exported` 并删除 `.pending`，失败保留标记下次重试；单次启动最多处理 3 份。
- `PruneQmMobileCrashReports`：沙盒内保留最近 10 份报告，超出部分连同标记一起删除。崩溃、系统退出与 hang watchdog 三类报告共用这一份上限——目录里原本就有从 10-31 起累积的 `hang_report`，不纳入清理会无限增长。公共目录则交给用户自行管理。

`copyToDownloads` 的 MIME 改为按扩展名判定：`.txt` 用 `text/plain`，文件管理器可直接预览；其余保持 `application/octet-stream`。

### 三、系统退出记录兜底

自己的信号处理器抓不到 ART OOM、ANR、被系统直接杀死这类退出。`QmCrashExitInfo`（Java，API 30+）在 `ClientActivity.onCreate` 里取最近一条非正常退出，连同系统 trace 写成 `..._exit_report.txt` + `.pending`，由同一套搬运流程导出。

用 `getHistoricalProcessExitReasons(packageName, 0, 5)` 而不是无参的 `getHistoricalProcessExitInfos()`：后者是 API 31 才加的。时间戳写入 `qm_exit_info_seen.txt` 去重，每次启动只导出未见过的一条。

## 配置项

`qm_mobile_crash_report_export`，默认 1。只有 Android 读取；桌面端没有这条路径，判定在 `#if defined(CONF_PLATFORM_ANDROID)` 内，桌面构建不引入任何行为。

与既有的 `qm_crash_report_on_startup` 一致，该开关没有设置界面入口，需要手工编辑配置。

## 构建脚本修复

`qmclient_scripts/android/cmake_android.sh` 原本要求 `$SDL3_JAVA_DIR/../../../proguard-rules.pro` 必须存在，否则 `exit 1`。该路径解析到仓库根，而脚本前面的 `copy_dummy_files` 已经把 Qm 模板复制到那里，等于把文件 cat 到自己；ddnet-libs 的预编译包也没有附带 SDL3 规则，于是打包必然失败。

project 模板里的 `-keepclassmembers class org.libsdl.app.*` 与 `org.ddnet.client.*` 已经覆盖全部 JNI 成员，SDL 官方规则只是更精确的补充。改为「存在则追加，缺失只记一行警告」，打包不再被这个问题阻断。

- Android arm64 native 699/699 编译并链接成功；产物内确认 `AndroidFatalSignalHandler`、`qm_mobile_crash_report_export`、`exported %d mobile crash report(s)`、`pruned %d old mobile crash report`、`_fatal_report.txt`、`_exit_report.txt`。
- aarch64 / armv7a / x86_64 三 ABI 对 `crashdump.cpp` 单独跑 NDK clang `-fsyntax-only -Wall -Wextra`，无告警。
- Release APK 打包成功（111 MB）。`classes.dex` 内含 `ClientActivity`、`exportToDownloads`、`QmMediaExporter`、`QmCrashExitInfo`、`getHistoricalProcessExitReasons`、`text/plain`、`_exit_report.txt`；`libDDNet.so` 内含 `_exit_report.txt` 与 `pruned %d old mobile crash report`。

### 真机（OPPO PKX110 / Android 17 / arm64，非调试版）

端到端链路已实测通过。非调试包无法从外部注入信号（`kill` 被 SELinux 拒绝、`am hang` 与 `cmd activity crash` 均无效果），因此改用同签名的 Debug 包验证，验证后装回 Release 包。

1. 启动 → 进入主菜单，版本号显示正确。
2. `run-as com.qmclient.client kill -11 <pid>` 注入 SIGSEGV。
3. 沙盒 `user/dumps/QmClient_Crash/` 立刻出现 `..._fatal_report.txt`（622 B，权限 600）与同名 `.pending`，进程退出。
4. 重启客户端 → `下载/QmClient/` 出现同名报告（属主 `media_rw`，即 MediaStore 创建），`.pending` 消失并生成 `.exported`。
5. 报告内容完整：平台、图形后端（OpenGL ES）、启动时间、PID、`Signal: SIGSEGV (11)`、fault address、pc/lr/sp/fp、5 帧回溯。
6. 清理逻辑：目录内积压 26 份历史报告（含 10-31 起的 `hang_report`），启动一次后保留最新 10 份。

真机验证暴露并修复了一个真实缺陷：模块表原先按 basename 合并，把 `/system/lib64` 与 APEX 下的同名库混成一个跨 GB 的范围，输出 `liblzma.so+0x1207FC3CC` 这种不可能的偏移。改为按完整路径合并后，越界地址不会再被误算进某个模块（新报告里不匹配的帧只输出裸地址）。

未验证：

- 真实硬件异常（`si_code` 非 0）下的回溯质量。注入的信号 `si_code=0`（`SI_USER`），中断点是线程的随机执行位置，帧链含垃圾值；真实内存访问崩溃会有完好的现场。
- 32 位 ARM 只验证了编译，未在设备上确认寄存器现场。
- 系统退出记录（`ApplicationExitInfo`）未触发到非正常退出场景，只确认了代码路径存在。

## 已知环境限制（本机）

- `cmake-windows.cmd` 的 Rust 段在沙箱/计划任务下会被管道阻塞卡死（`ring` 的 `cl.exe` CPU 恒为 0）。判据是 `Get-Process` 的 CPU 时间不涨，不是 `tasklist` 里有进程。改走计划任务 `.bat` 原生执行。
- 计划任务直接跑 `cmake_android.sh` 会在 native 结束后被中途终止，留下空的 `src/main/java/org/ddnet`，导致 APK 里只有 R 类和 SDL 类。打包应在 shell 里串行执行 native 构建与 `build.sh`。
- `TW_KEY_NAME` 用 `$HOME`（`/c/Users/...`）时 Gradle 会当成相对路径，必须传 Windows 形式 `C:/Users/...`。
- `build.sh` 把 `src/main/java/org/ddnet/client` **mv** 到目标包目录，只能成功一次。重新打包前必须重新复制 Java 源，否则 `rm -rf` 会删掉脚本自己的源、`mv` 又找不到输入，编出的 APK 缺全部业务类（启动即 `ClassNotFoundException`）。
- Debug 包是多 dex（应用类可能在 `classes5.dex`），验证「类是否进包」必须遍历 APK 内全部 `classes*.dex`，只看 `classes.dex` 会误判。

## 遗留

- 沙盒内只按时间保留 10 份，没有按体积约束；单份报告约几 KB 到几十 KB。
- 回溯只覆盖 frame pointer 链，`-fomit-frame-pointer` 编译的第三方库只能看到首帧。
