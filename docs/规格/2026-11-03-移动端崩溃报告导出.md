# 移动端崩溃报告生成与导出

状态：Android MVP 已落地；iOS 未接入。

## 问题

手机端闪退后没有任何可供用户取用的现场信息，两条原因叠加：

- `src/base/crashdump.cpp` 的实质实现全部在 `CONF_FAMILY_WINDOWS` 分支内，非 Windows 平台是空桩（`crashdump_init_if_available` 直接丢弃参数）。
- 客户端工作目录由 `InitAndroid()` 改到 `SDL_GetAndroidExternalStoragePath()`，即 `Android/data/<pkg>/files`，Android 11+ 的文件管理器不可见。即使写了报告，用户也拿不到。

## 约束

崩溃瞬间不能直接写公共「下载」目录，三条都不是工程层面能绕开的：

1. `ContentResolver.insert` 走 binder IPC，`JNIEnv->CallVoidMethod` 也不是 async-signal-safe。SIGSEGV 处理中调 Java 层大概率二次崩溃，报告一起丢。
2. Android 10+ 的 W^X / SELinux 禁止从应用数据目录执行二进制，Windows 的 `--qm-crash-reporter` 子进程方案（`crashdump_launch_reporter_if_available`）无法照搬。
3. 分块复制耗时，进程随时被系统回收，只会留下 0 字节的 `IS_PENDING` 残留。

## 实现（两段式）

### 一、崩溃时只写沙盒

`crashdump.cpp` 新增 `CONF_PLATFORM_ANDROID` 分支，安装 `SIGSEGV` / `SIGABRT` / `SIGBUS` / `SIGFPE` / `SIGILL` 处理器（`SA_SIGINFO | SA_ONSTACK`，配 64 KiB 独立信号栈，栈溢出时仍能执行）。

写入顺序刻意分成两步：

1. 先把信号、`si_code`、故障地址、pc/lr/sp/fp 写入报告并 `fsync`；
2. 再沿 frame pointer 链收集返回地址。回溯可能读到坏内存，重入即 `_exit` —— 此时核心现场已经落盘。

报告路径沿用桌面命名 `dumps/QmClient_Crash/..._fatal_report.txt`，另建同名 `.pending` 空标记。写完恢复默认处理并 `raise`，系统 tombstone 与崩溃统计不受影响。

报告文本与栈回溯是纯函数（`crashdump_format_fatal_report` / `crashdump_walk_frame_chain` / `crashdump_append_frame_lines`），不依赖真实信号，可在任意平台单测。

### 二、下次启动搬到下载目录

`CClient::Run()` 开头调用 `ExportPendingQmMobileCrashReports`：

- 只处理带 `.pending` 的报告，因此开关打开后不会把历史报告成批倒出来；
- 经 `ExportAndroidMediaFile` → `ClientActivity.exportToDownloads` → `QmMediaExporter.copyToDownloads`，即 `MediaStore.Downloads` + `RELATIVE_PATH = Download/QmClient` + `IS_PENDING` 两阶段提交，API 29+ 不需要任何存储权限；
- 成功后写 `.exported` 并删除 `.pending`，失败保留标记下次重试；
- 单次启动最多处理 3 份。

`copyToDownloads` 的 MIME 改为按扩展名判定：`.txt` 用 `text/plain`，文件管理器可直接预览；其余保持 `application/octet-stream`。

## 配置项

`qm_mobile_crash_report_export`，默认 1。只有 Android 读取；桌面端没有这条路径，判定在 `#if defined(CONF_PLATFORM_ANDROID)` 内，桌面构建不引入任何行为。

## iOS

不适用同一方案：沙盒模型没有公共下载目录，也没有 `MediaStore` 的等效物。可行做法是把报告写进 App 的 `Documents/` 并声明 `UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace`，让用户在「文件」App 里自行拷走；真正导出到外部必须走 `UIDocumentPickerViewController`，需要用户交互，崩溃时做不到。iOS 侧当前连崩溃处理都没有（`crashdump.cpp` 走空桩），不在本次范围。

## 遗留

- 未做沙盒内报告的数量上限清理：崩溃循环会持续累积文件，公共目录由用户自行管理。
- 回溯只输出裸地址，需要 unstripped 库配合 `addr2line` 解析。
- 32 位 ARM 只记录 pc/sp/lr，不做 fp 回溯（布局随编译选项变化，误判比缺失更糟）。
- API 30+ 的 `ApplicationExitInfo` 兜底未接，可覆盖自己 handler 抓不到的场景（ART OOM、ANR、被系统杀）。
