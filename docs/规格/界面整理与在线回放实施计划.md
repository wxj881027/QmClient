## 一、目标与范围

在线查看回放时，玩家继续保持服务器连接，看到回放成员和回放画面，保留服务器实时聊天。播放控制采用 Demo 浏览器播放普通 demo 时的进度条 HUD，旁观和视角切换采用正常旁观 HUD；两者的布局和逻辑行为共用生产实现。Rank 1 是回放来源和进入查看的入口，在线回放会话及其 HUD 不由 Rank 1 页面独占。

本轮不增加普通 demo 在线回看的新入口，也不实施后续回看功能。通用职责的整理只服务当前在线查看和现有普通 demo 的共同需求。协议、物理、预测和回放文件格式保持兼容；若接入完整播放行为需要超出已确认范围的核心调整，先说明具体依赖，不能以改成简化 HUD 代替要求。

卡片工作的重点是其他页面内容、布局和组件行为实现不完整。状态保存是配套基础设施，不能用“能记住折叠状态”代表卡片已经完整实现。名牌问题的重点是密度切换时边框粗细不连贯，验收以视觉连续性为准。

## 三、在线回放的玩家行为

### 播放 HUD

以当前普通 demo 的 `CMenus::RenderDemoPlayer` 为行为基准。普通播放与在线回放共用绘制、布局和交互入口，通过播放上下文适配数据和命令，不继续维护外观相似而行为不同的两份代码。

必须逐项接入：播放/暂停、停止并回到开头、进度拖动及原暂停状态恢复、跳转时长下拉、逐 tick、标记跳转和吸附、倍速及档位、快捷键开关与输入条件、时间提示、名称显示、HUD 拖动与边界限制、播放结束处理。原 HUD 的剪辑区间、预览、demo 文件导出及相关入口一并核对后端依赖并接入，不能静默删除或以无效按钮伪装可用。用户于 2026-10-01 明确在线视频导出不需要，该能力不属于本轮实现或验收要求。涉及缺失元数据或控制命令时补齐实际生产接口，再验证该动作。

进度条 HUD 不承担视角切换；当前在线回放控制条中的跟随、自由视角、多人视角按钮移入正常旁观职责。普通 demo HUD 现有的镜头相关动作在共用时归入旁观职责，保证两种播放上下文的职责一致。

关闭播放器在在线上下文中结束回放并恢复服务器画面；普通 demo 上下文沿用关闭普通播放器的返回路径。在线回放的跳转只重置回放自己的瞬时状态，不能调用普通 demo 的全局聊天清理去丢弃服务器消息。

### 旁观 HUD

正常旁观 HUD 共用一套布局、成员展示、命中判断、选中反馈、鼠标/键盘/触摸交互和视角操作。在线回放提供回放成员、成员身份与显示信息、当前选择和镜头控制，普通服务器旁观继续使用服务器成员。

跟随成员、自由视角和多人视角在旁观 HUD 切换。暂停时切换成员应立即刷新画面。成员数量变化、成员失效和选择越界有确定兜底；不能继续硬截成最多 12 名的自定义列表。数据不足时复用正常 HUD 的缺省显示能力，不伪造服务器玩家信息。

在线回放的选择命令只改变本地回放视角，不能发送服务器观战请求。正常在线旁观仍保留现有网络路径。完成接入后删除被替代的自定义成员行、侧面板、视角按钮和仅供旧实现使用的状态。

### Esc、输入与退出

沿普通 demo 的控制 HUD 与正常旁观 HUD 处理输入。打开或关闭游戏菜单保留回放时间、暂停状态、倍速、选中成员及视角；双 Esc 打开游戏菜单时不调用停止回放，菜单关闭后继续观看。

菜单、聊天输入、控制台、旁观选择器和弹窗按现有输入优先级取得活动权，同一次按键不能同时触发两层动作。菜单打开时回放控制层让出输入。外部点击、Esc、拖动中断、焦点丢失及取消重开都要正确释放活动项，避免鼠标拖住进度条后其他控件失效。

显式关闭回放、断线、换图、当前回放被卸载或加载失败时，结束/取消对应会话并恢复可用画面；异步旧请求完成不能重新激活已退出的回放。不得把服务器自身角色的输入误送到回放快捷键之外的路径，或让同一输入被双方重复消费。

### 画面与聊天

查看期间隐藏服务器玩家的角色、钩子、名牌及相关附属表现，显示回放成员。服务器实时数据继续更新，聊天显示服务器消息，不注入 demo 聊天。所有相关渲染模块查询同一在线回放显示策略，退出后恢复正常显示。

现有地图与画面内轨迹播放的实际能力边界在实施时说明。不得把手动影子时间线接上 HUD 就称为完整 demo 播放；逐 tick、标记、剪辑、事件与成员元数据必须逐项确认。

## 四、代码落点与实施步骤

1. 在 `menus_demo.cpp` 和 `spectator.cpp` 梳理原 HUD 的状态、动作及生命周期。以现有生产实现为主，抽出共用的播放 HUD 和旁观上下文接口，避免创建通用插件系统。
2. 在 `src/game/client/components/qmclient/` 整理在线回放会话职责：播放状态、时间线命令、成员、镜头、显示策略、退出与异步取消。保留并复用现有解析/缓存逻辑，Rank 1 页面负责来源与请求。
3. 普通 demo 与在线回放都接入共用播放 HUD；补齐实际使用的后端命令和元数据。会话实例分别持有拖动、暂停恢复、提示与剪辑状态，防止切换来源串状态。
4. 回放成员接入正常旁观 HUD，选择操作按上下文派发到本地镜头或服务器旁观。替换自定义 HUD 后清理旧函数、成员、helper 和构建注册。
5. 接入共享画面显示策略和聊天隔离，修复菜单开关与退出的状态转换。以正常玩家操作路径验证所有消费者。

共享接口尽量保持在 QmClient 目录，共用 HUD 的必要调用点落在现有菜单和旁观模块。引擎核心只为明确缺失的播放能力作必要调整，不顺手重构上游播放、snapshot 或预测。

## 五、图标与 Esc 菜单整理

复用 `CUi::DoButton_QmIcon`、菜单页签入口和 `UiTokens.h`。统一圆角标尺、图标视觉尺寸、点击区域、内边距、对齐、悬浮提示、禁用态和资源缺失兜底。图标绘制区域与命中区域分开计算，窄窗口与缩放时不得靠不断缩小图标解决拥挤。

逐页核对 Esc 的游戏、玩家、服务器信息、浏览、影子、Rank 1、投票，以及顶栏辅助图标。页签和独立容器采用统一圆角规则，容器拼接时明确外沿圆角与内部连接边，避免仅替换 `CORNER_NONE` 而产生缝隙或叠色。

服务器列表左上角按钮保留恢复列宽用途，提示明确为恢复默认列宽，图标不与列表刷新产生混淆。根据目标点击尺寸调整表头/按钮布局，重置不干扰列宽拖动、排序或列表选择。重置前后实际宽度与配置保存均验证。

## 七、名牌描边连续性

验收目标：缩放及密度切换前后，边框视觉粗细连续，不能明显突然变粗/变细。字形清晰度、布局稳定和帧时间同时保留。

先用同一字体、文本、描边设置和相机轨迹复现：记录栅格字号、烘焙密度、绘制密度及描边档位，在 17→18、48→49 栅格像素阈值附近比较切换前后画面，分别关闭/开启可配置边框以区分基础描边与效果层。当前 1/2/4 像素规则是候选原因，不作为已完成根因验证。

确认根因后调整密度变化与屏幕描边厚度的映射或覆盖生成；算法以实际复现选择，不预先指定过渡动画或双容器淡入。修复放在负责该行为的生产层，名牌专项策略不得无意改变菜单及其他文本的描边。姓名、ID、称号和 clan 的相关路径一并检查。

描边生成/厚度选择和缓存逻辑模块化，可直接行为测试与 Google Benchmark 测量；性能用同条件基线比较，记录字形生成、缓存及切换成本。实际 GPU、视觉及多人帧时间另测，CPU benchmark 不能替代。

### 2026-10-01：切换清晰度专项调查与落地安排

状态：生产实现已落地，正在完成行为、性能和实机画面对照。目标是切换时描边自然连续，同时保留清晰度；自动测试不能替代最终视觉验收。

当前存在三条需要分离验证的路径：

- 基础字形描边：text.cpp 的 AdjustOutlineThicknessToFontSize 在整数栅格字号 17→18 时从 1 变 2，48→49 时从 2 变 4。相邻字号的描边半径近乎翻倍，这是确定的算法不连续；是否主导用户看到的跳变仍需固定场景画面对照。原文「48 阈值」指阈值附近，实际分支是 FontSize > 48。
- 名牌密度切换：nameplates.cpp 以 log(1 / 0.866025) 为网格量化密度；缩放动画中保持旧位图，结束后才重建。旧位图放大会发虚；改成每帧栅格化则增加上传、hinting 和布局变化，不能直接放开重建。
- 分批与效果层：预算为每帧 16 个文字部件，CNamePlate::Update 按部件逐个执行，同一玩家的姓名/ID/clan/称号可能跨帧换密度。额外边框与辉光还有按可见人数削减绘制圈数的策略，需与基础描边分开复现，不能把所有粗细变化都归咎于字形半径。

实施顺序：

1. 固定单人和多人文本、字体、字号与镜头轨迹建立旧实现基线。记录实际栅格字号、当前/烘焙像素密度、重建及描边半径；分别关闭可配置特效、开启边框、开启人数自适应。比较 17/18/19 和 47/48/49/50，正常与中途反向缩放、停止在非整数档位、字体/窗口/DPI 变化。截图与短序列放 tmp；正式代码不保留逐帧日志。
2. 优先实现名牌专用的连续描边策略：目标是相对于字形大小的描边比例在密度切换前后稳定，位图生成使用小数半径的覆盖度，不把连续半径再四舍五入成 1/2/4。比例及小字号下限按基线可读性校准，padding 使用覆盖半径的 ceil 并保留透明采样边界。控制输入上限和生成工作量，保留旧通用描边策略作为菜单/聊天默认行为。
3. 接入独立的字形描边策略标识。SGlyph 图集哈希键、近期查找缓存、替代字符、预热/缺失记录及失效路径均必须包含或隔离该标识；当前只按字体面/字符/字号缓存。单改 RenderFlags 或描边生成函数会让名牌和菜单串用缓存，不能验收。称号的专用渲染覆盖路径也使用相同字形来源规则。
4. 将密度切换调度提升到一整个名牌：预算不足时保留旧的一整套，准备完整后统一切换，不按姓名、clan、ID、称号拆散提交。空/隐藏部件不阻塞，文本改变、坐标实时更新、字体失效、玩家退出和连续反向缩放需有取消/重新准备行为；目标过期时不发布旧结果。保持布局锚点，避免更换 hinting 结果后整行中心或基线跳动。
5. 测量过渡清晰度后，再选择有限的高密度预备策略：只准备当前可见名牌所需的邻近较高密度，放大时复用足够清晰的位图；降密度带滞回并延迟回收。不要固定最高字号、全玩家预烘焙所有档位或每帧生成字形。仅当基础描边、布局与密度策略仍留下可见切换时，再评估短时过渡；双容器 alpha 混合不能自动消除轮廓加厚，不先作为默认解法。

验证生产接口：小数半径的覆盖单调性、0 半径/边界/小尺寸缓冲、名牌与通用缓存隔离、阈值往返、替代字符、失效重建、整牌预算不足/取消/重入/空行。测试调用实际描边生成和密度调度实现，不读取源码证明 UI 行为。Google Benchmark 测量生产描边、缓存冷热与切换准备成本，采用同条件旧基线；人数变化、图集/GPU 上传和实际帧时间另测。最终必须有切换序列的实机画面对照，不能以测试或 benchmark 通过称“无缝”。

此阶段不改相机输入或缩放行为，不改变物理/预测，也不扩展到整个文字渲染器的距离场迁移；全局渲染变更只有在上述专项策略无法满足验收且有证据时才另定范围。
