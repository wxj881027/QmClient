# Demo 视频导出现代化实施方案

状态：主体实现已合入主工作树，交互、故障恢复、长任务与平台验收仍未全部完成。下文阶段规划保留设计背景，实际交付与验证范围以补充记录为准。

## 背景与现状

现有实现集中在 `src/engine/client/video.cpp`（约 1179 行）与 `src/engine/client/video.h`，经 2026-10-16 源码核对确认的限制如下：

| 编号 | 现状 | 位置 |
| --- | --- | --- |
| L1 | `avcodec_find_encoder(CodecId)` 按 CodecID 取默认编码器，无法指定 libx264/h264_nvenc/h264_amf/h264_qsv 等具体实现 | video.cpp:939 |
| L2 | 像素格式写死 `AV_PIX_FMT_YUV420P`（8-bit 4:2:0），彩色文字、锐利边缘损失色度 | video.cpp:1025 |
| L3 | `gop_size` 写死 12 帧 | video.cpp:1024 |
| L4 | 工作线程数 = `hardware_concurrency() + 2`（音频线程 = 一半 + 2），每线程独立全尺寸 RGBA 缓冲；4K 下 16 逻辑线程即 18 个视频线程，仅 RGBA 缓冲理论占用约 570 MiB | video.cpp:179-181 |
| L5 | `avcodec_send_frame` 返回值两处丢弃，编码背压与错误不传播 | video.cpp:1071、1123 |
| L6 | PTS 取自编码器内部 `frame_num`，时间戳管理依赖编码器状态 | video.cpp:668-671 |
| L7 | Stop 收尾集中等待线程、flush 编码器、写尾部，异常中断后普通 MP4 缺索引不可播放 | video.cpp:342 起 |

已具备的基础（本 worktree 已超前于公开 master）：容器可选 mp4/mkv（`cl_video_container`，`QmVideoRuntimeContainer()` 带 `av_guess_format` 回退）；已引入 `avcodec_get_supported_config` 条件编译层（video.cpp:972-978）；已有 x264 preset 标签 UI 与单元测试（`qm_video_preset_labels.h`、`qm_video_preset_labels_test.cpp`）。依赖侧：ddnet-libs 本地分支 ffmpeg-matroska 重编了 FFmpeg 7.0.1（libavcodec major 61），lib64 补了 matroska muxer。

玩家反馈的三个核心痛点：默认参数导出画质不理想；数小时 Demo 导出极慢；中途崩溃后数小时计算全部作废。

## 目标与非目标

三目标，按优先级：默认画质足够好；长时间渲染足够快；渲染失败可恢复。

非目标：不改协议、snapshot、物理与 demo 格式；不追求 FFmpeg 版本号本身；不把 FFmpeg 全部参数搬进 UI（只做预设 + 高级自定义）；不在本方案内做真正的 10-bit HDR 渲染管线（仅留路径）。

## 阶段规划

对应外部评估的 P0-P3 四阶段，按本仓库现状细化为八个里程碑。M1/M2 为 P0 级（稳定与资源），M3/M4/M5 为 P1 级（可恢复、硬件编码、依赖升级），M6/M7 为 P2 级（剪辑工作流、画质进阶），M8 为 P3 级（架构进阶）。同里程碑内任务串行，里程碑之间除 M5 外不互相阻塞。

### M1 编码错误处理修复

- `avcodec_send_frame` 两处调用检查返回值；`EAGAIN` 表示编码器需要先收包，需按 FFmpeg 文档处理背压，其余负值记录 `av_strerror` 并置错误标志。
- `WriteFrame`/`FinishFrames`/`CloseStream` 建立可传播的错误状态，Stop 后 UI 能显示导出失败原因而非静默产出坏文件。
- 显式管理帧序号与 PTS：在 `CVideo` 维护独立的帧计数器生成 PTS，替代读取编码器 `frame_num`（L6），保证 flush 阶段与取消路径时间戳一致。
- 涉及文件：video.cpp、video.h。验收：编码器故意注入错误（无效参数）时导出失败且日志可见，正常导出音画同步不变。

### M2 资源与吞吐重构

- 以固定上限的有界帧队列 + 少量转换工作线程替换按核数分配的线程与缓冲（L4）。初始值建议：转换线程 2-4 个，队列深度 8-16 帧，均可配置并 clamp 上限；实际数值以 4K/1080p 实测调优。
- 离线 Demo 渲染允许生产端在队列满时等待（反压），不丢帧、不无界缓冲。
- 编码提交仍经 `m_WriteLock` 串行，但转换与编码解耦；CPU 编码并行性交给编码器自身 `thread_count` 与帧级并行（x264 frame-threads）。
- 涉及文件：video.cpp、video.h。验收：4K 导出常驻内存相对现状下降且不随 CPU 核数线性增长；1080p60 与 4K60 导出耗时不变差。

### M3 分段渲染与断点续渲

- 支持把一次导出拆成固定时长片段（默认建议 5 分钟，可配），每段独立封装、验证（读尾部成功）并记录进度。
- 进度持久化：任务清单（源 demo、起止 tick、片段大小、编码参数指纹、已完成片段）写入 videos 目录旁的进度文件；导出重启时跳过已完成片段。
- 片段边界要求：起止对齐编码关键帧（片段首帧强制 IDR）；音频时间戳连续；Demo 侧按 tick 定位还原状态，必要时预热若干 tick 使特效、聊天等状态与整段导出一致。
- 拼接策略：片段编码参数一致时用 FFmpeg 流复制 concat 拼接；参数不一致或用户要求时保留独立片段。拼接前校验各片段流参数一致。
- 崩溃可恢复的容器侧：7.0.1 下 mkv 天然比 mp4 抗中断；FFmpeg 9 的 hybrid_fragmented MP4 列为 M5 后的可选增强。
- 提供 Demo 时间范围选择（复用上游 `demo_slice_start`/`demo_slice_end` 定位逻辑，UI 上在渲染确认弹窗加起止点），支持只渲染选区或多片段批量任务。
- 涉及文件：video.cpp/h、client.cpp（渲染状态机）、menus_demo.cpp（UI）、新增分段任务管理模块（建议 `qmclient/video_export/` 下）。验收：3 小时长 Demo 中途 kill 进程后重启能跳过已完成片段继续；整段与分段+拼接产物时长、帧数、音画同步一致。

### M4 编码器抽象与硬件编码

- 编码器按名称选择：新增字符串配置（如 `qm_video_encoder`，空值 = 现行为），`avcodec_find_encoder_by_name` 解析；为空时维持 `avcodec_find_encoder(CodecId)` 兼容。
- 像素格式协商：用已接入的 `avcodec_get_supported_config`（AV_CODEC_CONFIG_PIX_FORMAT）取编码器支持列表，从用户期望格式（420/422/444/rgb0 等）按优先级协商，替代写死 YUV420P（L2）。
- 硬件路径：NVENC（h264_nvenc）、AMF（h264_amf/hevc_amf/av1_amf）、QSV（h264/hevc/av1_qsv）、VideoToolbox（h264/hevc/prores_videotoolbox）。三层检测分离：FFmpeg 构建是否含该编码器（编译产物枚举）→ `avcodec_alloc_context3` + `avcodec_open2` 实际初始化探测 → 指定像素格式/参数能否打开。探测结果缓存，UI 只展示当前环境可用的选项。
- 各编码器独立质量控制：x264 用 CRF/preset；NVENC 用 CQ/preset；AMF/QSV/VideoToolbox 各自的质量参数映射。禁止一个 CRF 值跨编码器套用；高级参数按编码器动态显示。
- GOP 可配置（L3），默认值改为按用途评估（当前 12 偏小，评估 60-120 帧区间），分段渲染的片段首帧强制 IDR 不受此影响。
- 硬件失败回退：探测或运行失败时明确报错并可回退软件编码器，不静默换编码器。
- 涉及文件：video.cpp/h、config_variables.h、menus.cpp/menus_demo.cpp（编码器选择 UI）、新增编码器能力探测模块。验收：RTX 4060 Ti 上 h264/hevc/av1_nvenc 可选且导出成功；无独显环境 UI 不出现不可用项；x264 路径行为不变。

### M5 FFmpeg 升级（与 M4 可换序）

- 目标版本评估顺序：9.0.x（libavcodec ABI 63）> 8.1.x > 7.1.5（与 7.0.1 同 soname，drop-in，但 7.0 分支已停更）。升级必须连带重放 ddnet-libs ffmpeg-matroska 分支的 matroska muxer 定制（该定制存在于本地分支，origin 上游无此重编）。
- 兼容层已备：`avcodec_get_supported_config` 条件编译已就位；升级时核查 `avcodec_send_frame` 语义、声道布局 API、被移除的旧选项（如 NVENC 旧参数）。
- 升级后回归：全部既有导出预设音画同步、mkv/mp4 容器均正常；DLL 体积与安装包增量记录。
- 涉及文件：ddnet-libs 子模块（新分支）、qmclient_scripts 构建脚本如涉及。验收：C++ 测试套件通过 + 短 Demo/长 Demo 导出对比无回归；子模块提交与 VERSION 记录一致。

### M6 剪辑工作流与预设

- 新增编码格式：ProRes（prores_ks， MOV；macOS 可选 prores_videotoolbox）、DNxHR（dnxhd，MOV）、FFV1（MKV 无损归档）、HEVC Main10（可选 AV1）。每格式绑定推荐容器（MP4/MOV/MKV）与音频编码器（AAC/PCM/FLAC 按容器与用途）。
- 导出预设体系：「日常分享」（H.264/AAC/MP4）、「高效高画质」（HEVC Main10/MP4）、「专业剪辑」（ProRes 422 HQ/MOV）、「无损归档」（FFV1/MKV）、「自定义」。预设展开为编码器 + 容器 + 像素格式 + 质量参数组合，UI 按编码器动态过滤可选项。
- 色彩元数据：为输出流写入完整的颜色原色/传输特性/矩阵/range 标记（当前仅 `colorspace = BT709`，video.cpp:1026），保证 Premiere/Resolve 导入颜色一致。
- 涉及文件：video.cpp/h、`src/engine/shared/video.h`（格式名/后缀工具）、menus.cpp、config_variables.h。验收：ProRes 422 HQ 与 DNxHR HQX 产物在 Premiere 与 Resolve 中正确导入、颜色与帧率一致；FFV1/MKV 无损可逆。

### M7 画质进阶

- 独立渲染分辨率与超采样：导出时允许以高于输出的分辨率离屏渲染再缩小（如 2x 渲染 → 1080p 输出），改善 2D 图形边缘锯齿；需要独立离屏渲染目标，而非只改 FFmpeg 输出宽高。
- sRGB → Rec.709 SDR 转换路径固化并实测（截图、彩色文字、激光线、快速移动场景对比）；10-bit 输出路径仅在捕获链路升级到 10-bit 后有意义，本阶段仅确认协商机制可承载。
- 默认预设调优：以 DDNet 实际画面（彩色文字、Tee 轮廓、快速移动）对比 CRF/preset 组合，必要时调整 `cl_video_crf`/`cl_video_preset` 默认值并更新推荐文案。
- 涉及文件：video.cpp/h、图形后端 readback 相关（`GetReadPresentedImageDataFuncUnsafe` 调用路径）、menus.cpp。验收：超采样开启时文字与边缘主观明显改善；色彩元数据经 ffprobe 验证正确。

### M8 渲染架构进阶（远期）

- 异步 GPU readback（PBO/ staging 纹理）与 GPU 色彩转换，减少 GPU→CPU 拷贝与 CPU swscale 开销。
- 渲染子进程：导出任务放独立客户端子进程执行，主客户端可正常游玩；任务管理器展示进度、速度、内存与错误日志。
- 立项时机：M1-M6 交付并实测瓶颈分布后再决定是否启动。

## 关键设计决策

- 反压优先于丢弃：离线渲染场景帧都是必须的，队列满时生产端等待，绝不丢帧。
- 编码器选择以「名称字符串 + 能力探测」为准，CodecID 仅作回退；所有 UI 可选项必须来自运行时探测，不做硬编码设备表。
- 分段渲染的任务状态是纯数据文件（JSON 或键值对），不引入数据库；文件损坏时按「从头渲染该片段」处理。
- 时间戳唯一权威在导出任务层（帧计数器 × 1/FPS），编码器与容器只做转换。
- 配置前缀沿用 `qm_`/`Cl` 现行规则，新配置进 config_variables.h 相邻区域并附中文注释按现有文件惯例。

## 依赖与风险

- ddnet-libs 子模块是唯一 FFmpeg 供给方，matroska muxer 定制只在本地分支（ffmpeg-matroska，当前未推送）；M5 升级须在新分支重放该定制并保留分支说明。子模块对照仅走 GitHub API 只读（沙箱内 git fetch 会被终止）。
- 4:2:2/4:4:4 与多数硬件编码器不兼容（NVENC 10-bit H.264 需 Blackwell+），协商失败必须回退 420 并提示，不能让用户选了不支持的组合后导出坏文件。
- QSV 在 Windows 依赖驱动实现，AMF 版本差异大；探测必须真实 `avcodec_open2`，不能只看编码器注册存在。
- 长任务与并行会话：构建与测试遵循固定槽位规则，同 build 目录串行；方案实施周期长，各里程碑在本文档更新验证记录后交接。

## 测试与验收策略

分层（按 src/test/AGENTS.md）：单元测试覆盖像素格式协商、PTS 生成、分段任务状态机、编码器参数映射；集成测试覆盖分段任务管理（进度文件读写、断点跳过、拼接参数校验，用内存/临时目录 fake）；端到端冒烟与关键路径放 `qmclient_scripts/integration/`（短 Demo 导出、中断续渲、异常注入：磁盘不足、编码器初始化失败、强制终止）。

性能验收基线：1080p60 与 4K60 短 Demo（约 1-3 分钟）各测 x264 与 NVENC 导出耗时与常驻内存；3 小时长 Demo 验证内存不持续增长、断点续渲正确性。微基准不能替代导出实测。

每里程碑交付时：过滤相关单元/集成测试 + 构建受影响目标；跨容器、编码器选择等影响启动或导出全路径的改动补端到端场景；本文档「验证记录」一节登记实际运行的层级与过滤范围。

## 补充 21：按风险补验证（2026-10-21）

按补充 20 的 gap 清单从高到低补，过程中发现两个新的确定缺陷，均已修复：

1. **P1：分段 + 有声音导出，第二次拼接必然失败。** 新增 `video_export_segmented_audio_sync`（4 段 × 2 s、`snd_enable 1`）首次运行即失败：`Application provided invalid, non monotonically increasing dts to muxer in stream 1: 1984 >= 1983`，随后 `Could not write concat packet ... Invalid argument`。两个独立原因：
   - **音频没有按包序落到网格。** 视频走「包序 × 帧步长」重建时间轴，音频仍沿用输入 pts 平移；AAC priming 让段首 pts 为 0.021 s、末包可能越过段尾，按视频基准推进段间偏移后第二段音频 dts 回退。修复：`ConcatVideoFiles` 的 Grid 分支对音频按 `段起点 + 包序 × frame_size` 放置 pts/dts，与偏移推进使用同一基准，天然单调。
   - **matroska 段没有流时长，音频预算从未生效。** `AudioPacketBudget` 只在 `pInVideo->duration > 0` 时计算，而 matroska 不写流时长（`ffprobe` 的 `stream=duration` 为空），预算恒为 -1，等于完全没有裁剪。修复：时长不可知时单开一个输入上下文只数视频包，用 `包数 × 帧步长` 换算段时长再算预算；数不到时保持 -1 退回原行为，不猜会截掉真实内容的预算。
   - 证据：修复前 E2E 失败（`tmp/gap-seg-audio.log`、`tmp/gap-seg-audio2.log`），修复后 4 段拼接成功，每段 `audio=94 pkts`，最终产物音频包终点 7.984+0.021 s、视频 7.983+0.016 s，偏差 0.006 s（`tmp/gap-seg-audio3.log`）。
2. **P2：发布归档会带上旧版 FFmpeg DLL。** 实测已打出的 `QmClient-3.3-win64.7z` 里是 `avcodec-61/avformat-61/avutil-59/swresample-5/swscale-8`（FFmpeg 7），而仓库捆绑的是 `avcodec-63/avformat-63/avutil-61/swresample-7/swscale-10`（FFmpeg 9）。`verify_windows_package.py` 只核对 exe 清单与废弃资源，完全不看 FFmpeg 运行时，所以这个错配能一路通过打包校验。修复：校验器新增 FFmpeg 运行时检查——五个族各恰好一份，且与 `ddnet-libs/ffmpeg/windows/lib64` 的版本一致；`package_windows_release.py` 传入该目录。新增 3 项单测（同族重复、缺族、与捆绑版本不一致）。

3. **P1：分段导出停录时音频线程可能死锁（间歇）。** 分段带声音场景在单独连跑 5 次全部通过，但在完整 9 条 E2E 连跑时失败一次：日志停在 `Segment 1 done; resuming at segment 2/4` 之后完全静默，无崩溃、无 dump、无后续任何输出，进程被测试超时终止。两个独立成因：
   - **停止标志逐个置位。** `CVideo::Stop` 原实现「置位一个线程 → join 它 → 再置位下一个」。音频线程之间存在依赖：子线程在 `RunAudioThread` 里等待父线程清空 `m_AudioFrameToFill`。若先 join 的线程正好在等一个尚未收到停止信号的父线程，就会永久阻塞。修复：先把所有音频线程的 `m_Finished` 置位并通知，再逐个 join。
   - **等待条件无法被停止打断。** 该等待的谓词只有 `m_AudioFrameToFill == 0`，父线程若已退出循环就再也不会清空它。修复：谓词加上 `pParentThreadData->m_Finished || pThreadData->m_Finished`，并在 join 前对 `m_AudioFillCond` 补一次通知（等待方持有的是 `m_AudioFillMutex`，只通知 `m_Cond` 唤不醒它）。
   - 证据：修复前完整套件 1 次失败（`tmp/gap-e2e-final.log` 第 303 行）；修复后同一场景连跑 4 次全通过（`tmp/gap-dl-fix1..4.log`），完整 9 条 E2E 再次全通过（`tmp/gap-e2e-final2.log`）。这是间歇故障，上述次数不能证明根除，但两条阻塞路径都已按可打断的方式改写。

## 补充 22：剪辑格式重构与色彩采样（2026-10-21）

### PBO 异步读回（2026-10-24 同日补齐）

离屏视频路径的读回改为 PBO 双缓冲异步：GL 后端的 `SCommand_RenderTarget_Readback` 只把 `glReadPixels` 排进 PBO（DMA 立即返回），像素在下一次读回或新的 `CMD_RENDER_TARGET_READBACK_FLUSH` 命令里才 map 拷出并点亮完成信号——传输与下一帧渲染重叠，消除每帧的同步读回点。完成信号量从"同捆 Signal 命令"移入读回命令本身（结算时才点亮，不能提前）。Vulkan/Metal 的读回在命令内同步完成，Flush 命令注册为 no-op；老 GL 无缓冲对象时退回同步路径（行为与旧版一致）。

生命周期按「一帧延迟」推进：`EndVideoFrame` 排队本帧 DMA 并结算返回**上一帧**的像素（首帧为空不提交，客户端跳过空帧）；最后一帧由 `CVideo::Stop` 经 `FlushVideoFrameReadback` 结算并补交后再排空编码线程——帧数与窗口路径同刻度。`StopVideoFrame` 对异常序列做防御性结算；设备重建路径同步复位在途句柄。`ReadRenderTarget` 与静帧离屏（poses 超采样）改为「kick → 等空闲 → Flush → 等空闲 → 结算」的同步节奏，兼容 PBO 与无信号后端（Vulkan 仍按空闲后像素归属判定）。

验证（PBO 部分）：单测 103/103（含命令批/渲染目标策略）；E2E 预写 settings.cfg 强制 OpenGL 后端（命令行参数在图形初始化后才执行，换不了后端）跑通离屏 FSAA 场景：GL 4.6 + 窗口 FSAA=0 下按 **4x 多采样**离屏启动、全程无回退、成片 **120 帧整**（2s@60fps，一帧延迟生命周期无缺帧）；Vulkan 路径复跑离屏/超采样/分段带声音/窗口四个场景全部通过。窗口路径（默认配置读 GL_FRONT）仍为同步读回，其 PBO 化涉及捕获时序语义（defer 一帧 = 内容整体后移一帧），留作后续。

360p 下所有档位挤在 31-36 fps（编码器换 NVENC 也不变快）——瓶颈在管线固定开销（每帧渲染/读回/转换的同步点），不在编码；1080p 起编码器差异才显现；4K 最高画质 15.8 fps（0.26x 实时）。提速优先级因此是管线开销 > 转换线程 > 编码器本身。矩阵内 ffmpeg 直连编码 360p 可达 600-780 fps，编码器远非瓶颈。

### ProRes 4444 档位标签修复

现象：444 偏好 + ProRes 导出成片被 ffprobe 识别为 `HQ + apch + yuv444p10le`。定位：段文件（编码器直出）一直是正确的 `4444/ap4h/yuv444p12le`；**拼接 remux 时 `codec_tag` 被清零**（video_export.cpp），MOV muxer 按族默认重选 `apch`，剪辑软件按标签识别档位会认错。修复：拼接时视频/音频流继承源 `codec_tag`（段与成片同 muxer，标签必然有效；mov 族自带 tag↔codec_id 校验，matroska 忽略 tag）。验证：修复后成片 `4444 / ap4h / yuv444p12le`，120 帧整；video 域单测与 e2e（range/分段/离屏/超采样）通过。

### 其他观察

- 段起始静默截头已修复：主循环卡顿（如后端首帧编译）会让一次 Update 越过段起始 tick，高 demo_speed 下一次可跳几十 tick，从越过后的位置开录会把成片头部截短（帧网格仍均匀 1/60，非丢帧；批量采样 2/17 次命中，GL 后端 e2e 亦复现）。修复：预热态检测到越过段起始 tick 时先 `SetPos` 回起始 tick 再开录（client.cpp `DriveSegmentedExport` 的 ACT_START_RECORD 分支），每段起点同样受保护。确定性的卡顿注入回归钩子留作后续。
- 分辨率不设上限的实现细节确认：输出 2560x1440/3840x2160 均按输出尺寸离屏重栅格化（非拉伸），与显示器分辨率无关。

## 补充 27：真实分辨率基线、锐化/超分结论、2 深异步结算与质量基准（2026-10-24）

按「360p 无意义，以 1080p/2K/4K 为准」的口径重做基线并落地提速改动。

### 真实分辨率基线与瓶颈定位（改动前，GL，120 帧）

| 档位 | 1080p | 1440p | 4K |
| --- | --- | --- | --- |
| 最高画质（444/全帧内/CRF14/4xMSAA） | 19.8 fps | 18.8 fps | 15.8 fps |
| 最快（NVENC CQ18/420/GOP60） | 30.5 fps | 30.1 fps | 26.8 fps |

变体实验：4K 下转换线程 3→8、队列 8→32（单独或叠加）**全部更慢**（15.8→13.9~14.4、26.8→21.7）——像素格式转换级不是瓶颈，加线程只与 x264 的 11 线程争核；剩余杠杆指向每帧同步点。

### 2 深异步读回结算（提速落地）

原节奏：`EndVideoFrame` 排队本帧读回后 `WaitForIdle` 等渲染线程整体执行完，再结算上一帧——主线程与渲染线程逐帧串行。现改为：**有完成信号的后端（GL，PBO 与同步回退都点亮信号量）维持两笔在途，`ResolveBlocking` 阻塞结算「上上帧」**，主线程领先渲染线程一帧，本帧的命令录制与渲染执行重叠；无信号后端（Vulkan/Metal）保持逐帧整体等待的一深节奏（行为不变）。收尾改为 `FlushVideoFrameReadbacks` 批量结算（GL 补交两帧，帧数刻度不变）。GL 双 PBO 与两笔在途天然对齐（第 N 笔读回命令结算第 N-1 笔 DMA）。

实测（同配置 A/B，RTX 4060 Ti）：**最高画质 1080p 6.05s→3.65s（+60%）**；NVENC 两档与 4K 持平（重复采样确认无回退，4K 瓶颈在渲染与 33MB/帧读回拷贝本身，同步等待不占主导）。单测：读回队列 10/10（新增阻塞结算 3 项：迟到信号、已亮信号、失败保槽）；e2e：离屏 FSAA/超采样/range 全过。

### 锐化与超分（用户问询的量化结论）

- **锐化**：轻度 unsharp(0.5) PSNR-Y 50.4→42.2 dB、体积 +12%；强度 1.5 → 34.2 dB、+33%。VMAF 反给 100 是该指标偏爱锐化的已知度量伪象，非真实提升；视觉确认三明治光环（双轮廓）、地形边过冲白边、平坦区颗粒噪点（`tmp/quality/out/crops/sharp1080.png`）。原生分辨率渲染本身无模糊可恢复——**不做锐化**。
- **超分**：360p lanczos 上采样到 1080p 对照原生渲染 PSNR-Y 仅 31.0 dB / VMAF 38.4——原生重栅格化完胜任何上采样；管线支持任意输出分辨率原生渲染，AI 超分仅在源分辨率固定且低于目标时有意义，不适用。

### 质量量化基准接入

新增 `qmclient_scripts/integration/perf_video_export.py`（手动入口，非 gate，`scripts_overview.md` 已登记）：

- `speed_hd`：1080p/4K 两档预设真实导出吞吐，校验成片帧数不断言机器相关的速度。
- `quality_codec`：无损帧重编码的确定性画质门（daily/official ≥ PSNR-Y 45 + VMAF 90，best ≥ 46 + 90；阈值自 2026-10-24 基线留余量，同版本编码器下跨机器稳定）。
- `quality_aa`：导出 FSAA 生效性门（机制断言：日志采样数声明 + 无窗口路径回退；像素 Δ 因跨运行特效随机地板 ±1.5dB 大于 AA 信号本身，仅作参考输出——首跑实测 Δ 在 +1.6 与 -1.3 间波动，证明了该地板）。

客户端捆绑的 avcodec-61/63.dll **均未编入 libsvtav1**（`svt` 字符串零命中，方法经 libx264 五处命中阳性对照；此前矩阵中 SVT-AV1 数据来自 CLI ffmpeg 9.0.2）。接入前置条件是重建 ddnet-libs 的 FFmpeg（子模块级依赖变更，影响全平台），随后客户端侧仅为编码器注册表 + 质量映射（CRF 0-51 → SVT 0-63，preset 10 档 → SVT 0-13 反向）+ av1 家族别名的软件回退位。等 VMAF 体积 -39% 的业务依据见补充 26。

## 补充 28：SVT-AV1 接入与 FFmpeg 运行时收敛（2026-10-24 晚）

### FFmpeg 7 遗留清理

61 家族（avcodec-61/avformat-61/avutil-59/swresample-5/swscale-8）是 7.0.1 时代的构建目录遗留：DDNet.exe 只导入 63 家族（注意 **avutil-61 属于 FFmpeg 9**，其 59 才是 FFmpeg 7 的 avutil），ddnet-libs 中也无此家族。已从两个构建目录删除；历史打包产物与并行会话临时目录里的副本按「非必要不删」保留，下次打包从 ddnet-libs 重新生成，包验证器本就把同族两份判为错误。

### 运行时替换为 gyan 9.0.2 shared（含 libsvtav1）

- 背景：项目自建的 9.0.2 DLL 未编 SVT-AV1（字符串零命中，方法经 libx264 阳性对照），接入前置是换带 SVT 的同版本运行时。gyan full shared 与原 DLL **版本号逐一相同**（avcodec 63.1.102 等，ABI 一致），且全功能（libsvtav1/libx264/matroska 齐备）；MSVC .lib 导入库按符号名绑定 cdecl 导出，MinGW 构建的 DLL 兼容，无需额外运行时 DLL。
- 动作：`cmake-build-release`、`cmake-build-release-process-tests` 与 `ddnet-libs/ffmpeg/windows/lib64` 三处同步替换 5 个 DLL（备份在 `tmp/quality/dll_backup`）。
- **仓库侧待办**：ddnet-libs 是独立 git 仓库，其工作区现有 5 个 DLL 的未提交修改（自建 → gyan shared），需要维护者提交并 bump 子模块指针；avcodec 从 10.7MB 涨到 98MB（full 构建编入全部外部库）。其余平台（lib32/libarm64/linux/android）仍是自建 9.0.2（无 SVT）——SVT 导出当前仅 Windows x64 可用，探测门控会在未编入的运行时上自动隐藏该编码器。
- 许可：gyan full 为 GPL 组合；原构建因 libx264 已是 GPL 姿态，分发许可无变化。
- 实测副作用：SVT 探测/编码引入后，机器高负载时客户端启动可超过 harness 默认 15s 等待（GL 建上下文 4s），脚本侧已放宽启动等待；属环境噪声而非回归。

### 客户端接入

- 编码器注册表新增 `libsvtav1`（"AV1 / SVT (software)"），三层探测通过；`av1` 家族别名补上软件回退位——无 NVENC/QSV/AMF 的机器上 `qm_video_encoder av1` 也可用。
- 质量映射：统一质量值 0-51 直传 SVT CRF（0-63 的子集）；`cl_video_preset` 10 档映射 SVT preset 12..2（SVT 数值越大越快，medium(5) → 6）。

### 修复：legacy bit_rate 与 SVT 冲突

`video.cpp` 遗留的 `bit_rate = 400000`（x264/NVENC 忽略）与 libsvtav1 的 CRF 互斥：编码器打开直接报 `bad parameter (0x80001005)`，CLI 同版本 `-crf 35 -b:v 400k` 可稳定复现。已移除该赋值——当前全部编码器家族均为质量值模式（CRF/CQ/CQP/ICQ 或 profile 固定），未来接码率驱动编码器必须显式配置。

### 验证

- 单测 `VideoEncoder.*` 19/19（含 SVT CRF/preset 映射与三层探测；未编入的运行时上自动跳过）。
- 真实导出（1080p，GL 离屏，120 帧整）：SVT CRF35 **342KB**、CRF30 **464KB**，对照 libx264 CRF18 656KB——**等档位体积省 48%/29%**，导出吞吐 28.7fps（x264 33fps，preset 6 下慢约 15%）。
- e2e 回归（DLL 替换后）：range / offscreen_fsaa / segmented_audio_sync（mkv+AAC）全部通过。
- 人工实机确认：客户端启动、主菜单渲染正常（用户截图证据）。

### Vulkan 离屏 MSAA 解耦（评估结论，未实施）

硬阻塞在于 Vulkan pipeline 的 rasterizationSamples 必须匹配渲染附件采样数：离屏 4x 需要整套 4x 采样数的世界渲染管线变体（tile 层、quad、文字、QM 管线全部），属大重构，列为独立专项。当前默认 Vulkan 后端下离屏多采样仍按窗口 FSAA 钳制（日志明示 using 1x），导出 AA 的完整体验仍在 OpenGL 后端。
