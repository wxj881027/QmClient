# Demo 视频导出：画质根源与剪辑格式重构（第一期）

状态：第一期已落地，构建与测试通过；**剪辑软件实机导入（Premiere / Resolve）仍未做**，需要人工验收。
本文件是第一期交付与验收清单；后续期（硬件编码补齐、`.poses` 合影渲染）另立文档。

## 一、要解决的问题

上一轮调研（本会话）实测确认三件事，构成了本次改动的依据：

1. **ProRes 对本项目的源没有画质收益。** 渲染读回是 `GL_RGBA8`（`backend_opengl.cpp:337`），源头只有 8bit。同一测试画面下 4:2:0 的色度 PSNR 是 25.1/19.0 dB，4:4:4 是 42.9/42.1 dB，而 ProRes 422 HQ 只有 29.8/24.1 dB 却要 279MB（同画面 x264 CRF18 是 1.78MB）。ProRes 的体积大、画质并不更好。
2. **真正的剪辑收益来自全帧内，而不是容器或位深。** `x264 -g 1` 实测 299/300 帧是关键帧，随机定位与 ProRes 等价（两者都是全内帧），但体积 16.3MB 对 279MB（约 1/17），色度还更好，且任何播放器与 NLE 都能直接打开。
3. **NVENC 的 CQ 与 x264 的 CRF 同刻度但不等价。** 实测同素材 CQ23 ≈ CRF18（体积与 VMAF 均差 <1%），旧实现直接沿用 CRF 值会得到小一档画质。

## 二、改了什么

### 预设重构

| 索引 | 旧 | 新 |
| --- | --- | --- |
| 1 | 日常分享 (libx264/mp4) | 不变 |
| 2 | 高效高画质 (hevc_nvenc/mp4) | 表述改为 hevc/mp4（硬件可选，见后续期） |
| 3 | 专业剪辑 (ProRes 422 HQ / MOV) | **剪辑 (全帧内 H.264 / MP4)**，同时把 GOP 置 1 |
| 4 | 无损归档 (FFV1 / MKV) | **交换格式 (ProRes 422 HQ / MOV)** |
| — | （原 DNxHR 已在上一轮移除） | — |

FFV1 与 DNxHR 从候选表整体移除（用户明确不需要归档格式）。项目尚未发布，不做旧索引迁移。

### 新增配置

- `qm_video_pixfmt`（0=自动 1=4:2:0 2=4:2:2 3=4:4:4）：按 `WantedPixelFormatsForPreference` 展开成期望格式列表，交给已有的 `NegotiatePixelFormat` 按编码器真实支持能力协商。4:4:4 档不保留 4:2:2/4:2:0 退路——不支持就报错，不静默给更差的格式。
- `qm_video_prores_profile`（-1=自动，0..5）：ProRes profile 不再由质量值隐式切换。旧实现 `quality <= 15` 就选 4444，但输入仍是 422，实测会被编码器补成 12bit 422（体积 +48%、画质零收益）。现在由实际协商出的像素格式推导：4:4:4 → 4444，其余 → HQ。

### 行为修正

- **全帧内 GOP**：`qm_video_gop = 1` 表示全帧内，同时禁用 B 帧（I 帧之间没有参考帧，B 帧无收益）。
- **NVENC 最小 GOP**：NVENC 拒绝 `gop_size = 1`（`InitializeEncoder: "Gop Length should be greater than number of B frames + 1"`），请求全帧内时降级到 2（隔帧关键帧）并记一条 warn，而不是直接打不开编码器。
- **NVENC 质量偏移**：`cq = clamp(crf + 5, 0, 51)`。
- **续渲指纹**：`VideoExportConfigParams` 增加 `pixfmt` 与 `prores` 两段。否则换采样格式续渲会跳过已完成段，把两种色度采样的段拼进同一成片。
- `bit_rate = 400000` 加注释说明它对 CRF/CQ 模式无效（实测输出与 `bit_rate=0` 完全一致），保留是为了不改未测编码器的既有行为。

### UI

渲染回放弹窗「视频导出」分组新增「色彩采样」下拉行（自动 / 4:2:0 / 4:2:2 / 4:4:4），带 tooltip 说明「渲染是 8 位，10 位格式本身不增加细节」。分组高度从 8 行变成 9 行（230 → 254），`RenderContentHeight` 从 594 变成 618（在线 648），布局测试同步。

新增行为测试（`src/test/unit/engine/video_encoder_test.cpp`）：

- `NvencCqOffsetClampsAtBothEnds`：CQ 偏移在 0 与 51 两端钳制。
- `ProresProfileFollowsExplicitArgument`：profile 由显式参数决定，-1 回落 HQ。
- `PixelPreferenceAutoKeepsFamilyDefaults`：自动档不改家族列表；未知编码器名回退。
- `PixelPreferenceListsRequestedChromaFirst`：4:4:4/4:2:2 首选位深更高的格式；ProRes 请求 4:2:0 时降级 4:2:2。
- `PixelPreferenceNegotiatesRealEncoderSupport`：libx264 实际协商出 `yuv444p10le`。

集成测试 `CVideoExportStorage.DemoDisplayChangesInvalidateCompletedSegments` 扩展了两条：改 `qm_video_pixfmt` 或 `qm_video_prores_profile` 都会让已完成段失效。

实测旁证（ffmpeg 9.0.2 命令行，与 ddnet-libs 同版本）：`libx264 + -g 1 + yuv444p10le` 产出 `High 4:4:4 Intra`、119/120 关键帧、12.73MB（2 秒 720p）。

## 四、人工验收清单

以下各项需要在真实客户端里做，我这边只到「构建 + 单测 + CLI 实测」为止。

### A. 预设与导出产物

1. 启动开发实例（窗口化）：
   ```
   E:\Coding\DDNet\QmClient\cmake-build-release\DDNet.exe
   ```
2. 载入任意 demo → 演示播放器 → 「渲染回放」（Render demo）弹窗。
3. 预设选「**剪辑 (全帧内 H.264 / MP4)**」→ 导出。
   - [ ] 产物是 `.mp4`，`ffprobe` 显示 `codec_name=h264`；
   - [ ] `key_frame` 几乎每帧为 1（关键帧数 ≈ 总帧数）；
   - [ ] 在 Premiere / Resolve / VLC 里任意位置拖动都不卡顿、不花屏。
4. 预设选「**交换格式 (ProRes 422 HQ / MOV)**」→ 导出。
   - [ ] 产物是 `.mov`，`ffprobe` 显示 `codec_name=prores`、`profile=HQ`、`pix_fmt=yuv422p10le`。
5. 同一段 demo 导出两遍，比较体积：剪辑预设应显著小于交换格式（实测同画面约 1/17）。

### B. 色彩采样下拉

6. 色彩采样选 **4:4:4（细节最好）** + 软件编码器导出。
   - [ ] 产物 `pix_fmt` 是 `yuv444p10le` 或 `yuv444p`；
   - [ ] 画面里的细线、彩色小字（HUD 描边、聊天彩色名字）比 4:2:0 明显更锐利；
   - [ ] 体积约为 4:2:0 的 1.3 倍（不是数量级差异）。
7. 色彩采样选 **4:2:0** + ProRes 导出。
   - [ ] 不报错（自动降级到 4:2:2），产物仍是可播放的 ProRes。
8. 色彩采样选 **4:4:4** + 一个只支持 4:2:0 的硬件编码器。
   - [ ] 导出应明确报错（日志出现 `does not support the requested pixel format`），**不应**静默产出 4:2:0。

### C. NVENC

9. 选 `H.264 / NVENC`，质量填 18，导出同一段。
   - [ ] 体积与「软件编码器质量 18」应在同一量级（旧实现会小一档，看起来偏小）；
   - [ ] 日志里 `cq` 实际值相当于 23。
10. NVENC + GOP 填 1。
    - [ ] 能正常导出（不报 `InitializeEncoder failed`）；
    - [ ] 日志有 warn 提示 `cannot encode all-intra; using a keyframe every 2 frames`；
    - [ ] 产物关键帧约每 2 帧一个，不是每帧。

### D. 续渲与预设

11. 分段导出（`qm_video_segment_seconds` 设小一点，如 30）导出到一半中断，改色彩采样后续渲。
    - [ ] 旧段被重渲，不是直接拼接；成片全程采样格式一致。
12. 选「剪辑」预设导出一次，再把预设切回「自定义」。
    - [ ] GOP 输入框回到 60（预设必须显式写回，否则会残留 1）；
    - [ ] 色彩采样回到「自动」（不应残留 4:4:4）；

### E. 界面

13. 会话态：点开渲染弹窗 → 预设切到「剪辑」→ 点「Abort」→ 重开弹窗。
    - [ ] 色彩采样不是 4:4:4（会话态随弹窗关闭复位）；
    - [ ] `settings.cfg` 里的 `qm_video_pixfmt` 未被改写（只有确认导出才落盘）。

14. 渲染弹窗打开后：
    - [ ] 「色彩采样」行在「画质」与「容器」之间，文字不压到控件；
    - [ ] 弹窗整体高度够用，底部没有被裁掉的设置项；
    - [ ] 长译文（俄语、波兰语）下标签仍完整显示；
    - [ ] 鼠标悬停「色彩采样」出现说明 tooltip。

### F. 剪辑软件（我无法代做）

15. 把两种预设的产物导入 **Premiere Pro** 与 **DaVinci Resolve**：
    - [ ] 都能直接导入（不提示缺少编解码器）；
    - [ ] 时间线擦洗流畅度：剪辑预设应至少与 ProRes 相当；
    - [ ] 颜色与客户端画面一致（不应明显偏亮/偏暗/偏色）。

## 五、已知限制与未覆盖

- **8bit 源头**：`glReadPixels` 仍取 `GL_RGBA8`。提高位深不产生新信息，只能靠 4:4:4 提高色度密度；真正的位深提升需要改渲染缓冲为 10bit 并改读回路径，不在本期范围。
- **NVENC 无法真正全帧内**：驱动拒绝 `gop_size=1`，只能隔帧关键帧。需要严格全内帧请选软件编码器。
- **NLE 实机导入未做**：本机没有 Premiere / Resolve，验收清单 F 项需要人工。
- **性能未测**：本期没有跑导出墙钟对比；4:4:4 相比 4:2:0 的编码耗时增加量未量化。
- **PBO 异步读回未做**：仍在后续期。
