# QmClient 性能研究与优化方案

日期：2026-09-24。性质：部分源码静态调查 + 可执行测量与优化计划；不是运行基准报告。

## 1. 结论与证据边界

QmClient 应优先优化帧时间稳定性、交互时的长帧和功能关闭后的残留开销，然后再追求平均 FPS。模块化有价值，但运行性能收益来自更精确的生命周期、缓存失效、调度和数据访问；把 6000 行代码拆成几十个文件，本身不保证任何 FPS 提升。

补齐全部附件后的当前执行顺序：核对采集有效性与版本 → 复核 Windows 跨客户端图形/连接回归及后端正确性 → 复测文本光栅化与布局的历史热点 → 优化局部失效、资源预算、裁剪与直接批处理 → 仅在 CPU 提交瓶颈得到证明后试验 indirect/GPU-driven。详细增补见第 15 节，涉及优先级时以此顺序为准。

本次读取了仓库 master 上的 gameclient.cpp、engine/client/client.cpp、particles.cpp、skins.cpp、menus_qmclient.cpp、卡片目录实现、frame_scheduler.cpp、性能日志和卡顿诊断头文件等。仓库完整克隆与目录树获取未完成，没有固定到经验证的一致 commit 快照；下文行号是本次下载副本的定位信息，master 后续可能变化。没有构建或运行客户端，没有 CPU/GPU trace，因此所有收益和热点排名均需实测，不能宣称已定位某个实际掉帧根因。

用户附件《大文件拆分简章.md》完整读取。最初三张 PNG 分辨率不足；随后补充的《性能优化总纲.docx》《UI、UX_现代化.docx》《QmClient_Todo.docx》正文已完整提取阅读，补充审查见第 14 节，并以该节修订后的优先级为准。附件里的 43 张卡片、6173 行是该草案描述，并非本次重新核实的卡片数量。Todo 的开发标记不等于发布状态，正文提取也不用于判定全部勾选状态。

## 3. 建立可重复的性能基线（P0）

### 3.1 测量口径

帧预算 B = 1000 / 目标 FPS。60、144、240、300 FPS 分别约为 16.67、6.94、4.17、3.33 ms。

每个场景记录：

- 完整帧间隔的 P50/P95/P99，以及 >B、>2B、>16.67 ms 的帧数/分钟。最大帧时间可保留，但不能单独作为结论。
- 主线程、渲染线程、GPU 时间与等待时间；GPU 计时应异步读取，避免为了测量插入强制同步。
- 组件 Update/Render 的累计时间、调用次数、最大单次时间；嵌套计时注明 inclusive/exclusive，不能直接把父子阶段相加。
- 预测次数/秒、预测 tick 数、world copy 次数、实体数量；draw calls、纹理切换、可见粒子数。
- 每帧堆分配次数/字节、工作集/峰值内存、显存估算、上传字节数、待处理任务数量及最老任务等待时间。
- 设置首次打开、再次打开、切页、搜索、展开卡片、拖拽及皮肤缩略图首次可见的延迟。
- 功耗/温度/频率（特别是集显与笔记本），避免把热降频当作代码回退。

分别运行两种测量：①固定分辨率、不限帧且关闭同步的吞吐测试；②用户实际限帧/VSync 设置下的帧稳定性测试。一次只改变一个因素。主循环 Swap 返回间隔不等于屏幕真实显示间隔，更不能直接等同输入到光子的延迟。

现有性能开关对应 m_QmPerfDebug；控制台变量名称以实际配置注册为准。使用现有 dumps/QmClient_Perf 日志，不猜测不存在的启动参数。

### 3.2 场景矩阵

| 场景 | 固定条件 | 主要观察 |
|---|---|---|
| 主菜单/设置静置 | 固定页面和动画配置，前台/后台分别测 | 空闲 CPU、无效布局、节流是否生效 |
| 空图单人 | 固定地图、镜头、移动路线 | 客户端基础成本 |
| 多人密集区 | 16/32/64/128 人或能稳定复现的实际人数，记录可见人数和实体数 | 渲染、预测、姓名牌/HUD 的规模增长 |
| 复杂地图/高分辨率 | 固定视野，1080p/1440p/4K 按硬件支持选择 | GPU 填充、地图提交、透明叠加 |
| 高延迟与 dummy | 受控环境中 0/50/150 ms RTT，另加抖动场景 | 预测重算、复制、附加预测路径；不能只看 ping |
| 设置交互 | 固定滚动路线、搜索词、展开/折叠/拖拽序列 | definitions 重建、测高、文本布局 |
| 皮肤/资源页 | 相同资产集合，冷缓存/热缓存分别测 | 扫描、解码、合并、上传、取消 |
| 特效组合 | 单个开关与组合开关分别测 | 粒子/拖尾/聊天气泡/预览等增量成本 |
| 长会话及退出 | 运行 30–60 分钟，反复切图、切页、加载资源 | 缓存增长、任务积压、退出等待 |

同一发布构建配置和硬件，预热后每组采样建议 120 秒、重复 5 次，交替 A/B 顺序；这是研究起点，不是强制标准。短交互单独重复 20 次，保留事件前后帧时间。记录 commit、编译器、优化级别、GPU/驱动、后端、分辨率、配置、地图/demo 哈希和资源缓存状态。

Demo 适合可复现渲染回归，不能替代在线预测测试。比较上游 DDNet/Tater 时，先确认所基于版本及共有配置；Qm 自身功能开/关 A/B 更适合定位增量成本。

### 3.3 如何判定瓶颈

- 降低分辨率明显改善 GPU 时间，而主线程基本不变：优先查填充、透明层和 shader。
- 降低分辨率几乎无效，某核心耗时随玩家/实体数量增长：查 CPU 路径。CPU 总占用低不能排除单核瓶颈。
- 每隔一段时间出现尖峰：对齐资源维护、任务完成回调、上传、分配、日志和系统调度。
- client_update 高：继续拆网络处理、预测和组件更新；frame_render 高：继续拆 UI、场景提交；Swap 高：结合 GPU 与呈现等待判断，不能直接归咎 GPU 算力。

## 4. 优化工作包 A：卡片 UI 的失效范围与重复工作（P1）

### 4.1 具体证据与假设

menus_qmclient.cpp 的 ResolveModuleCardMeasureRevision() 会合并目录 revision，并遍历所有模块的测高依赖。HUD、功能、视觉页均将该汇总值用于 DefinitionsRevision。由此可以推导：与当前页面无关的配置变化也可能改变该页定义版本。是否导致有意义的长帧，需以 RenderCached 内部缓存和测量日志验证。

QmCardCatalogVisual.cpp 与菜单文件还各有部分测高相关 revision 分派。重复依赖维护增加漏失效或过度失效的风险，但并不证明现有逻辑出错。进一步读取 SettingsCardDeck.cpp 确认：当 m_InvalidateMeasurementsOnDefinitionsPrepare 为真时，会整体清空缓存高度和测量版本。需跟踪该标志的设置条件，把页级 revision 变化与实际重测次数连起来验证。

### 4.2 实施方案

1. 复用已有 CountDefinitionsPrepare、CountMeasure、CountRenderedCard 等计数，给缓存补齐原因维度：page-change、width、DPI/theme/font/language、card-content、expand、order、resource-ready。区分定义构造与 Prepare 的次数，补缺失的 cache_hit/miss 和耗时。
2. 分离三类版本：结构/成员/顺序版本；影响尺寸的 layout revision；只影响视觉内容的 paint/data revision。改颜色不应导致所有卡片测高，更新歌词/数值不应重建整页定义。
3. 页级版本只聚合本页依赖；单卡版本只聚合该卡布局依赖。跨页共享数据仍显式关联，避免为缩小失效范围漏掉真实依赖。
4. 把重复的测高依赖收敛到卡片模块唯一描述，分类页只选择 ID。先纯搬运，再单独改失效逻辑。
5. Deck 已在 Visible 或 m_RenderWhenClipped 条件下绘制，也有输入延续处理；核查绕过裁剪的卡片是否确有需要，以及预览更新、文本布局、资源申请是否仍在外部继续执行。只修缺口，不另建平行系统。
6. 不可见卡片使用缓存高度占位；尺寸或语言变更时按需要补测。焦点输入框、拖拽卡片和弹出菜单必须保留输入与状态处理，不能简单 `if offscreen return`。
7. 折叠只表示内容不显示，不意味着关闭卡片对应的实际游戏功能。可暂停该卡纯预览，但不能顺带停用语音、通知或功能服务。
8. 字体、换行、宽度计算缓存按文本/字体/字号/宽度/语言等真实依赖失效。不要为 43 张卡片先上复杂空间索引；通常顺序遍历足够。

验收：静态热缓存页面在无依赖变化时不持续重建定义；修改一项布局配置只重测必要卡片；快速滚动、中文换行、缩放、焦点和拖拽一致。计数先证明少做工作，再观察 P99 是否改善。

### 4.3 低优先级候选

BuildCard 当前用 stableId 映射和分类列表线性查找；可在配置规模扩大、且构建路径已成为热点时改成密集 ID→描述符索引。当前卡片数量不大且定义已缓存，直接优化这类查找通常不如减少重建次数。不要默认把 vector 全换成 unordered_map，也不要仅因 std::function 存在就重写接口；先测闭包构造/分配。

## 5. 优化工作包 B：资源流水线与整帧预算（P1）

### 5.1 当前值得验证的问题

CSkins::OnUpdate 已分别调用预览上传续传与加载完成处理，相关路径存在 1 ms 时间预算。两个局部预算、其它资源任务及页面预热若在同一帧执行，其开销可能累加；现有共享上传额度是否足够覆盖全部耗时，要查调用链与日志。

以 300 FPS 为例，一帧只有 3.33 ms；两个各消耗 1 ms 的工作包已占约 60% 帧预算。这是预算示例，不是本次测到的运行结果。

frame_scheduler.cpp 当前展示的是按 consumer 维护自适应状态，而不是由 EndFrame 统一结算的调度器。应先画出上传数量预算、主线程时间预算和消费者预算的关系，找出重复计费或绕过路径。

### 5.2 具体建议

- 尽量复用 IFrameScheduler、现有 SettingsFrameBudget 与上传限制器，提供统一的“本帧可延迟工作剩余时间”。保留消费者公平性，防止同一资源独占。
- 上传预算同时考虑次数、字节和时间。一个 8 MB 资源与一个 32 KB 图标不能仅按“各一次”视为相同成本。
- 将大型任务拆成可暂停小步骤；时间检查只能限制下一项开始，不能打断已发出的 GPU 上传或一次大解码。记录单项最大耗时及超预算次数。
- 优先可见资源，其次邻近预取，最后后台预热；设置页关闭后取消无价值请求，已运行工作用 generation/token 丢弃过期结果。
- CPU 解码、目录扫描和纯解析放现有工作队列；UI 状态合并与图形 API 操作遵守现有线程归属。不要为每张图片创建线程。
- 对解码结果队列设置字节上限与背压，防止“后台解码很快、主线程上传很慢”造成内存持续增长。
- 记录队列最老等待时间，保证大资源最终能完成。减少长帧但让缩略图永远不显示不算成功。
- 按资源版本复用结果；同一资产被多个卡片/预览请求时合并请求。处理加载失败、重试退避、切图取消和失效句柄。

源码中的 CSkinDownloadJob::Run 有 HTTP Wait，但它位于 job 实现中；不能据此声称主线程在同步下载。应进一步查工作池是否被等待占满、取消能否及时返回、退出是否等待长超时。

验收：冷启动与大量皮肤下 P99 改善，同时首屏可用延迟、全部资源完成时间、峰值内存和后台任务数量可接受；热缓存不得因调度框架新增明显成本。

## 6. 优化工作包 C：粒子、特效与渲染（P1/P2）

### 6.1 已存在的细节

RenderGroup 的缓冲路径在颜色、alpha、sprite 或容量变化时结束一批。若同一贴图的粒子生命周期不同，alpha 不同也可能导致批次变碎。这是可直接定位的候选，不是已测瓶颈。

旧渲染路径已按相邻 sprite 合并并保持透明顺序，因此“把所有粒子按贴图排序”不是安全的通用建议。透明混合通常有顺序语义。

### 6.2 实施步骤

1. 统计每组粒子：活跃数、可见数、绘制批次、平均粒子/批，以及批次结束原因。
2. 如果颜色/alpha 是主要打断原因，评估缓冲路径能否把每粒子的颜色/alpha 放入实例/顶点数据，保留绘制顺序并扩大相邻兼容批次。需要核查现有图形接口、shader 和所有支持后端；属于后续引擎改动候选。
3. 检查零实例提交，确认存在且频繁时再消除。现有批次初始化与首次切换路径可作为检查入口。
4. 核查拖尾、气泡、姓名牌、3D 背景等是否各自做了可见性判断、容量上限和关闭门控；本次未读取这些实现，不把缺陷视为已确认。
5. 只对纯装饰效果提供质量档位：粒子密度、拖尾采样数、模糊/辉光分辨率等。保持玩法判定、输入和物理不变。自动降质需用户可理解、可锁定，避免质量来回跳变。
6. 对静态几何/地图提交先抓图形帧，确认 CPU 提交、GPU 填充或同步谁占主导，再决定是否缓存几何或调整渲染目标。不能仅因 DDNet 是 2D 就忽视 GPU。

验收：粒子数量及画面等价时绘制批次下降、CPU/GPU 时间改善；透明重叠、不同 alpha、旧后端及新后端截图一致。降低质量带来的收益与等价优化分别报告。

## 7. 优化工作包 D：预测、世界复制与多人场景（先测量，P2）

OnPredict 中有 GameWorld→PredictedWorld、前一预测世界、常规预测世界与附加预测世界等复制；逐 tick 模拟数量又与预测跨度及 fast input 路径相关。人数、实体数、RTT、附加功能可能共同放大成本。

优先加入细分计数与采样：

- OnPredict 调用次数及耗时，起止 tick、普通/附加 tick 数。
- 每类 CopyWorld/CopyWorldClean 的次数、时间、复制实体数与分配字节。
- 世界 Tick 中 character/projectile/collision 的成本，以及事件处理耗时。
- dummy 开/关、fast input 开/关、AntiPingSmooth 开/关、相关附加预测开/关的独立 A/B。

第一轮只考虑可证明等价的工作减少：复用已分配容量、去掉同一有效状态内的重复查询、按已有配置语义跳过未消费的派生结果。若引入活跃实体列表，必须保持实体处理顺序及完整性，并测维护成本是否抵消收益。

不要直接采取以下做法：降低预测 tick 频率、删世界复制、按可见性跳过物理实体、用近似碰撞、随意并行玩家预测、启用会改变浮点行为的激进选项。它们可能改变本地手感、事件顺序或与服务器一致性。

预测缓存的有效键不能只有 server tick；还需考虑输入变化、dummy 切换、tuning、世界版本和影响预测的配置。否则“少算”可能只是用了过期状态。

验收：同一输入/快照序列，在同构建环境下逐 tick 比较位置、速度、冻结状态、钩索和武器事件；覆盖高延迟、切换 dummy、死亡重生、传送、tuning 变化等。录制回放能覆盖的部分与在线输入路径分别验证。不能仅凭 FPS 变高认定成功。

## 8. 优化工作包 E：模块生命周期、后台功能与内存（P1/P2）

OnUpdate/OnRender 当前遍历组件表。组件被调用并不意味着成本高，它可能立即返回；需看功能关闭后是否仍进行字符串处理、轮询、构造列表或申请资源。

建议为选定热点功能定义生命周期：启用、停用、订阅数据变化、可见性变化、资源就绪、释放。低频元数据由事件或低频调度更新；渲染时只做必要插值和提交。网络、输入、语音连续音频处理等有自己的实时要求，不能统一降到“每秒更新几次”。

如果存在音乐/歌词、翻译、远程状态等后台服务，重点测：轮询频率、响应解析在哪个线程、字符串和纹理是否重复构建、停用后任务是否继续、多个订阅方是否重复请求。相关实现本次未完整审查，属于待调查项。

内存优化按 profile 行动：

- 复用热路径临时 vector 的容量；适度 reserve，并对极端容量设置回收策略。
- 缓存格式化文本与解析结果，避免不变数据逐帧处理。
- 容量固定且生命周期明确的纯视觉对象可用现有对象池/固定存储；不要全项目自建分配器。
- 如果实体遍历被证明受数据访问限制，再考虑更连续的热数据布局；不要为了“现代化”先改 ECS 或 AoS/SoA。
- 所有缓存都需内存上限、失效规则、命中率与释放路径；缓存越多不等于越快。

验收：静态场景热路径分配次数减少，长会话内存进入平台期；功能关闭后的每秒工作量接近该功能确实需要的最低水平；重启功能不出现旧结果、悬空引用或重复订阅。

## 9. 模块化怎样真正帮助性能

| 改动 | 直接运行收益 | 主要价值/风险 |
|---|---|---|
| 大 cpp 拆成小 cpp | 不保证 | 缩小增量编译范围；头依赖过重也可能仍全量重编 |
| switch 改注册表 | 不保证 | 维护性提升；间接调用也有成本，不必以去 switch 为性能指标 |
| 单卡拥有自己的状态、测量依赖和缓存 | 有潜力 | 缩小失效范围，避免整页重建 |
| 纯预览与实际功能服务分离 | 有潜力 | 隐藏预览可暂停，后台功能仍正常 |
| 功能有明确启停/订阅生命周期 | 有潜力 | 停止无效轮询、重复解析和后台任务 |
| 重型任务通过现有调度接口申请预算 | 主要改善长帧 | 必须防止饥饿、过期工作及预算重复叠加 |
| 每功能独立计数与开关 | 间接收益很大 | 可以稳定 A/B 和归因，而不是靠猜 |
| runtime 动态插件系统 | 无必要保证 | 新增 ABI、生命周期和加载复杂度；本轮不建议 |

建议沿用当前 src/game/client/QmUi/cards/ 目录与 QmCardRenderHook 桥接，逐卡把实现、尺寸依赖、状态生命周期收敛到明确归属；功能服务仍放现有 qmclient 组件域。不要仅按 visual/function/hud 分类重新制造三个大文件。

附件提出的一张卡片一个文件可作为组织偏好，但“唯一真相源”来自唯一实现及依赖契约，并非物理同文件才能实现。大型复杂卡片允许内部分解，只要接口和状态归属清楚。

附件中“新增一个文件+一行注册”与“不修改任何既有文件”存在工程表述冲突；本次读取的 AGENTS.md 明确要求新卡片源文件登记 CMake GAME_CLIENT 列表。建议把目标改为“不修改宿主分发与既有卡片；允许修改声明式注册及构建清单”，不为追求零改动引入全局静态自注册或隐式 glob。

拆分验收与性能验收分开：

1. 纯搬运：功能、配置、卡片 stableId、顺序、折叠、搜索、焦点和画面一致；不混入缓存策略变化。
2. 优化：每个补丁只有一个可验证假设，说明减少了什么工作，给出前后计数与帧时间。
3. 构建效率：另行比较修改单卡后的增量编译时间、干净构建峰值内存和链接时间；不要把这些写成 FPS 收益。

## 10. 编译与发布优化（P3）

性能测试使用与发布接近的优化构建并保留符号，避免拿 Debug 数据做发布判断。先核查仓库当前已启用哪些选项，再评估 LTO/IPO 和基于真实混合场景的 PGO。

## 11. 实施顺序与退出条件

以下是建议工作包，不是未经测量的收益承诺，也不是固定工期。若实测显示别的路径占主导，应重排。

| 顺序 | 工作包 | 交付物 | 进入下一阶段的条件 |
|---|---|---|---|
| 0 | 固定 commit 和基准场景 | 配置、硬件记录、原始日志、帧时间分布 | 同条件可复现，已知道测量噪声 |
| 1 | 校验现有诊断 | 关闭/开启诊断 A/B、缺失计数、采样规则 | 不把日志限流后的明细当全量数据 |
| 2 | UI 局部失效实验 | 单卡/整页重建次数及交互延迟对比 | 行为一致，证明确实减少工作 |
| 3 | 资源预算实验 | 每帧累计耗时、上传字节、队列延迟 | 长帧下降且资源最终能完成 |
| 4 | 粒子批次实验 | 批次打断原因、CPU/GPU 对比 | 数据证实绘制提交值得改动 |
| 5 | 功能关闭残留与内存 | 功能成本表、长会话内存曲线 | 无持续增长与无价值后台工作 |
| 6 | 预测深层实验 | 复制/模拟占比与确定性回归 | 确认值得承担核心路径修改风险 |
| 7 | LTO/PGO | 同硬件发布配置 A/B | 多场景稳定收益且兼容性无回退 |

最先安排的五个具体任务：

1. 用现有性能日志采集“实际游戏卡顿”与“设置页卡顿”各一组，先判断主导路径。
2. 统计 definitions/measure 缓存失效原因，复现改一张卡片是否触发无关页面重建。
3. 汇总所有资源消费者同帧耗时，查局部 1 ms 预算是否叠加。
4. 给粒子批次增加结束原因计数，判断 alpha 差异是否使批次退化。
5. 在高人数/高 RTT/dummy 场景统计 world copy 和预测 tick，决定是否进入预测优化。

建议用“改善超过运行间噪声，且其它重要场景无可重复回退”作为合并标准。例如项目可以约定目标 P99 下降至少 10%–15%、非目标场景无稳定超过 3% 的回退，但必须根据测量波动调整，不能把这些示例数字当收益预测。

### 14.2 总纲应修正的技术判断

| 原文判断 | 建议修订 |
|---|---|
| 卡顿根因域是 CPU 侧单帧工作量 | CPU 堆叠是一个重要候选；GPU 超时、同步等待、驱动、系统调度、资源缺页及呈现节奏也需纳入模型 |
| 优化唯一目标是摊平峰值 | 主目标可定为减少长帧，但也需降低持续成本和等待；分帧必须同时控制结果就绪延迟 |
| 0.5 ms 优化到 0.4 ms 对 P99 毫无帮助 | 是否影响 P99 取决于它是否处在尾部帧的关键路径及是否跨越预算，不能绝对排除 |
| 8 ms 拆成 8 帧各 1 ms，P99 直接消失 | 只有每帧确有余量且任务可分割才成立；其它成本仍可能超预算，且资源就绪会延迟 |
| 300 FPS 预算 3.33 ms，同时将 5 ms 的 section 预算列为范例 | 5 ms 不能作为满足 300 FPS 的同步主线程可用额度；还需核查总纲所列 8.333 ms 自适应默认目标的实际调用覆盖值 |
| P99 和 Max 俗称 low 帧 | 分位帧时间、最大帧时间和 1% low FPS 是不同统计量；需明确工具定义，不能互换 |
| 必须每帧一条日志才能算分布 | 应完整观测每帧，但可批量序列化、压缩或使用有精度界定的统计结构；每帧写一行不是必要条件 |
| 日志体积只应正比于卡顿次数 | 全量帧记录必然随时长增长；准确模型是基础记录随时长增长，额外明细随触发事件增长 |
| 每秒 1000 条意味着每小时约 540 MB 是必然 | 这是每条约 150 B 且持续打满限额的估算，不是必然量；日志入口、豁免项、实际行长和触发率需单独核查 |
| 接入 IFrameScheduler 即获得全局预算保护 | 统一接口不等于所有消费者共享总余量；必须验证 ComputeBudget 的状态共享、调用方消费和额度耗尽路径 |
| 有 m_CardDrawTokens 就代表卡片绘制已受限 | 字段存在不证明执行路径消费了它，更不证明所有路径都无法绕过；需跟踪发放、消费、耗尽和延期行为 |

日志体积的算术基线：300 FPS × 3600 秒 × 16 B/帧，约 17.3 MB/小时（十进制），尚未计文件头和明细；若为 80 B/帧，则约 86.4 MB/小时。想把总量稳定控制在几十 MB 内，需明确格式、压缩、保留策略和事件上限，而不是只缩短文本字段。

总纲的呈现模式表不应直接指导默认设置。“无上限几乎不撕裂”“VSync 延迟必定最高”“呈现对齐几乎必然撕裂”均缺少适用条件；要结合后端、窗口/独占模式、合成器、VRR、队列深度和具体实现评估。高 FPS 不意味着整帧扫描发生在极短间隙内，也不保证画面无撕裂。CPU 帧时间与呈现是不同观测，但不是完全没有因果联系。

参考官方资料：[Microsoft DXGI 呈现模型](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)、[可变刷新率显示](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/variable-refresh-rate-displays)、[Intel XeLL 延迟说明](https://www.intel.com/content/www/us/en/developer/articles/technical/xell-developer-guide.html)。这些说明呈现行为的条件性，不直接证明 QmClient 的某个后端或 qm_present_align 实现怎样工作。

### 14.3 新 UI 目标必须附带性能约束

以下是对计划功能的设计建议，不表示已经发现对应源码缺陷。

| 计划 | 性能约束与验证重点 |
|---|---|
| 新旧 UI 一键热切换 | 共享配置和功能服务；只让当前 UI 更新布局与动画。切换时取消旧预览、释放订阅、处理焦点和弹层，防止两套界面持续工作 |
| 全局搜索就地呈现卡片 | 搜索元数据索引与卡片实际构建分离；空查询按文档目标显示搜索卡，避免默认构建全部功能预览；输入变化再更新结果 |
| 多种模糊、玻璃、阴影、辉光 | 先验证 GPU 成本；研究同背景效果复用，避免每张卡片重复全屏处理。裁剪区域、分辨率和质量档分别记录；质量折中不能冒充等价优化 |
| MTSDF 图标及字体回退 | 图集资源按 DPI/样式等真实依赖更新；检查首次使用上传尖峰与切换后的旧资源释放，避免每帧重载 |
| 下拉框离开视口后仍需维护弹层 | 锚点位置和交互延续与内容绘制分离；允许维护少量几何，不代表必须继续渲染整个离屏卡片 |
| 聊天消息复用为 Toast | 复用消息数据与绘制能力，分别管理队列、布局缓存和生命周期；避免为了显示单条 Toast 每帧布局整个聊天历史 |
| 动态预览与动效 | 只更新实际可见且活动的预览；布局版本不应跟随纯颜色/透明度动画逐帧变化 |

### 14.4 Todo 中需要提前设性能边界的功能

- SQLite 跨局统计：从主线程收集事件，使用有界队列异步批写；不要把磁盘事务放进每帧路径。退出时的持久化等待、失败重试及最大数据量需明确。
- 服务器镜像 JSON、缓存和好友跟随：共享查询结果并按版本增量刷新；缓存显示标注过期状态；限制轮询和重试，避免多功能重复拉取与排序。
- 截图管理器、皮肤和材质编辑器：目录索引、缩略图解码与可见项上传分离；资源数量增长时不能逐帧全量扫描。
- 画中画观战：单独量化额外视角的场景提交、渲染目标和像素成本；优先复用可共享的数据，不为显示第二视角默认复制整套预测服务。
- preinput 状态 HUD：按收到的数据更新派生状态，绘制读取缓存；消息缺失与过期时显示未知状态，避免推断出并不存在的按键状态。
- Bind 识别与配置归档：命令串变化或打开编辑器时解析；导入导出属于用户触发任务，不进入逐帧循环。
- 禅模式：隐藏纯视觉效果可以减少绘制；必须区分停止产生装饰效果、停止绘制、关闭实际服务这三种语义。
- Qm/TClient 分离：优先明确状态、资源与事件订阅的所有者，避免拆分后双方各维护一套相同缓存或后台任务。

### 14.5 修订后的第一阶段任务

1. 固定代码版本，制作“总纲声明—实际实现—运行证据”对照表，避免重复建设已落地机制。
2. 核实完整帧样本是否连续、阶段阈值与 dropped 是否只影响明细，验证现有报表的分位数口径。
3. 打通预算发放、实际消费、耗尽、延期与完成延迟的观测；统一解释 300 FPS、120 Hz 默认预算和 5 ms section 示例的适用范围。
4. 再按真实尖峰选择卡片失效、资源预算或游戏内路径的单项优化；本报告前述 UI/粒子候选继续保留，但不能压过实测结果。
5. 给新增 UI 与 Todo 功能定义热缓存成本、关闭状态成本、资源上限及取消规则，使模块化不仅方便搬代码，也能约束运行工作量。

## 15. 采集审查与渲染规格补充后的研究结论

本节依据用户提供的《性能采集体系审查.md》（2026-09-19）和《渲染规格.md》（汇编 8 月至 9 月的三份规格及后续补充），并对照本会话前段读取的源码副本。没有新增真机实测，没有将文档中的历史实验当成本次实测。未取得其引用的《Windows 图形掉帧撕裂与连接中断调查》原文和原始 trace。

### 15.1 采集审查应改成逐项复核，而非整体重建

审查报告最后明确承认：若有未检出的全量旁路，“正常帧没有数据”的结论需要修正。前段源码中确实读到 m_QmPerfFrameBatch.Record(PerfFrame(), FrameMs) 和 perf/frame 批记录路径。这证明存在独立帧记录入口，但尚不能证明整个采集—解析—报表链无漏帧。

| 9 月 19 日审查结论 | 与已读取源码的对照 | 现在应做什么 |
|---|---|---|
| 4 ms 可配置阈值截断正常帧 | 副本中阈值来自 300 FPS 对应的约 3.33 ms；存在独立完整帧批记录入口 | 固定 commit，确认阈值配置是否仍有效；核查 frame 序号、会话、首尾批及异常结束的缺失量 |
| QmPerfLogStageForce 名不副实 | 在已读 perf_logging.h 中未找到该函数；现有 QmPerfLogStage 将 Force 传入判断 | 不按历史行号修不存在的函数；追踪版本变化，验证当前 Force 语义 |
| 每秒 1000 条明细限额 | 副本仍有该限额及 dropped 计数 | 统计触顶比例、被丢弃的事件类别、关键事件保护与日志开销 |
| 卡片观测缺失 | Deck 已有测量/准备/绘制计数 | 检查是否真正连到采集和报表；计数不等于逐卡耗时归因 |
| HTML 依赖 CDN、无降采样 | 本会话尚未读取当前 report.ts 和解析器 | 保留为待核实问题，不能宣称已确认仍存在或已修复 |

还需修正三个采集设计细节：

1. 每帧 8 条限额在 300 FPS 下允许 2400 条/秒，按 150 B/条约 1.296 GB/小时，比 1000 条/秒的示例更大。按帧限额不自动减少体积；建议同时设置事件窗口预算、明细字节率上限、文件轮转/总量上限，并为完整帧记录保留独立通道。
2. 帧分布只能来自完整记录或明确误差的统计结构；展示降采样与统计计算必须分离。不能用图表抽取后的点重算 P99。峰值保留策略也应独立验证，不能把使用某种降采样算法当成保留所有异常的保证。
3. 有时长的阶段事件仍不等于时间线。归因至少需要单调时钟起止或 start+duration、线程/队列标识、frame/submission 关联和缺失标志；嵌套阶段与并行阶段不可直接求和。

“采集不修，任何归因都不可信”也应收窄：截断明细不能给出完整分布，但仍可证明某次被记录的操作耗时很高；一个有效 GPU capture 或独立采样 profile 不会因另一个报表缺陷而自动无效。先判定具体数据能回答什么，不必暂停所有局部研究。

### 15.2 文本路径已有历史测量，应先复测已做优化

《渲染规格》第三章 §6.3.1 记载了以下历史结果：

- 字形光栅化：单帧 30–44 ms，对应 108–210 个字形。
- plan 收集/布局：单帧创建 1697 个容器，约 12.7 ms。
- 所述场景 GPU 上传占比不足 1%。
- 文档称字形缺失记录、空闲预热、跨会话记录与 ESC plan 提前收集已消除相关打开场景尖峰。

这些记录使文本 CPU 路径成为优先复核对象，但不能推广为“所有文本卡顿都来自 CPU”，也不能直接认为当前版本还存在同样问题。需取得对应版本和日志，复测冷启动、热缓存、首次中文/新字形、语言切换、DPI/字号改变、图集扩容及运行中打开菜单。

测量拆为五段：文本 plan 收集、布局/测量、FreeType 光栅化、图集上传、容器构造/提交。每段同时记录耗时、处理数量和等待数量。

特别检查“空闲”的定义：菜单关闭但玩家仍在游戏中，并不意味着有空闲帧预算。预热应服从实际剩余预算和交互优先级，验证打开菜单时的尖峰没有被搬到游戏过程中。

文本任务成功标准：冷场景峰值下降、热缓存无回退、游戏中预热不制造新长帧、缓存能正确失效且内存有界。只有光栅化在剩余问题中仍占主要成本，才单独设计 FreeType 工作线程与字形发布生命周期；不能靠 GPU indirect 提交解决 CPU 字形生成。

### 15.3 Windows 跨客户端回归应独立于 Qm UI 优化

规格最后记载，同一 Windows 机器上的官方 DDNet、BC 和 QmClient 都能复现，且存在图形注入层、驱动及系统版本因素。这提高了共享图形路径或机器环境因素的调查优先级，但不证明具体驱动/注入层是根因，也不能排除三客户端共享代码的问题。

建议使用逐步收窄的实验，不做全部变量组合：

1. 保存现有版本、配置、后端、显示模式、刷新率、驱动和图形 layer 清单；三个客户端分别跑同一地图与相近配置。
2. 在隔离测试配置下比较有/无可选图形注入与覆盖层，逐项变化；不要把关闭一个程序窗口等同于确认其注入已移除。
3. 在实际支持的后端/present mode 下 A/B，记录实际运行状态，不以配置首选值代替；随后才考虑驱动或系统对照环境。
4. 同时采集主线程、图形线程阻塞、GPU/呈现和 network pump 时间戳。图形异常与连接中断必须对齐时间，不能凭先后描述认定因果。

重点验证的假设链：图形线程等待过长 → 命令队列背压使主线程等待 → network pump 间隔拉长 → 连接状态恶化。这仅是假设。需要区分“服务器/网络没有包到达”“包已到达但客户端迟迟没有处理”“游戏画面停滞但网络仍正常”。单纯切 FIFO/MAILBOX/IMMEDIATE 只能作为实验，不能先行写成主修复。

### 15.4 后端正确性优先，但需要限定到平台与能力

规格记录的 render pass 兼容性、命令重录状态缓存、离屏目标跨批次恢复、buffer 原地更新与 readback 生命周期问题，若在目标版本仍存在，应先于高级性能改造处理。性能基线必须建立在画面和资源状态正确的前提上。

本轮建议锁定的合同：

- 同逻辑帧 screenshot/read-pixel 不重复 present，读取同一结果，失败不伪造成功。
- GPU 尚在使用的 buffer/ring 区段不被 CPU 覆写；资源回收以完成状态为依据。
- pass/encoder 重启或命令重录后，所需 pipeline、descriptor、viewport/scissor 状态明确恢复。
- render target、MSAA、resize、最小化及恢复时保持尺寸、格式、sample count 和内容保存语义。
- 初始化失败后 capability 清空，区分用户请求与实际运行后端；兼容后端继续可用。

发现无必要 WaitForIdle 时，不能只删除等待；应先确定它保护的资源生命周期，并用正确的帧槽、完成信号或延迟回收替代。正常提交、截图、shutdown 和旧平台 workaround 的等待分别计数。

规格将 iOS 全平台适配放入 GPU-driven P0 阶段门，会使未上线平台阻塞桌面实验。建议后续规格评审采用“公共合同门 + 各平台发布门 + 各能力启用门”：桌面原型可以在目标平台正确性完成后评估，但不得因此宣称 iOS 可用。此处是评审建议，不是擅自修改原规格的既定门禁。

### 15.5 GPU-driven 是后期条件任务，不是总方案的起点

遵循渲染规格中较务实的顺序：

1. 核查已有屏外裁剪及边界修正，避免漏画钩索、弹道、缩放边缘对象。
2. 保留现有连续 tile index range 合并，先统计实际有效性。
3. 减少文本重建、临时分配、descriptor 更新和无必要等待。
4. 优先验证现有 sprite-multiple 的实例数据与相邻兼容批次；本报告的每实例颜色/alpha 候选可在此阶段评估。
5. 只有 CPU encode/submit 明确占主导且离散 draw 足够多时，试验 indirect；报告构建间接命令、上传、同步及执行的净收益。
6. compute culling、render graph 扩展、SDL_GPU adapter 分别设实验和停止条件，不合并成一场架构重写。

早期可在现有命令与后端内部完成实验，不必先要求所有游戏/UI 调用迁移为新的 packet。长期中立 packet 合同可保留，但应避免旧命令转换再复制一遍带来的额外 CPU/内存成本。GPU-driven 收益未超过噪声或只惠及不现实的极端场景时，保留实验开关或终止。

规格中的上游 commit/PR 清单基于 8 月检查，不代表当前仍未合入。实施前核查等价实现、依赖修正和回归覆盖；本次没有移植这些提交。

### 15.6 渲染文档自身需要一次状态整理

合集第一章称“尚无 Metal 后端、默认 OpenGL”，第三章又描述已有 Metal shader、性能模式和自动版本回退；这是不同历史阶段并存，不能同时视为当前仓库事实。第二章已描述 OpenGL 版本显示修复，但后面的执行顺序仍将修复列为第一步，也需要消除状态漂移。

建议在每节首部补充：适用 commit、最后核验日期、设计/已实现/已实测状态、替代章节、剩余阻断项。三套 P0–P5 应注明属于 Metal 接入、后端性能还是 GPU-driven，避免团队误把同名阶段看成同一验收范围。

### 15.7 现在最值得交付的四个研究结果

| 研究结果 | 必须回答的问题 | 完成证据 |
|---|---|---|
| 采集可信度表 | 哪个分布完整、哪个明细受门控、丢多少？ | frame 连续性、日志开销、解析口径、离线报表检查 |
| 文本场景对照 | 旧尖峰是否已修，冷字形和预热是否仍影响游戏？ | 冷/热及失效场景的五段成本、P99 与就绪延迟 |
| Windows 因果时间线 | 图形停顿与网络断连是否通过主线程阻塞关联？ | 跨客户端对照及线程/呈现/network pump 同时序证据 |
| 渲染提交成本表 | CPU 提交、GPU 执行还是同步等待主导？ | draw/descriptor/upload/wait 与 CPU/GPU 耗时对应 |

完成这四项后，再决定卡片失效、资源调度、粒子实例或 indirect 哪项进入实施。模块化继续推进纯搬运和状态归属整理，但不把文件拆分数量作为性能进度。
