## 二、官方 20.0 的既有做法

上游已经验证过一条路径：**按设置分类一个文件**。`ddnet-upstream/master` 的 `menus_settings*` 系列共 **14 个文件**：

```
menus_settings.cpp
menus_settings_appearance.cpp      menus_settings_graphics.cpp
menus_settings_assets.cpp          menus_settings_language.cpp
menus_settings_controls.cpp        menus_settings_player.cpp
menus_settings_credits.cpp         menus_settings_sound.cpp
menus_settings_ddnet.cpp           menus_settings_tee.cpp
menus_settings_general.cpp         menus_settings_tee7.cpp
```

对比当前 `dyl_dev` 只有 4 个（`menus_settings.cpp` 8836 / `menus_settings_assets.cpp` 7825 / `menus_settings_controls.cpp` 920 / `menus_settings7.cpp` 716）——**拆分是上游已经在走的路，本仓库落后了**。

**可复用的结论**：官方证明了"大文件可以按功能边界拆开"这件事可行，但它采用的是**设置分类**粒度（本质是页面切片）。全局卡片需要的是**卡片级**粒度（功能单元）——两者差异见 5.1。官方的价值在于：证明此路可行，且 `menus_settings_*` 是现成先例，本仓库可借以减少与上游的冲突。

## 四、为什么要拆（理由）

按影响从强到弱：

1. **认知边界**：卡片要"功能与页面解耦"，前提是功能代码本身有边界。一个 7000 行文件里，任何改动都要先理解全部上下文。
2. **合并冲突**：与上游同步时，大文件是冲突重灾区。本仓库正落后上游 2018 个提交，每次同步都在这些文件上打架。
3. **编译增量**：改一行触发整个翻译单元重编。7000 行文件的重编成本远高于 800 行文件。
4. **可测试性**：2261 行的函数无法写针对性测试，只能做整体快照。
5. **可拖拽**：`#165` 的"组件拖拽器"要求卡片可跨分类移动。若卡片声明与渲染混在一个文件里，移动卡片就要动大文件。

**反面提醒**：不是为了"好看"才拆。若拆分后接口更绕、调用链更曲折，那不如不拆。

## 五、拆分方案

### 5.1 两个维度：官方按"页面分类"，卡片按"功能单元"

这是本方案与官方做法的**根本差异**：

| | 官方维度 | 卡片维度 |
| --- | --- | --- |
| 切分依据 | 设置分类（appearance / graphics / sound…） | 卡片（功能单元） |
| 本质 | **页面切片** | **功能切分** |
| 一张卡片的位置 | 渲染、测量、revision 可能散在多个文件 | **自包含于一个文件** |
| 跨页移动卡片 | 跨文件搬代码，还要找散落的测量与 revision | 改一行注册声明 |
| 复用卡片 | 需要把多处代码各复制一份 | registry 多注册一次 |
| 高度一致性 | 靠人工跨文件对齐（**已出过 bug**） | 三者同文件，改动就近 |

**结论**：官方维度解决"文件太大"；卡片维度解决"单元不清"。全局卡片要的是后者——**卡片成为文件，文件就是卡片**。

### 5.2 一张卡片 = 一个自包含文件

每张卡片文件包含四部分，**前三部分同处一个文件，这是关键**：

```cpp
// card_translate.cpp —— 翻译卡片

namespace {
    // ① 内容渲染（HSplitTop 顺序消耗）
    void RenderContent(CUIRect &Content, ...) { ... }

    // ② 高度测量 —— 紧邻渲染函数，改一处就能看见另一处
    float MeasureHeight(float ContentWidth) { ... }

    // ③ 依赖声明 —— 决定何时重测
    uint64_t ContentRevision() { return ...; }
}

// ④ 注册 —— 唯一的对外接口
qm_card::Register({
    .StableId = "qm:translate",
    .Page     = EPage::Function,
    .Render   = RenderContent,
    .Measure  = MeasureHeight,
    .Revision = ContentRevision,
});
```

**收益**：③ 让"高度单一真相源"从一个规约变成**物理事实**——渲染与测量在同一文件；跨页移动卡片时，测量代码不会掉队。

### 5.3 目录结构

```
src/game/client/components/qmclient/cards/
├── framework/
│   ├── card_definition.h      # 卡片定义（沿用 SSettingsCardDefinition）
│   ├── card_deck.cpp          # 牌堆调度（沿用 SettingsCardDeck）
│   ├── card_registry.cpp      # 注册表（沿用 QmCardRegistry）
│   └── card_widgets.cpp       # 共享小控件
├── visual/     card_camera_view.cpp(732) · card_skin_transition.cpp(111) · …   共 9 张
├── function/   card_translate.cpp(528) · card_pie_menu.cpp(361) · …            共 15 张
└── hud/        card_voice.cpp(627) · card_lyrics.cpp(71) · …                   共 14 张
```

**framework 层必须存在**：`RenderQmFunctionCheckbox`(11)、`RenderQmVisualCheckbox`(11)、`RenderQmVisualLabel`(5)、`RenderQmHudCheckbox`(24)、`RenderQmHudLabel`(5)、`RenderQmHudKeyBindRow`(30) 这 6 个是**多张卡片共用的小控件**，不属于任何单张卡片。放在框架层，否则拆卡片会产生循环依赖。

### 5.4 分类由数据表达，不由目录表达

卡片属于哪个分类（visual / function / hud），**由注册声明里的 `Page` 字段决定，不是由文件所在目录决定**：

- 目录只作**默认归类**，便于人查找；
- 卡片换页 = 改注册声明，**不需要移动文件**；
- 真正实现"拖拽"依赖的是 registry 的 `tab` / `column` / `order`（已在 `SCardDefault` 中定义）。

**这点很重要**：若分类靠目录表达，拖拽就必须移动文件，问题会退回成"文件组织"。让分类由数据表达，文件只承载代码。

## 六、风险与执行顺序

### 6.1 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **头文件声明膨胀** | 方法从 `CMenus` 拆出后，声明放在哪 | 优先沿用"仍是 `CMenus` 成员方法"的做法，只拆 `.cpp`；这在上游 `menus_settings_*` 已验证 |
| **静态成员/文件级状态** | 拆文件后 `static` 变量作用域变化 | 逐处检查需跨文件共享的 `static`（如 `s_aCollapsed`），改为类成员或集中声明 |
| **测量/渲染配对被打散** | `m_Measure` 与渲染函数必须在同一逻辑单元 | 同一张卡片的两者放同一文件（如 `MeasureContentHeight` 与各 `RenderQm*Content` 同文件）|
| **与并行工作冲突** | 当前仓库正在合并上游 | 拆分需在合并完成后进行，否则冲突翻倍 |

### 6.2 执行顺序（按风险递增）

1. **先做无依赖的**：`menus_qmclient.cpp`（分类前缀已就绪，纯搬运）；
2. **再做需要拆函数的**：`menus_tclient.cpp`（先拆 2261 行函数）；
3. **最后做与上游耦合的**：`menus_settings*.cpp`（建议直接采用上游 14 文件结构，减少未来冲突）。

**每步的验收**：拆分后**不改变行为**——构建通过、相关测试通过、界面观感一致。纯搬运不应引入任何逻辑改动。

## 七、判定标准

1. **没有任何单个源文件超过 2000 行**（当前 25 个）；
2. **没有任何单个函数超过 300 行**（当前最大 2261 行）；
3. **一张卡片的渲染、测量、依赖声明位于同一文件内**（卡片自包含）；
4. **新增一张卡片不需要修改任何既有文件**——只需新增一个卡片文件并注册。若新增卡片仍需编辑 `menus_qmclient.cpp`，说明拆分未达卡片维度；
5. 拆分后**接口没有变得更绕**——若某个函数被拆成 5 层调用才能读懂，视为拆分失败；
6. 与上游同步时的冲突面**不再集中在少数几个文件**。

其中第 3、4 条是**卡片维度特有**的判据，只有按卡片拆才能满足。
