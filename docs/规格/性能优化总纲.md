# 性能优化总纲

> 状态：**现行**（2026-09-19）
> 配套证据：[性能采集体系审查.md](性能采集体系审查.md)
> 本文不是执行清单，而是把"性能优化"这件事在本项目里的完整模型说清楚：**问题的本质是什么、为什么会发生、怎么测才算准、优化的唯一目标是什么、这套体系应该长什么样。**

---

## 第一章 · "性能"这个词被混用了

讨论性能之前必须先拆词。在本项目里，"性能有问题"至少指三件**互不相干**的事：

| | A. 帧时间分布 | B. 画质稳定性 | C. 资源占用 |
| --- | --- | --- | --- |
| **现象** | 卡顿、low 帧 | 撕裂、闪烁、画面不稳 | 显存/内存/包体膨胀 |
| **判据** | 帧时间分布的尾部 | 输出与期望是否一致 | 绝对量是否超预算 |
| **根因域** | CPU 侧单帧工作量 | 呈现/合成路径与驱动 | 资源生命周期管理 |
| **"优化"的含义** | 摊平单帧峰值 | 消除不一致 | 减少驻留与重复 |

**最常见的错误**就是拿 A 的手段治 B 的病（例如用改垂直同步去治卡顿，或用降画质去治撕裂）。三者必须在报告、讨论、文档里始终分开表述。

本文主要处理 **A**，并在第七章单独界定 **B**。**C** 不属本文范围。

## 第二章 · 帧时间的物理模型

### 2.1 帧预算是硬约束

渲染是一条流水线，每帧必须在固定时间内完成。本项目以 **300 FPS 为目标**，即每帧预算：

```
1000 / 300 ≈ 3.333 ms
```

这个数字是理解一切的起点。超过它，帧就掉了。

### 2.2 平均帧率是骗人的指标

假设某段时间平均 60 FPS。它可能是：

- **稳定型**：每帧都是 16.6 ms —— 流畅；
- **锯齿型**：一半帧 4 ms、一半帧 29 ms —— 平均也是 16.6 ms，但体感是**持续顿挫**。

**平均值丢失了分布形状**，而体感恰恰由分布决定。所以判断卡顿必须看**分位数与最大值**：p95 / p99 / Max，尤其是 **p99 与 Max**（俗称 low 帧）。

报表里那些 p50/p95/p99/Max/合规率（240Hz/120Hz/60Hz）之所以是正确方向，原因就在这里。

### 2.3 卡顿的成因是"单帧内工作堆叠"

DDNet 本身对硬件要求很低——它**不吃性能**。那卡顿从哪来？

答案不是"某段代码太慢"，而是**本该分散到多帧的工作，被挤进了同一帧**：

```
理想：
帧 N     [网络 0.3ms][UI 0.5ms][渲染 1.2ms]              合计 2.0ms  ✓
帧 N+1   [网络 0.3ms][UI 0.5ms][渲染 1.2ms]              合计 2.0ms  ✓

实际：
帧 N     [网络 0.3ms][UI 0.5ms][渲染 1.2ms]              合计 2.0ms  ✓
帧 N+1   [网络 0.3ms][UI 8.4ms][渲染 1.2ms][资源 6ms]    合计 15.9ms ✗ ← 爆发
```

**单帧爆发（spike）** 是这样定义的：一帧内**串行**执行的工作总量超过帧预算。

注意"串行"二字：这不是吞吐问题，是**调度问题**。同样的工作量摊到 5 帧就完全无感。

### 2.4 由此得到优化的唯一目标

> **不是让快的更快，而是把峰值摊平。**

这是本文最重要的一句话。一个 0.5ms 的函数优化到 0.4ms，对 p99 毫无帮助；而把一个 8ms 的同步加载拆成 8 帧各 1ms，p99 直接消失。

## 第三章 · 架构层面为什么会爆发

### 3.1 immediate mode UI 的固有代价

DDNet 的菜单是 **immediate mode**：`CMenus::OnRender()`（`menus.h:2281`）每帧从头描述整个界面。这意味着**每帧都要重新完成**：

- 布局计算（控件位置、尺寸、换行）
- 文本测量（`TextWidth` 调用）
- 可见性判定
- 内容构建

immediate mode 的好处是简单、无状态同步问题；代价是**成本随界面复杂度线性增长，且每帧固定发生**。

### 3.2 爆发的三个典型触发场景

| 场景 | 机制 | 为什么是爆发 |
| --- | --- | --- |
| **页面/页签切换** | 新页面全部 section 首次进入，测量 + 构建集中发生 | 一次性做完全部工作 |
| **列表滚动** | 视口内条目重建 + 文本测量 | 滚动越快、单位时间工作量越大 |
| **首次进入某功能** | 资源同步加载阻塞在主线程 | I/O 直接计入帧时间 |

### 3.3 一个可参照的范例：`CSectionLoader`

`src/game/client/components/section_loader.h:350-395` 的注释描述了一个**成熟的摊平设计**：

> **但它未必是通用最佳解**。四状态机是为"设置页 section"这种**固定、可枚举**的集合设计的；对**动态集合**（如搜索结果、实时列表）未必适用。它真正的价值在于两点：一是体现了**四条摊平原则**（预算、限量、优先级、去冗余），二是**与全局卡片理念契合**——内容块独立可声明，由统一容器调度，而非各自为政。

以下是它的四条原则（**原则可迁移，状态机不必照搬**）：

```
UNINITIALIZED  →  测量高度（成本可忽略）
MEASURING      →  可选渐进预热路径
COMPACT        →  渲染完整交互 section（每帧最多 1–2 个）
FULL           →  每帧渲染完整 UI；dirty 刷新配置哈希
```

它的四个关键设计：

1. **每帧时间预算**：`Begin(MainView, TimeBudgetMs = 5.0f)` —— 明确给出单帧上限，而不是"做完为止"；
2. **每帧限量推进**：`COMPACT` 状态每帧最多 1–2 个 section —— 直接限制单帧工作量；
3. **视口优先**：靠近滚动位置的 section 优先提升 —— 让用户看到的先就绪；
4. **四状态机**：避免重复测量，`dirty` 才刷新 —— 消除冗余计算。

**这四个手段就是"摊平峰值"的全部武器**：预算、限量、优先级、去冗余。

### 3.4 反面模式

- **同步加载**：在主线程等 I/O（皮肤、地图、预览、歌词）；
- **每帧全量重算**：无缓存、无 dirty 标记的布局与文本测量；
- **无预算循环**：`while(还有工作) 做完` —— 把可变工作量塞进固定时间槽；
- **隐式触发**：一个配置变更引发全页面重建。

## 第四章 · 测量：什么叫做"测准了"

### 4.1 测量有三个正交维度

任何采集设计都必须在三个维度上明确取舍，**任何一个含糊都会让数据不可用**：

| 维度 | 取值 | 影响 |
| --- | --- | --- |
| **覆盖率** | 全量 / 采样 | 决定能否算分布 |
| **条件性** | 无条件 / 条件触发 | 决定是否有偏 |
| **形态** | 横向汇总 / 纵向时间线 | 决定能否归因 |

### 4.2 条件采样的数学后果：分布被截断

这是本项目当前最严重的方法论问题。现有实现（`perf_logging.h:45`）：

```cpp
inline bool QmPerfShouldLogDuration(double DurationMs, bool Force = false)
{
	return Force || DurationMs >= QmPerfThresholdMs();   // 默认阈值 4ms
}
```

而 `perf/main_thread` 的全部 14 处、`perf/render` 的全部 5 处调用都传 `Force = false`——**全部走门控**。`client.cpp:3827` 的作者注释确认了后果：

> `// 且仍走 QmPerfLogStage 的阈值门控（正常帧不产生任何日志行）。`

**数学上发生了什么**：设真实帧时间分布为 `F(x)`，阈值 `T = 4ms`，则被记录的样本服从**截断分布**：

```
观测样本 ≈ { x | x ≥ T }
```

后果有三：

1. **分位数失效**：报表里的"p50"实际上是"慢样本的中位数"，它描述的是 `F` 在 `[T, ∞)` 上的中位数，**不是用户体感的中位数**；
2. **阈值敏感**：阈值可配置（`qm_perf_debug_threshold_ms`），**同一现象在不同阈值下得出不同结论，历史数据不可比**；
3. **最需要的数据最缺**：正常帧零记录，导致"基线"无从建立——没有基线，就无法判断某次尖峰是异常还是常态。

工具侧目前的做法是用 p5 去**事后反推**截断点（`perf/README.md` 的"采样偏差提示"）。这等于承认了源头的截断，却选择在末端打补丁。

### 4.3 正确的分工

条件采样**本身没有错**，错的是**用它去回答需要全量才能回答的问题**：

| 问题 | 需要的数据 | 能否条件采样 |
| --- | --- | --- |
| "p99 是多少？" "有没有变差？" | 全量帧时间 | **不能**——必须每帧一条 |
| "这次尖峰花在哪？" | 尖峰帧的明细 | **可以**——只记慢的完全合理 |
| "哪个子系统常出问题？" | 全量 + 归因标注 | 不能，需要频次统计 |

**结论**：全量层只存**极小字段**（帧时间 + 少量计数），代价恒定；明细层条件触发，用于归因。两层**分开存储、分开统计、分开展示**，绝不能混进同一张分位图。

### 4.4 体积的正确量级

当前日志的体积来自"每秒 1000 条明细"（`perf_logging.h:73` 的 `LIMIT = 1000`）：

```
1000 条/秒 × ~150 B ≈ 150 KB/s ≈ 540 MB/小时
```

这与"日志动辄几个 GB"吻合——**不是偶发，是设计的必然**。

正确的量级关系应该是：

> **日志体积 ∝ 卡顿次数**，而不是 ∝ 运行时长。

实现路径：平时只写全量帧行（每帧一条、字段极少），检测到尖峰时把**该窗口前后的环形缓冲整段倒出**。正常运行一小时的日志应在 MB 级。

### 4.5 另外两个容易忽略的坑

- **限额丢样本**：`LIMIT = 1000` 是"先记录再丢弃"，且丢弃恰好发生在最忙时刻——**卡顿最严重处证据最少**（生存偏差）；
- **明细密度与帧预算脱钩**：200 FPS 时理论每秒只有 200 帧，却允许 1000 条明细，说明单帧可写 5 条以上——**埋点密度必须与帧预算挂钩**。

## 第五章 · 归因：从"慢"到"为什么慢"

### 5.1 归因需要层级

一次有效的归因必须能沿这条链走下去：

```
帧 → 阶段 → 页面 → section → 卡片 → 控件
 │     │       │        │        │      └─ 哪个控件
 │     │       │        │        └─ 哪张卡片
 │     │       │        └─ 哪个区域
 │     │       └─ 哪个页面
 │     └─ 网络/更新/渲染/输入
 └─ 哪一帧
```

### 5.2 当前只覆盖了第一层

| 层级 | 锚点数 | 状态 |
| --- | --- | --- |
| 帧 → 阶段 | `perf/main_thread` 14 处、`perf/render` 5 处 | 有 |
| 页面 | `perf/menu`、`perf/client` | 部分 |
| **section** | **2 处**（`menus_settings.cpp:702`、`section_loader.cpp:333`） | **几乎空白** |
| 卡片 / 控件 | 无 | **缺失** |

报表自己也承认：`report.ts:1169` 写"尚不是 `CSectionLoader::Process()` 的完整生命周期视图"。

**后果**：报表能说"某个大阶段慢"，说不出"为什么慢"。而"为什么慢"才是行动依据。

### 5.3 横向汇总之外，还需要纵向时间线

横向汇总回答"哪个模块总耗时高"；但**单帧爆发是纵向现象**——它取决于**同一帧内哪些工作串行堆叠**。

因此必须具备**帧内时间线**：把一帧内部各阶段的**先后顺序与时长**完整呈现。只有看到这条线，才能回答"这 15ms 是怎么攒出来的"，进而判断该用哪种摊平手段。

## 第六章 · 优化：唯一目标是把峰值摊平

### 6.1 四种手段及其适用

| 手段 | 做什么 | 适用 | 代价 |
| --- | --- | --- | --- |
| **缓存** | 同一输入不重复计算 | 文本测量、布局、解析结果 | 内存、失效复杂度 |
| **分帧** | 把一次大工作拆到多帧 | 加载、构建、预热 | 就绪延迟、状态机复杂度 |
| **异步** | 移出主线程 | I/O、解析、压缩 | 线程安全、结果发布时机 |
| **去冗余** | 消除重复与无效计算 | 每帧重建、重复遍历 | 需要 dirty 机制 |

`CSectionLoader` 同时用了**分帧（每帧 1–2 个）+ 预算（5ms）+ 去冗余（dirty）+ 优先级（视口）**，是本项目最成熟的范例。

### 6.2 判断该不该优化

- **有明确归因证据**才动手。没有证据的"优化"是在赌；
- **先问"这是不是串行堆叠"**。若是，摊平；若不是，才考虑降低单项成本；
- **不牺牲正确性换取帧时间**。降画质、降采样、加限帧都是**掩盖**，不是优化；
- **每次优化必须能用同场景前后对比证明**。

### 6.3 不该做的事

- 不做"感觉更快了"的优化；
- 不为未复现的问题预先优化；
- 不用"加缓存"处理**生命周期问题**（会造成更隐蔽的 bug）。

## 第七章 · 画质稳定性：另一条路

### 7.1 它与帧时间无关

游戏内需要的不是"更快"，而是**不撕裂、不闪烁、输出稳定**。这属于**呈现/合成路径**问题，与 CPU 帧时间没有因果关系。

### 7.2 三种呈现模式的实际差异

必须把三种模式分开说清楚——它们的**副作用方向不同**：

| 模式 | 延迟 | 撕裂 |
| --- | --- | --- |
| **垂直同步**（`gfx_vsync`，上游描述 "may cause lag"） | **最高** | 无 |
| **无上限渲染对齐刷新率**（`qm_present_align`） | 比垂直同步**低** | **几乎必然** |
| **正常无上限**（两者都关） | 最低 | **很少甚至没有** |

最后一行是个反直觉但成立的事实：无上限时帧率极高，每帧都在极短的扫描间隙内完成，撕裂发生在扫描位置随机的相位上，视觉上不被察觉；而**一旦把呈现对齐到刷新率，撕裂位置被锁定在同一相位，反而固定可见**。

所以 `qm_present_align` **不是"低延迟版垂直同步"**——它牺牲的是**画面完整性**，不是延迟。把它默认打开，用户会看到撕裂却找不到原因（他明明没开 vsync），这正是"造成用户混乱"的机制。

### 7.3 由此得到的两条结论

1. **呈现模式必须由用户显式选择，不得强制默认开启**——三种模式各有副作用（高延迟 / 撕裂 / 帧率波动），没有一种对所有人都对。
2. **稳定性下降的根因不在这三个开关**。上游改动后出现的问题，应当定位**具体是哪段呈现路径发生了变化**（呈现间隔分布、丢帧计数、合成路径、驱动交互），而不是在三者之间试错。

### 7.4 需要什么证据

画质稳定性需要的是**逐帧的呈现证据**：呈现间隔分布、丢帧计数、合成路径变化、驱动交互。这与帧时间日志是**两套不同的观测**，不能互相替代。

## 第八章 · 当前基础设施与可采用的点

一个常见的误判是"性能优化要从零建设"。实际上这个项目**已经有一套相当完整的摊平基础设施**。真正的问题不是缺机制，而是**观测没有覆盖这些机制**。

### 8.1 全局帧预算仲裁器：`IFrameScheduler`

`src/game/client/frame_scheduler.h` 定义了一个统一的帧预算仲裁器：

```cpp
enum class EFrameSchedulerConsumer : int
{
	SettingsText = 0, IngameText = 1, Assets = 2,
	DemoBrowser = 3, IngameServerInfo = 4, SettingsTee = 5, Count
};

class IFrameScheduler : public IInterface
{
	virtual SSettingsAdaptiveBudgetOutput ComputeBudget(EFrameSchedulerConsumer Consumer,
	                                                    const SSettingsAdaptiveBudgetInput &Input) = 0;
	virtual void BeginFrame(int FrameId) = 0;
	virtual void EndFrame() = 0;
	virtual const SSettingsAdaptiveBudgetState &State(EFrameSchedulerConsumer Consumer) const = 0;
	virtual const SSettingsAdaptiveBudgetOutput &LastOutput(EFrameSchedulerConsumer Consumer) const = 0;
};
```

**六个消费者**各自独立取预算，由统一调度器仲裁。这与"全局卡片：每个页面只声明自己有哪些卡片"是**同一种思路**——工作不自己决定何时做，而是**向中央申请额度**。

### 8.2 十五种令牌：预算不是一个数字

`SSettingsAdaptiveBudgetOutput`（`settings_resource_jobs.h:251`）把预算细分为 15 类：

```
可见内容 / 预取 / 后台 / GPU 上传 / 资源上传
文本预构建 / 文本容器 / 字形栅格化 / 字形上传
段落布局 / 元数据布局 / 预览产物 / 纹理上传 / 卡片绘制 / Demo 元数据
```

外加两个决策元数据：

- `m_Mode`：预算模式（如 `IDLE`）
- `m_Reason`：本次预算的**原因**——即自适应决策是可解释的

**注意 `m_CardDrawTokens` 已经存在**：卡片渲染本就走在这套预算体系内。

### 8.3 自适应输入：预算依据实时状态

`SSettingsAdaptiveBudgetInput`（`settings_resource_jobs.h:205`）说明预算不是拍脑袋给的：

| 输入 | 含义 |
| --- | --- |
| `m_FrameMsAverage` / `m_FrameMsP95` | 实时帧时间（均值 + p95） |
| `m_TargetFrameMs = 8.333f` | 目标帧时间（120Hz） |
| `m_ScrollActive` | 是否正在滚动 |
| `m_TabSwitchFirstFrame` | 是否页签切换首帧 |
| `m_PostScrollRecoveryFrames` | 滚动后恢复帧数 |
| `m_VisibleWaiting` | 等待构建的可见项数 |
| `m_WindowActive` | 窗口是否激活 |
| `m_TextContainer*MsEwma` | **EWMA 成本估算**（平滑的历史成本） |

即形成闭环：**帧时间偏高 → 收紧预算；滚动中 → 压低非可见项；队列积压 → 适度放宽**。

### 8.4 其他已落地机制

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| `CSectionLoader` | `section_loader.h:375` | 四状态机 + 每帧 5ms 预算 + 每帧 1–2 个 + 视口优先 |
| `CSettingsWarmupScheduler` | `settings_warmup.h:117` | `WarmupFrame(BudgetMs)` 预热调度 |
| 文本容器池 | `menus.cpp` `m_MenuTextPool` | 容器复用，避免重复创建 |
| 令牌桶 | `menus.cpp` `m_CurrentSettingsUiFrameBudget` | 单帧额度控制 |
| 资源任务按预算消费 | `settings_resource_jobs.cpp` | `SettingsResourceConsumeGpuUpload` 等 |
| `settings_runtime_cache` | `settings_runtime_cache.h` | 运行时缓存 |
| `SQmMenuUiFramePerf` | `QmUiPerf.h:20` | 菜单帧指标 |

其中 `SQmMenuUiFramePerf` 采集的维度尤其有价值：

```cpp
float m_UiMs, m_LayoutMs, m_TextMs;                  // 分层耗时
int m_HeapAllocs;                                     // 堆分配次数
int m_CacheHits, m_CacheMisses, m_CacheEvictions;     // 缓存效率
int m_ItemsTotal, m_ItemsVisible, m_ItemsProcessed, m_ItemsSkipped;  // 处理量
```

**这比 `perf/*` 日志更贴近"为什么慢"**——它直接回答"是布局慢、文本慢，还是缓存没命中"。但目前**仅在 4 处调用**（`menus_browser.cpp` 2 处、`menus_demo.cpp` 1 处、`menus_settings.cpp` 1 处）。

### 8.5 关键判断：摊平机制已存在，观测没跟上

把机制与观测并排看：

| 能力 | 摊平机制 | 观测覆盖 |
| --- | --- | --- |
| 帧预算仲裁 | ✅ `IFrameScheduler` 6 消费者 | ❌ 无 `perf/*` 锚点 |
| 令牌细分 | ✅ 15 类 | ❌ 无 |
| 自适应输入 | ✅ 9 项实时输入 | ❌ 无 |
| 卡片绘制限流 | ✅ `m_CardDrawTokens` | ❌ 无 |
| 文本容器池 | ✅ | ❌ 无 |
| 菜单帧指标 | ✅ `SQmMenuUiFramePerf` | ⚠️ 仅 4 处调用 |
| section 级归因 | ✅ `CSectionLoader` | ❌ 仅 2 处 |

**结论**：不需要重新发明摊平机制，需要的是**让已有机制的决策过程可被观测**。当前预算给多了还是给少了、自适应是否真在起作用，**都没有数据**。这才是"分析先行"最该先补的地方。

### 8.6 可采用的点

对新功能（例如搜索页卡片化），可直接接入的既有能力：

1. **接入 `EFrameSchedulerConsumer`**：新增消费者或复用现有消费者，立即获得预算保护；
2. **使用 `m_CardDrawTokens`**：卡片绘制已有专用令牌，不必自建节流；
3. **复用令牌桶与容器池**：避免重复实现单帧额度与对象复用；
4. **上报 `SQmMenuUiFramePerf`**：新页面接入该指标即可与现有页面横向对比；
5. **参照 `CSectionLoader` 的原则而非状态机**：四状态机为固定可枚举集合设计，动态集合（搜索结果）未必适用——**接入帧调度器比照搬状态机更重要**。

### 8.7 需要补的观测

| 缺口 | 建议 |
| --- | --- |
| 预算决策无观测 | 记录每次 `ComputeBudget` 的 `Mode` / `Reason` 与关键令牌值 |
| 令牌耗尽无统计 | 统计各令牌的**耗尽次数**——即被预算卡住的频率 |
| `SQmMenuUiFramePerf` 覆盖太少 | 扩到全部主要页面 |
| 缓存效率无日志 | `CacheHits / Misses / Evictions` 接入统一日志 |

## 第九章 · 从 0 到 1：这套体系应该是什么样

如果今天从零设计，应该长成这样。

### 9.1 采集层

**三档并行，各自明确职责**：

| 档位 | 内容 | 触发 | 体积 |
| --- | --- | --- | --- |
| **帧行（全量）** | 每帧一条：帧时间、少量阶段计数 | 无条件 | 恒定（~200 条/秒 × 几十字节） |
| **明细行（条件）** | 超阈值阶段的完整字段 | 阈值触发 | ∝ 尖峰次数 |
| **快照（触发）** | 尖峰窗口前后的环形缓冲整段 | 检测到尖峰 | ∝ 卡顿次数 |

**硬性约束**：
- 明细密度与帧预算挂钩（单帧最多 N 条）；
- 不设"每秒 1000 条"这类与业务无关的限额；
- 全量档字段越少越好，宁可多一列维度也不要多一段文本。

### 9.2 归因层

- 锚点覆盖到**卡片/控件级**，且**每处锚点标注所属层级**；
- 提供**帧内时间线**视图，而不只是横向汇总；
- 后端（Metal/Vulkan）的计数器**接入同一时间轴**，否则前后端数据无法对齐。

### 9.3 分析层

- 报表**无外部依赖**（离线可开）；
- 时间序列**降采样**（保留峰谷形状），体积可控；
- **明确区分全量口径与条件采样口径**，不混图；
- 质量检查（缺字段、采样偏差、截断）**作为一等输出**，而不是脚注。

### 9.4 决策层

数据到行动之间需要一条明确规则：

```
报表指出尖峰帧 → 帧内时间线定位串行堆叠 → 选择摊平手段 → 同场景复测 → 对比
```

任何一环缺失，"优化"就退化为猜测。

## 第十章 · 判定标准

这套体系算不算成功，用四个问题检验：

1. **任意一份尖峰帧日志，能否给出具体到卡片/控件的归因？**
2. **p99 是否可信？** 即换一个采样阈值，结论是否不变？
3. **一小时常规运行的日志，是否在几十 MB 以内？报表是否离线可开且体积可控？**
4. **每次优化的收益，是否都能用同场景前后对比证明？**

四个问题全部能答"是"，说明体系成立。
