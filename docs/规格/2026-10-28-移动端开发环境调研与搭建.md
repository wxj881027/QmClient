# 移动端开发环境调研与搭建

## 目标与结论

要回答两件事：QmClient 手机版（Android 为主，iOS 附带）的开发环境该怎么搭；这台 Windows 机器能不能真的把调试包编出来。

结论：

1. **Android 可以在 Windows 上搭起来并编出 Debug APK。** JDK 21、Android SDK + NDK r27d、Rust 的 Android 目标、cargo-ndk 4.1.2、Gradle 8.13（wrapper 自动下载）。版本与 `.github/workflows/build.yml` 的 Android job 对齐，避免本地能过、CI 炸。
2. **iOS 不能在这台机器上构建，也无法在这里验证。** `scripts/ios/cmake_ios.sh` 的 `assert_ios_sdk_found` 在非 Darwin 主机直接报错退出，需要 macOS + Xcode。仓库没有 iOS 的 CI job。
3. **搭建中发现 4 个真实缺陷，其中 3 个会让 Android 构建直接失败。** 都不是环境问题，而是代码/脚本对「关闭录像」和「构建目录位置」的假设不成立，已按最小改动修复。

## 从零搭建

Windows 上用 MSYS2/Git Bash，不要用 WSL（脚本假定能看到 Windows 路径和 `.exe`）。

1. **JDK 21**：Gradle 8.13 + AGP 8.13 要求 JDK 17 以上，仓库按 21 配置。装完确认 `java -version` 是 21。
2. **Android SDK**：装 `cmdline-tools`，然后
   `sdkmanager --licenses`、`sdkmanager "platform-tools" "platforms;android-36" "build-tools;36.1.0" "ndk;27.3.13750724"`。NDK 版本必须与 CI 相同，否则 16 KB page size、编译器行为都可能对不上。
3. **Rust Android 目标**：`rustup target add aarch64-linux-android armv7-linux-androideabi i686-linux-android x86_64-linux-android`。
4. **cargo-ndk**：`cargo install cargo-ndk --version 4.1.2 --locked`（版本跟 CI 的 `CARGO_NDK_VERSION` 一致）。
5. **依赖**：`ddnet-libs` 子模块要就位。Windows 上没有预编译流程，必须用仓库自带的静态库；Android 侧 `ddnet-libs/<lib>/android/lib{arm,arm64,32,64}` 全是 `.a`。
6. **Vulkan 着色器工具**：`cmake/BuildVulkanShaders.cmake` 需要 `glslangValidator`，确保在 PATH 里。

## 一键环境脚本

`qmclient_scripts/android/android-env.sh` 负责导出这些变量（`JAVA_HOME`、`ANDROID_HOME`、`ANDROID_NDK_VERSION`、`ANDROID_NDK_HOME`、PATH、`BUILD_FLAGS`），并检查缺失的命令：

```bash
source qmclient_scripts/android/android-env.sh
bash qmclient_scripts/android/cmake_android.sh arm64 QmClient com.qmclient.client Debug tmp/android-build
```

脚本只导出变量、不改仓库状态；路径都能用 `QM_JAVA_HOME`、`QM_ANDROID_HOME`、`ANDROID_NDK_VERSION`、`BUILD_FLAGS` 覆盖。

## 构建与产物

单 ABI（arm64，真机最常用）：

```bash
source qmclient_scripts/android/android-env.sh
bash qmclient_scripts/android/cmake_android.sh arm64 QmClient com.qmclient.client Debug tmp/android-build
```

链路是：CMake 交叉编译（`scripts/android/cmake_android.sh` 的配置项由 `qmclient_scripts/android/cmake_android.sh` 传）→ Rust 侧由 `cargo ndk` 编 `libddnet_engine_shared.a` → 链接出 `libDDNet.so` 和 `libDDNet-Server.so` → 复制 Gradle 工程模板并改写包名/版本 → `./gradlew builddebug assembleDebug`。

产物：`<build>/build/outputs/apk/debug/QmClient-debug.apk`。装到手机：

```bash
adb install -r tmp/android-build/build/outputs/apk/debug/QmClient-debug.apk
```

## 调研发现

### 1. Windows：构建目录在仓库根目录下会让 clang 建不了临时文件

现象：Rust 侧编译 `ring` 的汇编时失败，`warning: ring@0.17.14: clang: error: unable to make temporary file: Permission denied`，整个构建停在第一个 Rust 产物上。

定位过程（用最小复现 crate 逐项排除）：

- 换 `TMP`/`TEMP`/`TMPDIR`（系统临时目录、`E:/tmp`、构建目录内）都无效。
- 手工在同一个目录、用同一条 clang 命令行编译同一个 `.S` 文件始终成功——只有经 cargo 构建脚本派生 clang 时才失败。
- 逐个对比两边的完整环境变量，只有 `PATH`、`CARGO_TARGET_DIR`、`OUT_DIR` 不同。
- 二分 `CARGO_TARGET_DIR` 位置：`<repo>/tmp/<x>` 成功，`<repo>/<x>` 失败，仓库外的目录成功。

缓解：**构建目录放在 `tmp/` 下**（`tmp/android-build`）。这条已写进环境脚本的提示。

根因尚未确认。工作区根目录上有一条 `Everyone` 的 deny 删除子项权限项，怀疑与 clang 用 delete-on-close 语义创建临时文件有关，但直接用手工 CreateFile 复现不出来，所以只能先记录现象和稳定规避方式，不当作已解决。

### 2. 关闭录像（`CONF_VIDEORECORDER`）时编译/链接不过

Android 和 iOS 都在构建脚本里传 `-DVIDEORECORDER=OFF`（没有对应平台的 FFmpeg 预编译库），而 `CMakeLists.txt` 明确写了「保证 CLIENT 在 FFMPEG_FOUND=OFF 时仍可编译（视频功能经 CONF_VIDEORECORDER 优雅降级）」。实际上有三处没做到：

1. `src/engine/client/client.h`：`VideoExportConcatPending()` / `VideoExportConcatFailed()` 标了 `override`，但基类 `src/engine/client.h` 里的同名虚函数在 `#if defined(CONF_VIDEORECORDER)` 内，关闭录像后没有基类成员可覆盖 → `only virtual member functions can be marked 'override'`。
2. `src/engine/client/client.cpp` 的 `Con_PosesVideo`：函数体整体没有守卫，调用 `StartVideo()`（同样只在录像开启时声明）→ `no member named 'StartVideo' in 'CClient'`。
3. `src/engine/shared/video.cpp`：`IVideo` 的静态成员定义被 `#if defined(CONF_VIDEORECORDER)` 包住，但 `IVideo` 的声明在 `src/engine/shared/video.h` 里是无条件的，HUD、聊天、Vulkan/线程后端都在读 `IVideo::Current()` → 链接期 `undefined symbol: IVideo::ms_pCurrentVideo`。

修法都是补守卫或补定义，不改变开启录像时的行为：前两处按 `CONF_VIDEORECORDER` 分别守卫声明和函数体（关闭时命令只打印一句提示），第三处把静态成员定义改成无条件（声明本来就在守卫外）。

### 3. Android 下没有 `open_link`

`src/base/system.h` 里 `open_link` 的声明在 `#if !defined(CONF_PLATFORM_ANDROID)` 内（Android 侧由系统浏览器接管，base 层不提供）。`src/game/client/QmUi/QmCardWikiPanel.cpp` 的 `NavigateTo` 无条件调用它 → `use of undeclared identifier 'open_link'`。

已加 Android 守卫并保留桌面行为。Android 上点击 wiki 卡片里的外部链接目前不会打开浏览器，这是平台能力缺口，不是这次要补的功能——留待产品决定（可以走 `IClient::ViewLink`，它内部在 Android/iOS 上用 `SDL_OpenURL`）。

### 4. Android 包装脚本用 `../` 定位仓库资源

`qmclient_scripts/android/cmake_android.sh` 打包阶段 `cd "$BUILD_FOLDER"` 之后用 `cp ../scripts/...`、`cp ../other/icons/...` 取模板和图标，隐含要求构建目录是仓库的**直接子目录**。把构建目录放到 `tmp/android-build` 后这一步报 `cp: cannot stat '../scripts/android/files/build.sh'`。

已改为先用 `SCRIPT_DIR` 算出 `REPO_ROOT`，再用绝对路径取资源。这样构建目录放在哪都能打包，和上面的规避方式配套。

### 5. 16 KB page size

原报告猜测「NDK 版本与 16 KB 页不匹配导致秒闪退」。当前树的事实：CI 与本地都用 NDK r27d，`ANDROID_SUPPORT_FLEXIBLE_PAGE_SIZES=ON` 在 `qmclient_scripts/android/cmake_android.sh` 里显式传了，NDK r27 的 `flags.cmake` 会为 arm64-v8a/x86_64 追加 `-Wl,-z,max-page-size=16384`，生成的 `build.ninja` 里确认有该链接参数。所以「因为没加 16 KB 参数而崩溃」这个假设在当前版本上不成立；真机闪退需要另找原因（见待办）。

### 6. Android 上配置保存必然失败（模拟存储不支持 flock）

现象：手机上退出客户端弹「Error saving settings」，而且每次启动都回到语言选择框——配置从来没落盘。模拟器上复现后查应用外部目录 `files/user/qmclient/`：只有 `config_save.lock`、`lifecycle_pending.marker`、各种 `*.tmp` 残留，没有 `settings.cfg`。

根因：`CConfigManager::Save()` 用 `CConfigSaveLock` 做跨实例互斥，POSIX 分支用 `flock(LOCK_EX|LOCK_NB)`。Android 的模拟存储（`/sdcard`，包含应用的 `files` 目录）**不实现 flock，直接返回 ENOSYS**。锁拿不到 → `Save()` 在第一步就返回 false → `client.cpp` 的退出路径把 `Error saving settings` 放进 `m_vQuittingWarnings` 弹出来，同时整份配置不写盘。

证据（NDK 编的小程序推到模拟器跑，同一路径逐项对比）：

```
/data/local/tmp/qm_lock_test3:                                  flock=0/0(ok)   fcntl=0/0(ok)
/sdcard/Android/data/com.qmclient.client/files/qm_lock_test3:   flock=-1/38(Function not implemented)  fcntl=0/0(ok)
```

修复：`src/engine/shared/config.cpp` 增加 `LockConfigFileExclusive()`——先试 `flock`，只有在返回"不支持"（ENOSYS / ENOTSUP / EOPNOTSUPP）时才退回 `fcntl(F_SETLK)`。真的被别的写入者持有时仍按失败处理，不放宽互斥语义。

验证：x86_64 Debug 包重装到模拟器，启动后 `files/user/qmclient/settings.cfg` 出现（2069 字节，含 `gfx_screen_width 2400`、`gfx_backend`、`qm_launch_count 1` 等运行期值），退出不再报保存失败；Windows 桌面 `game-client` 增量构建同时验证未被破坏。

## 模拟器实测

没有真机，用 AOSP `system-images;android-34;default;x86_64` 起模拟器验证运行时行为（WHPX 可用，`emulator -accel-check` 报 `WHPX(10.0.26300) is installed and usable`）：

- 手动铺 SDK 包：`sdkmanager --install emulator` 在本机会卡在 "Preparing Install" 不下载，所以直接按 `repository2-3.xml` 的 URL 用 curl 下 `emulator-windows_x64-*.zip` 和系统镜像 zip，再用 `tar -xf` 解到 `$ANDROID_HOME`。
- `avdmanager` 会因为缺 `emulator` 的 `package.xml` 拒绝建 AVD，因此手写 `~/.android/avd/qm34.avd/config.ini` + `qm34.ini` 绕过。
- 帧率：`-gpu swiftshader_indirect`（软件渲染）时 `EGL_emulation` 每帧 19–30 ms；换 `-gpu host` 后稳定 16.7 ms（≈60 fps，垂直同步上限）。所以低帧率来自模拟器软件渲染，不是客户端渲染路径。
- 启动时客户端会先尝试 Vulkan（`qm_graphics_mode` 默认 1 = 性能模式，Android 上解析成 Vulkan），模拟器缺一个 Vulkan 扩展导致创建实例失败，弹出红色 Warning 后回退 GLES/OpenGL。回退后的 backend 现在会随配置一起落盘，不会每次启动重复弹。
- Android 17（API 37）已实测：铺 `platforms;android-37.0` 与 `system-images;android-37.0;default;x86_64`，同一份 minSdk 24 / targetSdk 36 的 APK 正常安装启动，界面渲染正常，配置同样写入 `files/user/qmclient/settings.cfg`。
- 客户端日志在 logcat 里按 `com.qmclient.client/<子系统>` 打标签（`/config`、`/gfx`、`/vulkan`），排查手机端问题直接 `adb logcat | Select-String 'com.qmclient.client/'` 即可，不用另开日志文件。

## iOS 调研

- 入口：`scripts/ios/cmake_ios.sh <device|sim-arm64|sim-x86_64|sim> <App name> <Bundle id> <Debug|Release> <build folder>`，内部用 Xcode generator + `aarch64-apple-ios` 之类的 Rust 目标。
- 主机要求：macOS + Xcode + iOS SDK。`assert_ios_sdk_found` 在非 Darwin 上直接 `log_error` 退出，Windows 无解（也没有可替代的交叉工具链路径）。
- CMake 侧支持是完整的：`TARGET_OS=ios` 分支、`src/ios/ios_main.mm`、Metal/OpenGLES/UIKit 等框架、`iOS-Info.plist` 与 asset catalog、`ddnet-libs/<lib>/ios/*.xcframework` 的 slice 选择逻辑。
- SDL 不是问题：`cmake/FindSDL3.cmake` 开头就写明「所有客户端平台和 Android Java 绑定使用同一份 SDL 源码」，`find_package(SDL3)` 由它自己接住，FetchContent 编 SDL3 3.4.18，`ddnet-libs/sdl3/SDL3-3.4.18.tar.gz` 是离线源（SHA256 与 `URL_HASH` 一致）。所以 **macOS 和 iOS 都是源码编 SDL3，不依赖任何 SDL 预编译产物**。`ddnet-libs/sdl/*` 是迁移前的 SDL2 预编译库（含 `sdl/ios/libSDL2.xcframework`），现在只剩上游脚本 `scripts/android/cmake_android.sh`、`scripts/compile_libs/gen_libs.sh` 还引用，客户端构建路径不再用它——属于可以择机清掉的遗留。
- 其他预编译库：`curl`、`freetype`、`opus`(含 ogg/opusfile)、`png`、`sqlite3`、`wavpack` 有 iOS xcframework；`boringssl`、`webp`、`zlib`、`ffmpeg` **没有 iOS 目录**。iOS 脚本传的是 `-DPREFER_BUNDLED_LIBS=ON`，这几个库找不到 iOS 产物时会退回系统查找，能否成立必须在 macOS 上实测——这也是 iOS 从没被验证过的直接证据。
- 没有 iOS 的 CI job（只有 macOS dmg），所以 iOS 目前完全没有自动化验证。
- 顺带说明：`-DVIDEORECORDER=OFF` 同样会踩上面第 2 条的三个缺陷，修完之后 iOS 侧也才可能编过。

### 为什么 iOS 必须要 macOS

构建 iOS 目标需要 Xcode 工具链里的 `clang`（带 `-target arm64-apple-ios`）、`ld`、`actool`（编译 asset catalog）、`codesign` 和 iOS SDK，这些只有 Apple 在 macOS 上分发，许可条款也限定在 Apple 硬件上运行。具体到这套工程：

- `scripts/ios/cmake_ios.sh` 的 `assert_ios_sdk_found` 在非 Darwin 主机直接报错退出；
- 它用 CMake 的 Xcode generator，`build` 走 `xcodebuild` 语义；
- `IOS_USE_ASSET_CATALOG` 打开时调 `actool`，macOS 独占；
- 真机安装还要签名（免费 Apple ID 的 7 天描述文件，或者开发者账号）。

可行的替代只有「换一台 macOS」，形式可以挑：本地 Mac（Mac mini 最省）、macOS CI runner（GitHub Actions 的 `macos-*`，公开仓库不额外收费，仓库现在只是没配 iOS job）、或者云 Mac / SSH 到别人的 Mac。theos、cctools-port 这类 Linux/Windows 交叉工具链能勉强产出 Mach-O，但拿不到合法 iOS SDK、缺 `actool`/`codesign`，也无法安装到真机，只能算 hack，不能作为团队流程。

结论：Windows 上能做到「代码与 CMake 结构就位、改动不破坏其他平台」，但 iOS 的构建与验证必须有一台 macOS（实体机或 CI runner）。

### Android 17 工具链升级（AGP 9 / compileSdk 37）

改了三处，必须一起动：

- `scripts/android/files/build.gradle`：AGP `8.13.0` → `9.5.0`；`compileSdkVersion 36` → `compileSdk 37`；`targetSdkVersion 36` → `targetSdk 37`；`buildToolsVersion` `36.1.0` → `37.0.0`；同时把 AGP 9 里改名/移除的 DSL 一起换掉（`packagingOptions` → `packaging`、`lintOptions` → `lint`、`minSdkVersion` → `minSdk`，`namespace` 从 `defaultConfig` 提到 `android` 层级）。
- `scripts/android/files/gradle/wrapper/gradle-wrapper.properties`：Gradle `8.13` → `9.8.2`，`distributionSha256Sum` 同步。
- 本地 SDK：装 `platforms;android-37.0` 与 `build-tools;37.0.0`。

为什么不能只改一处：AGP 9 要求 Gradle 9.x，只升 AGP 会直接报 Gradle 版本不足；只改 `compileSdk` 则 AGP 8.13 不支持 37。

验证结果：`arm64`/`x86_64` Debug 走同一条脚本构建通过（`BUILD SUCCESSFUL`），APK 的 badging 变成 `platformBuildVersionName='17'`、`compileSdkVersion='37'`、`targetSdkVersion='37'`、`minSdkVersion='24'`；装进 API 37 模拟器能启动，日志显示走宿主 GPU 的 OpenGL ES 3.1（NVIDIA RTX 4060 Ti），主菜单正常渲染。

CI 影响：workflow 只显式装 `platforms;android-34` + `build-tools;34.0.0`，AGP 会在构建时自动补装缺失的 platform 与 build-tools（许可证已经由 `yes | sdkmanager --licenses` 接受），Gradle 由 wrapper 自己下载。Release/AAB 通道这次没有跑，升级后需要单独验一次。
