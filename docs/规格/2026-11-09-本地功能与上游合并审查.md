## CI 失败作业的根因与处理（2026-11-09）

PR #603 的失败作业逐个定位后都与本分支的净改动无关：出问题的测试文件与脚本在 `origin/master` 上就是当前写法（`qm_pose_map_test.cpp`、`qm_demo_display_test.cpp`、`QmCardWikiPanel.cpp`、`cmake_android.sh`、`check_jni_contract.py` 均不在 165 个提交的差异范围内）。第二轮修完后的结果是 `Android` 与 `Linux` 转绿。

- `Linux` 与 `check-clang-san` 原为同一项 `QmPoseMap.AbsolutePathIsUsedAsIs`：用例写死 `C:/maps/...`，而 `fs_is_relative_path` 在 POSIX 上只把 `/` 开头视为绝对路径，`C:/...` 于是被当成相对文件名、落进索引匹配后返回 `NOT_FOUND`。改为按平台取绝对路径（Windows 盘符 / POSIX 根目录），断言仍覆盖「绝对路径原样交给引擎」；修复后 `Linux` 通过。
- `check-clang-san` 在 `QmPoseMap` 通过后继续跑进了 `qm-ui-popup-tests`（`run_cxx_tests` 用 `&&` 串联，前一个二进制失败时它根本不会执行），由此暴露 `qm_wiki_panel_test::ResetState()` 的真实缺陷：`gs_WikiPopupContext = SWikiPopupContext{}` 是整块赋值，而 `CLineInput` 内部保存的是指向自身 `m_aBuffer` 的指针，赋值后它指向临时对象的栈缓冲区；下一个用例 `Clear()` 按 256 KiB 往失效栈地址写，ASan 报 `SEGV on unknown address 0x0`，栈回溯停在 `mem_zero` ← `CLineInput::Clear` ← `StartWikiPopup`。改为就地析构 + placement new 重建，指针重新绑回自己的缓冲区；独立探针确认整块赋值后指针不在自身缓冲区内、重建后在。
- `macOS` 的 `QmDemoDisplay.CaptureFreezesTheSameOptionsUsedForRendering` 触发 SIGTRAP（signal 5 / code 2）。2026-11-03 记的是「`m_Hud` 取值与源码矛盾」，这次直接崩在用例入口，两轮共同的前提是该用例读了没初始化的配置：`CConfig` 是纯聚合体、没有默认成员初值，`MakeConfig()` 里的 `CConfig Config;` 声明出的是一堆栈上残值，而 `Capture()` 会读从未赋值的 `m_QmVideoRenderDemoOnly`。读未初始化内存在 -O2 下是未定义行为，MSVC 碰巧读到 0 所以一直绿，arm64 的 clang 直接按 UB 收敛成陷阱。改为 `CConfig Config{}` 清零、并显式写出 `m_QmVideoRenderDemoOnly`，各平台取值确定。
- `Android` 在 `cmake_android.sh` 打包末尾失败：脚本把 `$SDL3_JAVA_DIR/../../../../..` 当作 SDL 源码根传给 `check_jni_contract.py`，但 ddnet-libs 的 SDL3 预编译包只带 `java/` 与库、不带 C 源码，读 `src/core/android/SDL_android.c` 直接抛 `FileNotFoundError`。改为先探测可用源码树（`_deps/sdl3-src` 或旧的相对位置），找不到就告警跳过，与同脚本中 ProGuard 规则缺失时只告警的处理一致；修复后 `Android` 通过。
- `Windows Portable` 第二轮改为在 `Setup sccache (Windows)` 步骤失败（`Unable to locate executable file: undefined`），属 CI 动作侧的环境问题，与本树代码无关，重跑该作业即可。
- `Windows`、`Analyze`、`check-style`、`check-clang-tidy`、`CodeQL` 均通过。
- 第二轮修完 `Android` 与 `Linux` 转绿；第三轮 `check-clang-san`、`Windows Portable` 也通过，只剩 `macOS` 一项，随后按未初始化读取修复。
