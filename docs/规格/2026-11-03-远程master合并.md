## macOS regex_error 的真实成因

前面两轮都在「把异常 catch 住」上打补丁（编译点 try/catch、包装器 `catch(...)`、`test()` 兜底），CI 仍然 abort。加 `backtrace` + `dladdr` 后才看清栈：

```
#4 __throw_regex_error<error_type=5>
#5 basic_regex::__parse_bracket_expression
#8 basic_regex::basic_regex(string const&, syntax_option_type)
#9 Regex::Regex(string const&, bool)
#10 QmKeywordReplyRules::CRuleSet::SetConfig(char const*)
```

栈帧完好地停在抛出点，说明 `_Unwind_RaiseException` 没找到任何 handler 就直接 terminate：既不是「catch 写错类型」，也不是「catch 被优化掉」，而是这条路径上 libc++ 的 unwind 没能回到调用者。同一份代码在 libstdc++ 下（WSL 单文件探针）能正常返回 `error()` 且 `test()` 为 false，所以问题不在包装器写法。

结论：不要依赖标准库的错误通道去处理「用户输入了非法正则」。现在 `Regex` 构造前先做一次低成本结构检查（转义、字符类、括号、`{n,m}` 量词闭合），明显非法的 pattern 直接判为不可用；`try/catch` 保留作为其余错误路径的兜底。关键词回复的合同不变：非法正则只表示不回复。
