# 性能采集体系审查

> 状态：**审查报告**（2026-09-19）
> 范围：`src/game/client/components/qmclient/perf_logging.h`、`perf_diagnostics.h`、`qmclient_scripts/perf/`、全部 `perf/*` 日志锚点及其历史文档。
> 结论：**问题不在"缺什么工具"，而在现有采集设计本身有三个互相矛盾的机制，共同造成了日志 GB 级、报表巨大、信噪比低。**

---

## 一、核心结论

现有体系不是"不够用"，而是**采样设计自相矛盾**：

| 机制 | 设计意图 | 实际后果 |
| --- | --- | --- |
| 阈值门控（`>= 4ms` 才记录） | 降噪，只留慢事件 | 分布被截断，正常帧零数据，**p50 不可计算** |
| 每秒 1000 条限额 | 防止爆量 | 忙时反而丢样本，**产生生存偏差**；且 1000/s 本身就是爆量 |
| 全量写入 + 无降采样 | 数据完整 | 日志 **~0.5 GB/小时**，报表全量数据点内嵌 |

三者叠加的结果：**记录下来的既不是全貌（门控截断），也不是精确的慢事件（限额丢弃），却是海量体积**。

---

## 二、机制层面的证据

### 2.1 阈值门控：正常帧完全没有数据

`perf_logging.h:45-48`：

```cpp
inline bool QmPerfShouldLogDuration(double DurationMs, bool Force = false)
{
	return Force || DurationMs >= QmPerfThresholdMs();
}
```

`QmPerfThresholdMs()` 返回 `QmStutterFrameBudgetMs()`，默认阈值 `qm_perf_debug_threshold_ms = 4`（ms）。

`QmPerfLogStage`（`perf_logging.h:357-378`）在入口处拦截：

```cpp
if(!QmPerfShouldLogDuration(DurationMs, Force))
    return;
```

**影响范围**：`perf/main_thread` 全部 14 处、`perf/render` 全部 5 处调用都传 `Force = false`，即**全部走门控**。

`client.cpp:3827` 的注释是作者自己写下的确认：

> `// 且仍走 QmPerfLogStage 的阈值门控（正常帧不产生任何日志行）。`

**为什么这是硬伤**：
- 若阶段数据只有 `>= 4ms` 的样本，那么报表里的 **p50 描述的是"慢样本的中位数"，不是真实中位数**；
- 阈值可调（`qm_perf_debug_threshold_ms`），意味着**同一份报表在不同阈值下不可比**；
- 这正是 `perf/README.md` 说"采样偏差提示（使用 p5 估计采样阈值）"的由来——工具在**事后猜**截断点，而不是从源头避免截断。

### 2.2 每秒 1000 条限额：忙时丢样本

`perf_logging.h:66-88`：

```cpp
class CQmPerfDetailBudget
{
	static constexpr int LIMIT = 1000;
	bool Allow(uint64_t Second)
	{
		if(m_Count < LIMIT) { ++m_Count; return true; }
		++m_Dropped; return false;
	}
	...
};
```

超限时丢弃并汇总为 `event=detail_sampling dropped=N`（`perf_logging.h:320/340`）。

**后果**：
- 丢弃发生在**最忙的时刻**——而那正是需要证据的时刻；
- 留存的样本偏向"低负载时段"，**卡顿最严重处反而证据最少**；
- 200 FPS 时理论上每秒只有 200 帧，却允许 1000 条明细 → 说明单帧可写 5 条以上明细，**埋点密度与帧预算脱钩**。

### 2.3 体积：1000 条/秒的来源

按每条明细约 150 字节（含 `perf/<system>`、`stage=`、`duration_ms=`、`frame=`、`session=`，以及可选的 `page=`/`tab=`）：

```
1000 条/秒 × 150 B ≈ 150 KB/s ≈ 540 MB/小时
```

这与"日志动辄几个 GB"完全吻合——**不是偶发，是设计的必然结果**。

## 三、报表侧的问题

### 3.1 "自包含 HTML"与实际不符

`report.ts:2` 注释写"生成自包含 ECharts HTML 报表"，但 `report.ts:654` 实际是：

```html
<script src="https://cdn.jsdelivr.net/npm/echarts@5.5.0/dist/echarts.min.js"></script>
```

**依赖 CDN 加载**。离线环境下打开是白屏。对"事后分析本地日志"这个场景，这是错的。

### 3.2 没有降采样

`qmclient_scripts/perf/lib/*.ts` 全量检索无 `downsample` / `decimate` / 降采样实现（仅 `stats.ts:2102` 的直方图分桶）。

因此**全部原始数据点直接写进图表的 series**，长日志必然生成巨大 HTML。

### 3.3 图表堆砌

`report.ts` 同时渲染 timeline / histogram / QQ / percentile / box / section 六类图表（`report.ts:1290-1435`）。在样本本身有偏（§2.1）的前提下，**图表越多，越容易让人从有偏数据里读出"结论"**。

### 3.4 工具自己承认的局限

- `report.ts:1169`：
  > "按 `perf/section` 事件聚合局部 section 耗时，当前数据仍来自设置页局部包装采样，**尚不是 `CSectionLoader::Process()` 的完整生命周期视图**。"
- `perf/README.md:65`：
  > "Section Top-10（基于当前 `perf/section` 样本，**仍受 C++ 覆盖面限制**）"

这两句把"覆盖不足"写成了**说明**，而不是**待修的缺陷**。读者会误以为这是正常状态。

## 四、锚点覆盖的结构性问题

| 事件 | 锚点数 | 问题 |
| --- | --- | --- |
| `perf/section` | **2**（`menus_settings.cpp:702`、`section_loader.cpp:333`） | 报表的核心归因维度几乎无数据；无法定位到卡片/控件 |
| `perf/render` | 5 | 只有整段耗时，无子阶段 |
| Vulkan 后端 | **0** | 非 Apple 平台无法与 Metal 对比 |
| Metal 后端 | 有 `m_MetalPerf*` 计数器（CommandBuffer/RenderEncoder/帧槽等待/命令处理）但**未接入 `perf/*`** | 后端数据与客户端数据不在同一时间轴 |

**结构性判断**：锚点集中在"客户端帧循环的大阶段"（`main_thread` 14 处），而**真正需要归因的细粒度层（页面 → section → 卡片 → 控件）几乎是空的**。这导致报表能说"某个大阶段慢"，说不出"为什么慢"。

## 五、一个具体的语义缺陷

`perf_logging.h:375-386`：

```cpp
inline void QmPerfLogStageForce(...)
{
	if(!QmPerfShouldLogDuration(DurationMs))   // ← 名为 Force，却在入口拦截
		return;
	...
	QmPerfLogPayloadForce(...);                 // payload 层才是 Force
}
```

**函数名暗示"强制记录"，但入口仍然被阈值门控拦掉**。只有 `DurationMs >= 阈值` 时才会走到下面的 Force 分支——语义与命名矛盾。

- 该函数**全仓无任何调用**（`grep QmPerfLogStageForce` 仅命中定义处）；
- **无测试覆盖**（`src/test/` 无 `LogStageForce` 相关断言）；
- 对照 `QmPerfShouldLogDuration` 有明确测试（`qmclient_monitoring_runtime_test.cpp:673-675`，验证 `3.999 → false`、`4.0 → true`）。

即：这套代码的**测试只覆盖了门控本身，没有覆盖"Force 应当绕过门控"这一被命名的语义**。

## 六、改进建议

按"先减小伤害、再修正采样、最后扩展"排序。

### 建议 1（最高优先）：把"全量帧数据"与"慢事件明细"分离

现状把两者混在同一套门控里。建议明确两层：

- **帧级（必全量）**：每帧一条，只记帧时间与阶段汇总，代价恒定（~200 FPS → 200 条/秒），用于算**可信的 p50/p99**；
- **明细级（门控 + 限额）**：只在超过阈值时记录，用于**尖峰归因**，明确标注"这是条件采样，不可用于分布统计"。

**验收**：报表能明确区分"全量口径的帧分布"与"条件采样的慢事件明细"，两者不混进同一张分位图。

### 建议 2：删掉每秒 1000 条的限额假设

1000/s 是"先记录再丢弃"的思路，本质是先制造垃圾再扔。改为：

- 按**帧**限流而非按秒：单帧最多写 N 条明细（如 8 条），超出合并为一条 `dropped=N`；
- 或改为**环形缓冲 + 触发式落盘**：平时不写盘，仅在检测到卡顿窗口时，把该窗口前后的缓冲**整段倒出**。

**验收**：日志体积与"卡顿次数"成正比，而不是与"运行时长"成正比。

### 建议 3：报表去掉 CDN 依赖，并做降采样

- ECharts 内联或本地提供，保证离线可开；
- 时间序列按像素宽度降采样（如 LTTB 算法），保留峰谷形状。

**验收**：一小时日志的报表体积可控（例如 < 5 MB），离线可打开。

### 建议 4：补齐"页面 → section → 卡片"的锚点

`perf/section` 从 2 处扩到卡片级，让报表能回答"哪个卡片慢"。这是把报表从"看整体"变成"能定位"的关键一步。

**注意**：此步必须与**建议 1/2 同时做**，否则锚点一多、限额一打，数据反而更容易被丢。

### 建议 5：修正 `QmPerfLogStageForce` 语义或删除

要么让 Force 真正绕过门控（`Force = true` 传给 `QmPerfShouldLogDuration`），要么直接删除这个无调用、无测试的死代码。**不要保留名不副实的函数**。

### 建议 6：把工具局限从"说明"提升为"缺陷"

`README.md` / 报表里那些"仍受限制""尚不是完整视图"的措辞，应改为明确的**已知缺陷 + 修复计划**，否则会被当成正常。

## 八、审查方法说明

本文所有结论均来自源码与脚本的静态阅读，证据形式为**文件路径 + 行号 + 代码片段**。未做运行时验证，因此：

- 体积估算（~540 MB/小时）是**基于限额与字段长度的推算**，非实测；
- "p50 不可计算"的结论基于门控逻辑，**若存在未检出的旁路全量写入，该结论需要修正**；
- 建议的优先级基于影响面判断，**未经过性能实验验证**。
