0. 结论摘要

不是「经常掉帧」。剔除 160 Hz 空闲节流的 6.25 ms 帧后，p50 1.27、p90 2.04、p99 4.54、p99.9 8.73 ms，>16 ms 只占 0.04%（16 帧），max 305 ms 出现在加载。需要处理的是冷切页、首次进页与加载阶段的一次性成本。

  1. 最值得借鉴的是 Godot 的「数据没变就复用」。服务器列表的行级插桩证明 2.63 ms 花在每帧重建可见索引，行绘制只有 0.12 ms；缓存后同场景 3.31 ms → 0.88–0.94 ms。主目录已迁移（94a8c3b269、cb64f3ce76）。
  2. 切页首帧靠「池寿命 + 首屏预建」解决，不是靠继续压稳态帧时间。现有 24 字形 / 1 ms 预热预算可以复用，只需把目标页首屏排到队首。
  3. MSDF 能降低字形层重建概率，不会自动消除容器与切页尖峰。固定 em 后中文不再按字号重复烘；但缺字生成、容器 miss、预案应用仍需单独处理。
  4. 多线程对平均 FPS 几乎无收益，对 p99.9 有。优先搬「整形/断行」这类无共享状态的活；字形光栅化受 FT_Face 线程安全约束，放在 MSDF 方案确定之后。
  5. 后处理链不值得为菜单性能建全套。只做能同时降 CPU 的两件：SDF 文字与已有的半分辨率 Dual Kawase 模糊。
  6. 1000 fps 与「绝不超预算」互相矛盾。单帧预算从 6.25 ms 缩到 1 ms 后，同样一份文本工作更容易越预算；600 fps 反而比 1000 fps 更稳。

2. 文本重建由什么触发

2.1 缓存键的粒度

菜单文本池键由 FormatMenuTextCacheKey（src/game/client/components/menus.cpp:487）生成：

scope:页:tab:子tab:文本:fs字号:al对齐:mw最大宽度:usUI缩放:hd:cm
段来源实际粒度
fsMenuTextBucket（menus.cpp:479）按 0.1 精度取整（×10）
mwUiTextWidthBucket（src/game/client/QmUi/UiCacheQuantization.h:27）4 px 一桶
usqm_ui_scale（menus.cpp:609）50–200 整数
hdScreenHiDPIScale()（menus.cpp:611）×100 取整

结论：普通布局抖动（差 1 px）不会直接换键，只有跨 4 px 桶、改 UI 缩放或字号档时才漂移。排查「键漂移」应优先看桶边界和 us/hd 变化，而不是假设每帧都在换键。

2.2 miss 来源

来源触发条件性质
首次进页池里没有这个键，一页几十到上百条一起 miss一次性，可用预算摊薄

按帧过期的寿命：160 Hz 是 3.75 s、600 Hz 是 1 s、1000 Hz 是 0.6 s——正好和「追求高帧率」互相打架。容量 4096 条（QmUiPerf.h:9）本身够用，不应再用帧数过期。

2.3 缓存淘汰

CMenus::TrimMenuTextPoolForInsert（menus.cpp:7396）每秒插入时遍历一次池：超过 600 帧未用即淘汰；容量满时淘汰 m_LastUsedFrame 最旧的条目。这是「按帧 + 容量」的混合策略，缺的是墙钟语义。

3. 现有预算与尖峰位置

3.1 已经存在的机制

  • 容器令牌与队列：DrainMenuTextContainerBuildRequests（menus.cpp:7506），超预算推迟到下一帧。
  • 字形预热已在同一份预算内：SSettingsTextPrewarmBudget{24, +1ms}（menus.cpp:8209）；每条待建文本先 Prepare 再 Advance，最后调用 TextRender()->QmPrewarmGlyph（menus.cpp:8253-8256，src/engine/client/text.cpp:1839）。
  • 预案分批合并：PrebuildSettingsTextPlanItem（menus.cpp:7761），不是一次性提交整页。

3.2 缺口：预热之外的同步 miss

CreateTextContainer 内部仍会走到 GetGlyph → RenderGlyph（src/engine/client/text.cpp:635）。一次 FreeType 光栅化 + 描边扩张 + 图集上传（text.cpp:713-732）全部发生在当前帧。可见的兜底行为是空白或旧容器，而不是掉帧；用户感知更接近「字晚一两帧出现」。

5. 多线程

对平均 FPS 几乎没收益，对 p99.9 有。把可并行的工作按性价比排序：

候选可行性主要成本
字形光栅化（FreeType）最值得，但 FT_Face 不是线程安全的每线程独立 face 或串行化；图集写入与 GPU 上传仍需回主线程
文本整形 / 断行纯 CPU、无共享状态，最好搬结果顺序与文本容器生命周期
服务器列表解析与过滤serverbrowser_update 实测 3.4 ms / 1379 条结果发布要带修订号，避免覆盖新列表
缩略图 / 皮肤解码已有异步链路继续复用，不为文本另起线程池

收益预期：p50 不动，p99.9 从 8.7 ms 掉到 2–3 ms，1% low 好看很多。成本是要处理 face 复用、容器加锁、结果顺序。它不是通往 1000 fps 的路，因为 1000 fps 的瓶颈在 present 和 4K 填充。

字形光栅化多线程应与 MSDF 方案一起决定：如果 MSDF 固定 em 且离线预烘，光栅化次数本身就大幅下降，再为旧路径建线程池会白做。

6. 后处理链与 shader 化 UI 材质

「效果能力落后」指没有后处理链（bloom、DOF、色调映射）、没有 shader 化的 UI 材质、没有 GPU 粒子。对这个客户端，实际影响只有三处：

  1. 菜单观感：毛玻璃、发光、动态渐变、圆角阴影——现在全靠 CPU 生成纹理硬扛，每加一个效果写一份 CPU 代码，CPU 峰值跟着涨。
  2. HUD 特效：击杀光效、连击发光这类。
  3. demo / 视频导出的画面处理。

值不值：不值得建全套。值得做的只有两件，因为它们同时能降 CPU：

  • SDF 文字（第 7 节）：描边/发光由 shader 免费获得。
  • 半分辨率背景模糊：Dual Kawase 已经存在（src/engine/client/graphics_threaded.cpp:1155），一张半分辨率纹理替代 CPU 逐像素，不需要重写。

全套后处理链、材质系统、GPU 粒子不建议为菜单性能而建；每加一个效果就多一份 CPU 峰值和跨后端（GL / Vulkan / Metal）维护成本。是否做某个单独效果，按「能不能同时降低 CPU 或替代现有 CPU 生成纹理」判断。

7. MSDF 烘焙

7.1 当前实现

每个字形按「填充位图 + 烘死的描边位图」两张图集存放：FT_Load_Glyph 光栅化后 QmGrowGlyphOutline 做 CPU 外扩，再分别 UploadGlyph(FONT_TEXTURE_FILL/OUTLINE)（src/engine/client/text.cpp:713-732）。四边形按「描边半径 + 1 px」扩边（text.cpp:683-687），图集单元的边距也只有这 1 px。

7.2 为什么「歪」

  1. 单元内边距不够。距离场要在字形边界外有 4–8 px 的渐变区间；现在只有 1 px，阈值一变就是锯齿/斜边。
  2. 把「填充 + 描边」当成一个形状求距离。单通道场只有一条等值线，无法同时表达填充边界和描边边界；采样阈值一变，描边会塌进填充里。
  3. 四边形按填充度量、图集块按描边扩边。两者基准不一致，每个字偏移量不同，整行文字就不齐。

商业引擎的解法是统一的：只对填充轮廓求距离，描边在 shader 里用第二个阈值画，不用第二张描边图集。

引擎做法
Unity TMPSDF 图集，_OutlineWidth / _FaceDilate / _GradientScale（padding）在材质里调，描边是一次采样换个阈值
Unreal SlateFSlateFontInfo::OutlineSettings，距离场字体 + 轮廓从同一个场里取
Godot 4msdfgen 生成 MSDF，outline_size 由 text.glsl 用 px_range 再做一次阈值

7.3 改造硬条件

  • 只烘填充轮廓；描边在 shader 里用第二个阈值画。
  • 固定 em（32 或 64 px）烘一次，缩放交给采样与 px_range。
  • padding ≥ 描边宽度 + 2 px。
  • 四边形按 padding 对称扩边，advance 仍用 FreeType 的度量。
  • 图标字体保留现有位图路径，不与正文混用。

7.4 对首帧尖峰的判断

会降低字形层的重建概率，但不会自动消除切页尖峰。

  • 当前字形按「字符 + 像素字号」各存一份，菜单里正文/小字/标题几个档位会重复占图集；固定 em 后一个字符只烘一次，图集占用与 GlyphAtlasRevision 作废概率明显下降。
  • 但文本容器 miss、键漂移、预案结果应用都不受 MSDF 影响；切页首帧仍要靠预建解决。
  • 如果缺字在运行期才生成，MSDF 只是把「普通位图光栅化」换成「距离场生成」，未必更快；需要把生成放进现有预算或离线预烘。
  • 中文覆盖面是主要风险：固定 em 减少重复，不等于覆盖所有字符；必须有缺字回退路径和覆盖率统计。

7.5 验证方式

同一冷切页、同一字号档位，对比 glyph_rasterize_ms、图集页数/占用、容器创建次数、首屏文字就绪延迟。不能只用稳态 FPS 或微基准下结论。

8. 文本池过期与缓存策略

优先级最高、成本最低的改动：

  1. 600 帧 → 10 s 墙钟 + 容量 LRU。语言、字体、图集版本变化仍保留强制失效。
  2. 切页首屏预热。把目标页首屏条目排到预案队首，复用现有 24 字形 / 1 ms 预算；扩展 PrebuildSettingsTextPlanItem，不新建队列。
  3. 把同步 miss 也纳入预算。预热之外若仍触发 RenderGlyph，至少保证一帧只做 N 个，并保留空白/旧容器兜底。

验收指标从「帧时间」改为「点击到首屏文字出现」的延迟，配合容器创建次数与 settings_text_miss 日志。预期：切走再切回从「必然重建」变成「大概率命中」；首次进页仍需一次预算内摊薄。

9. 实施顺序

  1. 文本池寿命改时间 + LRU；目标页首屏排队预热。
  2. 用现有日志把冷切页拆成字形/容器/预案三段，确认尖峰占比。
  3. 按实测决定是否启动 MSDF 试验；先离线烘一份固定 em 的子集，验证清晰度与图集占用，再谈全量。
  4. 多线程只搬「整形/断行」这类无共享状态的活；字形光栅化在 MSDF 方案确定后再评估。
  5. 后处理只做已被证明能替代 CPU 路径的单点效果。

10. 验证方法

10.1 场景规格

  • 3840×2160 窗口化、关 vsync、Release 构建、关闭一切调试日志（qm_perf_debug 0）。
  • 同一场景：100 行服务器列表（可见约 23 行），每行 4 个文本列（名称/地图/玩家/延迟）+ 一张静态背景图，无动画、鼠标不动。
  • 预热 5 s 后测 10 s，跑 3 次取中位；报告 p50 / p90 / p99 / p99.9 + 超过 6.25 ms 的帧比例，并单列加载帧（> 100 ms 不参与稳态分位）。
  • 再做两个对照把成本拆开：①只画文本不画背景 ②只画四边形不画文本。
  • 口径对齐：我们这边用 loop_total/frame_batch，Godot 在 _process 里用 Time.get_ticks_usec() 记帧间隔写 CSV；两边都排除加载帧。

10.2 客户端入口

使用客户端自带的 benchmark_quit <秒> <文件>（src/engine/client/client.cpp:7917），只写 Frametime N us，不依赖 qm_perf_debug。两个坑：菜单空闲节流会把帧率压到屏幕刷新率；窗口失焦会把更新限到 cl_refresh_rate_inactive，测容量时都要显式关掉。

10.3 Godot 侧

Control 树 + 每格一个 Label（不要用一个多行 Label，否则批处理行为对不上）+ TextureRect 背景，--resolution 3840x2160，启动参数关 vsync。100 MB 免安装包，半小时能出数。Unity 要装 Hub + 许可证，Unreal 50 GB 起，这两家先不做。

11. 未决问题

  • 文本池改为时间过期后，长时间挂机再切回的命中率与内存上限取多少。
  • MSDF 固定 em 选 32 还是 64；中文首屏的字形预算是否需要单独一档。
  • 图集耗尽时的策略：扩容、淘汰、还是回退位图；当前只有 UNSUPPORTED 返回。
  • 多线程字形生成是否需要每线程 FreeType library，还是每线程 face 共享 library。
  • 切页「首屏就绪」的可观测点放在容器有效、首个非空文本帧，还是页面动画结束。
  • 预案结果一次性应用是否需要按时间切片；现有皮肤列表已按条数分批，文本预案仍需独立计时。
