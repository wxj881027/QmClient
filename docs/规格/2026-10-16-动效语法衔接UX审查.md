## 1. 总览：三个设计世界

QmUi 目前有 197 个文件、约 4.7 万行，已经不是 DDNet 菜单的一层皮肤，而是一套独立的应用界面：常驻左侧图标栏、顶部社区/页签栏、中央内容区、右侧好友面板、底部状态/筛选区。设置页再叠卡片甲板，搜索页叠全局检索，HUD 再叠灵动岛。玩家可以在「找服 → 看朋友 → 进服 → 局内 HUD」这条主链上不迷路。

但它同时存在三个设计世界：

1. **玻璃卡片世界**（设置页、二级面板、弹窗、输入框）：半透明表面、模糊、圆角、白色透明度层级、弹簧与 token，成熟度最高。
2. **DDNet 表格世界**（服务器列表、语言/国旗列表、部分历史页）：行高紧凑、列头排序、1 单位分隔、裸色与固定字号，仍带着上游表格的 DNA。
3. **HUD 世界**（灵动岛、通知、计分板、状态条）：尺寸更小、节奏更快，和菜单不是同一套尺度。

三个世界各自都成立，拼在一起时层级会打架：设置页卡片标题是 18，页面标题是 16；服务器列表选中态是 0.5 白，国旗选择器叠成约 0.57；好友行用整块底色同时表达「好友/战队/离线/AFK/悬停/同服」六种状态。玩家不会说“token 不一致”，只会说“这一块比那一块亮”“这个列表点起来有点糙”。

**做得好的地方（不要回潮）：**

- 材质语言统一：`SURFACE_GLASS` / `SURFACE_ELEVATED` / `BORDER_SUBTLE` 在卡片、弹窗、输入框上基本一致，模糊只在需要的地方出现。
- 设置卡片甲板：整 Deck 共享一条入场轨道、固定副标题高度、拖拽换列、折叠高度过渡；拖动时其余卡片按目标 Y 让位（0.18s，1 档 0.12s），是“大地面稳定、小元素运动”的正确做法。
- 弹窗的抽屉语言：锚点弹层从锚点边展开，模态保持内容尺寸只做 8px 上浮；开关共用一条 ALPHA 轨道，中途反转能带速度续接。
- 输入与 IME：光标 80ms 短补间、逐字回弹只改顶点、不参与排版；这是很多商业客户端都做不到的细节。
- 响应式下限：`QmBrowserStatusLayout` 在 430/550 宽度切换布局，窄窗把标签堆到输入框上方，不是简单截断。
- 工程底座：动效 token、`qm_ui_motion_level` 三档、Google Benchmark、行为测试库存，让后续修改有地方落。

**结构性的弱项：**

- **表格层没有跟上卡片层。** 浏览器是使用频率最高的页面，但它的排序、筛选、换列、行悬停仍是硬切；同一屏里按钮有 120ms 淡入，列表行却是瞬变。
- **状态表达依赖颜色。** 好友角色、AFK、同服、选中、悬停都挤在背景色的 alpha 上；排序方向靠白/黄区分。色弱玩家和灰度截图下信息会丢失。
- **字号是“很多正确的小数字”，不是一套阶跃。** 仅底部筛选区就出现 10/11/12/13/14 五档；`TITLE=18` 比页面标题 `HEADLINE_LG=16` 还大。
- **交互模型仍以鼠标为主。** 全局 Tab 链不存在，键盘焦点环只在拆分按钮上绘制；这不是“小细节”，但它决定了这套 UI 能否被称为完整。
- **动效词汇很富，产品用法很窄。** 引擎有队列、优先级、等待组、自定义曲线，生产代码几乎只用 `REPLACE`/`MERGE_TARGET` 和 ease-out。

| 维度 | 分数（设计审查，不是指标） | 判断 |
| --- | --- | --- |
| 视觉语言 | 8.0 / 10 | 玻璃材质与卡片语言已经成立；表格层拉低一致性 |
| 信息架构 | 7.0 / 10 | 主链清楚；五个常驻区域偏多，找服→连接路径偏长 |
| 动效执行 | 7.5 / 10 | 弹窗/卡片/输入很好，卡片拖动有让位；列表与排序仍是断点 |
| 交互细节 | 6.5 / 10 | 空态、悬停、焦点、热区仍有一批“差半拍” |
| 键盘与无障碍 | 5.0 / 10 | 焦点不可见、无全局 Tab 链、状态靠颜色 |
| 工程与一致性 | 7.5 / 10 | token/测试/基准齐全；颜色与动效审计尚未闭环 |
| **总览** | **7.2 / 10** | 有辨识度的客户端 UI，正在从“皮肤”长成“系统” |

看完第二批界面后，总分不变，但归因更清楚：单页大多能到 7–8 分，跨页一致性只有 5–6 分。问题不是“没有设计”，而是同一件事被每个页面重新实现了一遍：

| 语义 | 现在出现过的形态 | 玩家要猜什么 |
| --- | --- | --- |
| 布尔开关 | HUD 页 switch、红色药丸、统计页普通按钮、回放页红色 switch | 哪个是开关、哪个是筛选、哪个是动作 |
| 页面标题 | 设置 16、统计 24、HUD/Tee 只有页签或“设置”、搜索/回放没有标题 | 现在在哪个层级 |
| 搜索位置 | 皮肤搜索在卡片顶部、回放在底栏、服务器在底栏、功能搜索居中 | 搜索只作用于当前卡片还是整页 |
| 主操作 | 启动页五个等宽按钮；服务器连接绿色、刷新深色；设置页大量同级按钮 | 第一眼该点哪里 |

这四行不是审美问题，是组件缺失。下一轮最该做的不是“再设计一个更漂亮的页面”，而是把 `Switch`/`Choice`/`Dropdown`/`Button`/`PageHeader` 抽出来，让新页面没有机会再写错。

## 2. 动效引擎：A- 的核心，B 的接线

**它是什么。** 底层是 `CQmAnimationBackend`（879 行 `.cpp` + 260 行 `.h`），上面是 `CUiRuntimeV2` 的每帧推进、`CQmTree` 的 presence/layout 解析、`UiTokens.h` 的语义 token，以及一层 `ResolveUiAnim*` 便捷入口。生产代码有 370 处 `EUiAnimProperty` 引用、74 处 `CUiV2AnimationRuntime` 引用；浏览器之外的界面基本都已接入。

**核心素质（在游戏 UI 里属于少见）：**

1. **解析解弹簧**：欠阻尼、临界、过阻尼三支都有闭式解，按真实 `Dt` 推进，帧率无关、无条件稳定；不是固定子步欧拉。
2. **参数化弹簧**：`FromResponse(ResponseSec, DampingRatio)` 把设计师的“响应时间/阻尼比”翻译成 `k/c`，和积分器闭合。
3. **打断语义完整**：`REPLACE`/`MERGE_TARGET` 统一转弹簧接管，继承当前值与速度；tween 被打断时按时长映射成弹簧，不会从当前值重放曲线。
4. **感知属性守卫与差异化休眠**：ALPHA/COLOR 强制临界阻尼，避免过冲被 clamp 截断造成曝光停滞；空间 0.25px/0.5px·s⁻¹、ALPHA 0.002、COLOR 0.001，和弹簧显式阈值取更紧者。
5. **可测**：`QmAnimCoreTest` / `QmAnimSpringTest` / `QmAnimTreeTest` / 组件行为测试，加上 `qm_anim_benchmark.cpp` 的稳态、活跃、presence、切换、缓存五条路径，测试与基准不是摆设。

**但复杂度花在了“控制面”，不是“编排面”：**

| 能力 | 现状 | 评价 |
| --- | --- | --- |
| 队列 `QUEUE` | 生产引用 1 处（枚举定义本身），无实际使用 | 过度建设 |
| 优先级 `KEEP_HIGHER_PRIORITY` | 生产引用 1 处（枚举定义本身） | 过度建设 |
| 等待组 `AwaitTracks` / `PollGroupCompletedEvent` | 只有单元测试调用，生产零调用 | 建好没接线 |
| 自定义曲线 `RegisterCustomEasing` | 4 处引用，主要是测试/定义 | 低频能力 |
| `MERGE_TARGET` | 18 处，弹窗/工具提示/导航在用 | 真正的核心 |
| 卡片甲板 reflow | 拖动时整组让位，受影响卡片各自补间到目标 Y：0.18s（1 档 0.12s）、`EASE_OUT_QUART`，`qm_ui_card_reflow_animations` 可关；非拖动的折叠/可见性变化的位置重排走 snap（高度本身另有高度动画） | 局部让位已落地 |
| 通用/逐卡 FLIP / 共享元素 / 顺序编排 | `ResolveLayoutTransition` + `CARD_REORDER` 仅测试调用，生产零接线；没有跨容器的 FLIP、共享元素和顺序编排（presence 的 enter/exit 已有，`QmTree.cpp:82`） | 通用能力缺口 |

这形成一个更具体的判断：**引擎最擅长“一个值怎么优雅地到达另一个值”，也已经在卡片甲板上做出整体让位；但它还没有“一串东西按什么顺序、从哪里长出来”的通用编排。** 卡片甲板是局部实现：拖动时其余卡追目标 Y，所有卡同时开始，没有跨容器的 enter/exit 重排、共享元素或 FLIP 编排；服务器列表排序/筛选仍是替换，页面切换没有共享元素，通知没有排队编排。继续加曲线预设的收益已经很低，补通用 FLIP/编排的收益很高。

卡片甲板的 reflow 在 `SettingsCardDeck.cpp:671-722`；拖动时几何变化不走 snap 分支（`SettingsCardDeckShouldSnapReflow` 在 drag active 时返回 false，`SettingsCardDeckLogic.cpp:365-368`），其余卡按目标 Y 续接；非拖动的折叠/可见性变化的位置重排才 snap（高度本身另有高度动画）。归档统一方案已把 deck 重排记为“整体过渡，无逐卡 FLIP”，本轮沿用这个区分。`CARD_REORDER`（`UiTokens.h:302`）与 `ResolveLayoutTransition`（`QmTree.cpp:31`）只在 `QmAnimTreeTest.cpp`、`QmAnimSpringTest.cpp` 等测试/基准里出现，生产零调用——所以“卡片有整体让位”和“逐卡 FLIP 未接线”是两件事，不能合并成一句“没有 FLIP”。同一时长/目标 Y 续接思路也出现在搜索页输入卡的居中↔置顶过渡（`menus_qmclient_search.cpp:315`）；两处都是逐属性 tween，仍不是通用 FLIP。

## 3. 仍有效的缺口

### P1 · 服务器浏览器全界面零动效轨道——排序/筛选是最大的因果断点

**证据**：`menus_browser.cpp` 对 `QmAnimationRuntime / RequestAnimation / EUiAnimProperty / SUiSpringConfig / ResolveUiAnimValue` 的引用计数为 **0**；卡片甲板已有 reflow，但浏览器一行都没接。点击列头排序、修改筛选条件后，行内容逐帧硬跳到新位置；拖拽换列提交后被换位的列同样硬切。

**问题本质**：行不是「移动到新位置」而是「被替换」——正是 onetake 判定的 slideshow 特征。浏览器是使用频率最高的界面，排序/筛选是其最高频状态转换，此断点的体感权重最大。

**建议**：批二 FLIP 基建落地时，首个应用场景改为服务器列表排序/筛选（皮肤队列仍用落点线/幽灵，`QmCardCatalogTee.cpp:2423-2434`、`:2505-2524`，不占首个场景），复用 `CARD_REORDER` 弹簧（token 已有，生产尚未接线）；拖拽换列提交后同用 FLIP 让被让位的列滑入新槽位。节奏红线：排序用单弹簧、不做逐行 stagger（stagger 属入场语言）、落定后完全静止；表头与列宽（大 ground）不得参与动画。

### P2 · 灵动岛连接质量图标状态硬切换

**证据**：`hud.cpp:5052/5082` 直接以当前档位的纯函数结果绘制图标与颜色，HIGH→MEDIUM→LOW 变化时字形与颜色单帧硬换。

**建议**：档位切换时旧/新字形交叉淡出约 0.16s、颜色同步插值；LOW 持续期间可加低频呼吸（报警语义，动效等级门控，恢复 HIGH 即静止）。实现上每岛一组 ALPHA 轨道或对档位序号做一条 tween；双份渲染路径同口径。此项同时收敛 Gemini 维度四「网络健康感知」的警示诉求。

### P3 · 地图预览二级面板的来源线索 + 骨架屏流光

**证据**：预览面板走 `ResolveSettingsSecondaryPanelRect` 居中 + `SecondaryPanelProperties()`（fade + 8px 上浮），触发点在列表行内的预览图标——效果（居中大面板）与原因（哪一行）视觉断连；首开还有 100–300ms 同步解码空窗。

**建议**：不做锚定展开（与字体商店既定模式冲突），改为触发图标短暂高亮/选中态让视线可回溯；同时给占位区加自左向右的浅色渐变光带（shimmer），加载完成即静止。两件事共享“预览面板打开体验”一个场景，合并实施。

## 5. 两个需要展开的决策

### 5.1 局内聊天现代化：做，中优先级

只做两件，不扩成聊天皮肤：

- `:` 表情面板：键入 `:` 后 2–3 个字符过滤，`Enter` 插入、`Esc` 关闭；复用现有 emoticon 资源，不新增一套表情资产。全程可键盘完成，不依赖鼠标。
- @提及高亮：仅在名字前缀匹配时触发；整行底色呼吸 2 个周期（约 0.9s/周期）后落定，不做永久闪烁。提及是注意力提示，不是装饰。

它属于局内输入链，和菜单的 `QmCardCatalog`、D9 焦点环不是同一套代码；不要为了“统一”把它塞进设置卡片。

### 5.2 按键绑定冲突：并入 bind 项目，不做独立页

现有 Bind 一览卡已经把 `key → command` 摊平（`QmCardCatalogBind.cpp:481-498`），动作分组在 `bind_overview.h:33-90`，但它只回答“现在绑了什么”，不回答“这次赋值会覆盖谁”。DDNet 的模型是 `key + modifier → 一条命令`，真正的冲突发生在**赋值瞬间**；脱离编辑器的“冲突列表”没有稳定数据源，容易做成一张无用的键盘占位图。

如果 bind 项目启动，按三层做，顺序不要反：

1. **赋值提示（最小）**：捕获到已占用键时，在按键框下方显示 `W 已用于 跳跃（+jump）；改为 左移（+left）？[覆盖] [取消]`。用文字说清旧/新动作，不要只把键染红；这是唯一能独立先做的一层。
2. **键盘占用图（可视）**：全键盘布局，按动作组着色（移动/武器/聊天/其他），顶部切换 `无 / Shift / Ctrl / Alt`；悬停显示命令，空键降透明度。它回答“哪些键被用了”，不制造“重复命令=冲突”的假警报——同一命令绑多个键是玩家有意为之。可以直接长在现有 Bind 一览卡上，不必新页面。
3. **蓝图 / cfg 编辑器（结构）**：键事件 → 条件 → 命令链的节点图，边表示顺序与同时按下；同一键在同一修饰键下多条出边、或命令链里同时出现互斥动作（如 `+left` 与 `+right`）时才标冲突；右侧 cfg 源码带语法高亮、解析错误定位、`bind`/`unbind` 预览。这是 bind 项目的核心，不是本轮 UI/UX 的附属页。

“预设码一键分享”不做；bind 项目需要交换时，导出/导入 cfg 文本即可。

**设计语法：**

- 节奏标尺已建制：竞技快击 ≤80ms、交互级 120–180ms、通告级「0.20s 入场 → 2.5s 静止 → 0.10s 收折」、wordRise 列表入场（14ms cascading、28 行封顶）。

**沿用原则：**

- 尺寸变化一律「满幅布局 + 揭示裁剪」，禁止内容跟随临时矩形重排。
