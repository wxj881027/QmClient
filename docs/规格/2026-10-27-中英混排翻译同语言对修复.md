# 中英混排翻译的同语言对与错误文案直出修复

状态：源码修复与本地验证完成（相关过滤测试、quick gate、game-client 与 testrunner 构建）；真实客户端界面验收未执行。

## 现象

接收翻译目标为中文时，中英混排消息（例："快说bye"）的消息下方显示大写英文 `PLEASE SELECT TWO DISTINCT LANGUAGES`，而不是译文。该文案是服务返回的错误说明，被当作成功译文渲染到聊天。

## 根因

三处缺陷叠加，缺一不会表现为该现象：

1. MyMemory 不支持源语言自动检测。旧的 `ResolveSource` 只按"出现过汉字"判定来源，任何含汉字的消息都会被推断为 `zh-CN`；目标 `zh` 在 MyMemory 编码后同样为 `zh-CN`，于是请求变成 `langpair=zh-CN|zh-CN`。
2. 服务对相同语言对不返回 HTTP 错误，而是 HTTP 200 且 `responseData.translatedText` 写入 `PLEASE SELECT TWO DISTINCT LANGUAGES`，同时 `responseStatus` 是**字符串** `"403"`。
3. `ParseResponseJson` 只接受整数或浮点状态码，字符串状态被忽略后 `Status` 保持 200，错误说明因此走了成功分支。这违背 2026-10-08 已定的"聊天失败仅显示本地化短提示，不展示供应商原始响应"。

## 修复

- `translate_detect` 新增 `SelectExplicitSourceLanguage`：按字形数量取多数候选作来源，跳过与目标同语言的候选；只剩目标语言字形时返回 `nullptr`。中文变体仍按不同语言处理，简体转繁体等转换请求保持有效；与目标同数时沿用既有优先级（假名 > 谚文 > 西里尔 > 汉字 > 拉丁）。仅当文本不存在字符形统计（空、纯数字、纯符号）时不进入该路径。
- MyMemory 改用该函数选源；用户显式指定的来源与目标相同时同样视为无需请求。没有可用来源时以 `ALREADY_TARGET_LANGUAGE` 结束，不发送请求。
- 解析接受字符串状态码；`PLEASE SELECT TWO DISTINCT LANGUAGES` 归类为 `SERVICE_NOTICE`，由调用方显示本地化文案。
- 新增本地化文案 `This text is already in the target language.`；`data/languages/*.txt` 本轮未生成，非英语界面暂回退英文。

## 真实服务对照（2026-10-27 实测）

| 请求 | 返回 |
| ---- | ---- |
| `q=快说bye&langpair=zh-CN\|zh-CN` | HTTP 200，`translatedText=PLEASE SELECT TWO DISTINCT LANGUAGES`，`responseStatus="403"` |
| `q=快说bye&langpair=en\|zh-CN` | `快说再见` |
| `q=我快说bye&langpair=en\|zh-CN` | `我快说再见`（中文部分保留） |
| `q=gg 好厉害&langpair=en\|zh-CN` | `gg 好厉害`（无中文可译时原样返回） |

FTAPI 当前返回 PythonAnywhere 的 "Coming Soon" 占位页，`qmclient.icu/api/v1/translate` 返回 Obsidian 发布页，两个链路本轮无法实测，不属于本次修复范围。
