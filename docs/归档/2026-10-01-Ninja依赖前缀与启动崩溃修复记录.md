# Ninja 依赖前缀与启动崩溃修复记录

## 核对结果与根因边界

交接中提到 `build.ninja` 没有 `msvc_deps_prefix`。实际该变量位于被它 include 的 `CMakeFiles/rules.ninja`；变量存在，但值已经出现乱码。修复脚本使用 `errors="replace"` 尝试 UTF-8 解码，探针路径仍可匹配时就会接受已经损坏的前缀，导致输出字节与 Ninja 规则不一致。Windows 封装入口原先只在构建之后修复，无法保护当前编译产生的依赖记录。

初始 `ninja -t deps` 有 993 条记录，其中 398 条为零依赖；`skins.cpp.obj` 和 `gameclient.cpp.obj` 均是有效的零依赖记录。真实 Ninja 回归实验已经证明，错误的 MSVC 前缀本身足以产生这一现象。零依赖数量不能单独证明 `.ninja_deps` 被并发写坏；并发构建风险和此前类布局错配的分析保留，但不能把它们当作本轮独立证明的事实。

仅改前缀不会改变 C++ 编译命令，原来的零依赖对象仍可能保持不重编，因此恢复必须包含这些对象的重新编译。

## 实现与恢复

`qmclient_scripts/repair_ninja_msvc_prefix.py` 按编译器原始输出字节提取和修复前缀，不再经过替换解码；保留生成文件的其他内容与换行，并支持补入缺失变量和同步 RC 的 cmcldeps 参数。前缀变化时读取现有 Ninja 依赖表，校验对象路径属于构建目录，将有效零依赖对象的修改时间标为待重编，保留现有文件；依赖查询失败时不会先写入修复状态。

`qmclient_scripts/cmake-windows.cmd` 在构建前修复；如果构建中 CMake 重新生成错误规则，则在成功后修复并补一轮构建。修复失败会返回失败，不继续报告构建成功。封装日志保留在工作区 `tmp/`。

客户端串行重建成功，随后测试、服务端与 `qm-benchmarks` 目标也已重建。最终 996 条依赖记录中，`skins.cpp.obj` 有 332 条依赖、`gameclient.cpp.obj` 有 346 条依赖。剩余 12 条零依赖分别来自当前配置下为空或仅含注释的编译单元、已由 Ninja 显式输入跟踪的预编译头，以及简单图标 RC 文件；预编译头相关对象通过 `ninja -t query` 核对了输入关系。

同轮还修复了 `gate/lib/runner.py` 在 GBK 输出流打印 U+FFFD 时的 `UnicodeEncodeError`：显示使用替换错误处理，返回的完整诊断和子进程退出码保留。测试同时覆盖成功、失败和 Unicode 内存输出流。

## 构建入口的持续约束

后续会话根据用户“不能总是单次解决”的要求，把目录互斥实现为构建入口行为。`cmake-windows.cmd` 继续加载 VS/MSVC 环境，并调用 `qmclient_scripts/cmake_windows.py`。新模块将目录锁、前缀检查、构建、规则重生成后的依赖恢复和日志留存组织为同一事务，避免在多个 batch 分支中重复维护这些行为。

锁以规范化后的绝对构建路径识别目录，Windows 使用系统文件区间锁。configure、build、CMake 测试目标、打包目标及 install 共用该目录锁。同目录第二个任务显示等待提示，最多等待 10 分钟；获得锁后才运行前缀探针或写入构建目录。不同构建目录仍可以并行。单次 Ninja 内部的 `-j 14` 编译并行度保持原样。锁文件留存在 `tmp/build-locks/`，互斥由系统持有的锁决定，不由“文件是否存在”决定。

测试覆盖同目录不同路径写法的等待与释放、不同目录并行、等待超时不进入事务，以及持锁进程退出后的重新获取。真实 Windows/MSVC 集成进一步验证：被占用目录不会先生成 `CMakeCache.txt`；释放后完成 configure；编译错误原样返回；修正源文件后下一轮构建成功；CMake 重生成规则后头文件依赖仍可触发重编。

这把锁覆盖使用仓库 Windows 入口的调用者。直接运行 CMake/Ninja 不会获取它；日常构建、测试、打包仍统一通过 `qmclient_scripts/cmake-windows.cmd`。同一目录构建时修改源文件也不受这把锁约束；编辑过程中不要把尚未稳定的产物作为验收或发布结果。
