#8 滚动抖动根治

已实现

现状

QmClient 设置页（qmclient/menus_qmclient.cpp）和 TClient 设置页（tclient/menus_tclient.cpp）在滚动时出现抖动。滚动状态管理集中在 settings_resource_jobs.cpp：SettingsBuildFrameContext（:392）构建每帧资源上下文，含 m_ScrollActive、m_JumpScrollActive、m_PostScrollRecoveryFrames。

根因（已确认）

主因：资源加载预算阶梯跳变。滚动期间资源加载预算被压到最低（finalize 16 / gpu upload 4），滚动结束后的 2 帧恢复期跳到 48/192，再跳回正常。这种预算阶梯式跳变导致每帧加载/上传的资源数突变 → 可见项目逐批出现 → 视觉抖动。

次要风险：布局重算与滚动不同步。m_PostScrollRecoveryFrames > 0 期间，SettingsResourceSharedHeavyBudget（:1269）返回 RecoveryBudget 而非 NormalBudget，导致恢复期有额外重算。

已实现方案

把离散跳变（16→48→64）改为连续线性插值。新增 SettingsRecoveryBudget 函数（settings_resource_jobs.cpp:417-424）：

int SettingsRecoveryBudget(const SSettingsResourceFrameContext &Context, int ScrollBudget, int IdleBudget)
{
    const int RemainingFrames = maximum(Context.m_PostScrollRecoveryFrames, 0);
    if(RemainingFrames <= 0)
        return IdleBudget;
    const int RecoveryFrames = maximum(2, RemainingFrames);
    const int CompletedFrames = std::clamp(RecoveryFrames - RemainingFrames + 1, 1, RecoveryFrames);
    return ScrollBudget + (IdleBudget - ScrollBudget) * CompletedFrames / (RecoveryFrames + 1);
}

所有 finalize/gpu upload/source load 预算函数（:426-435、:437-447、:449-458、:564-566、:577-579）在 m_PostScrollRecoveryFrames > 0 时统一调用 SettingsRecoveryBudget，实现从 ScrollBudget 到 IdleBudget 的平滑过渡。

影响范围

  • settings_resource_jobs.cpp（预算函数 + 新增 SettingsRecoveryBudget）
  • src/test/settings_warmup_test.cpp（回归测试已更新）

验收标准

  • QmClient 和 TClient 设置页滚动时无可见抖动。
  • settings_warmup_test.cpp 全绿。
  • gap 视觉验证仍需人工补充（quick gate 已过，但人工肉眼确认抖动消失未做）。

#10 通知栏贴边回归 + HUD 编辑器/实际渲染一致性

已实现
本任务与 #14.2 强耦合，已一起完成，共用一套贴边 Helpers（commit e54bb209ac + 7dd0b6ec09）。

原问题

qm_hud_notifications_edge_margin（默认 8）通过私有 InsetAnchoredRect 在变换前空间施加边距，但 BeginTransform 用未含边距的 AnchorRect 做变换，导致编辑器拖到屏幕边时「预览框贴边了但实际渲染贴不到」。

已实现方案

在 hud_editor.h 的 QmHudEditor 命名空间新增通用贴边设施：

namespace QmHudEditor {
    struct SEdgeMargin { float Left, Right, Top, Bottom; };
    CUIRect ApplyEdgeMargin(const CUIRect &Rect, const SEdgeMargin &Margin,
                            bool AnchoredLeft, bool AnchoredRight,
                            bool AnchoredTop, bool AnchoredBottom);
    enum class EHorizontalFlow { LeftAnchored, RightAnchored };
    EHorizontalFlow ResolveHorizontalFlow(const CUIRect &VisibleRect, float ScreenWidth);
    // 旧 helpers 保留：
    CUIRect InsetAnchoredRect(...);      // 委托 ApplyEdgeMargin

B6. 马甲注册与识别 拆双类型

需求重述（用户三轮澄清后定稿）：马甲分两种类型，UI 和数据流完全不同。类型 A 保持完整功能（不退化），客户端代码先行，服务端接口由远程仓库主（中心服务 42.194.185.210 维护者）实现。

当前权威口径：B6 必须拆成两个任务验收。类型 A 是「中心服务端契约 + 客户端预埋/降级」，服务端未就绪时不能宣称端到端完成；类型 B 是纯客户端私人标注，可独立推进。当前代码已有 qid 身份链，但没有 alt_of / alt_name 字段解析或上报。

类型 A：公告马甲（alt_account）——主动注册，所有 QmClient 用户可见

玩家自己声明「我是 XXX 的马甲」，注册后所有 QmClient 用户都能看到标注。UI 极简（填主号名 + 马甲名，无发码/无验证码）。客户端在 /qm/users.json 在线名单里按名字查到主号的 qid，走 POST /qm/alt/register。

服务端需新增接口（由远程仓库主实现）：POST /qm/alt/register、/qm/users.json 下发 alt_of、/qm/report 接收 alt_of、GET /qm/alt/lookup。

客户端实现范围（本开发者做）：马甲管理 UI、注册调用 + report 字段、users.json 解析扩展、渲染、配置。具体 7 点：① 「马甲管理」设置区 UI（menus_qmclient.cpp，极简两输入框）；② 名字→qid 转换（复用 /qm/users.json 查询，qmclient_utils.cpp）；③ /qm/alt/register 调用封装（HTTP POST，带 auth_token）；④ /qm/users.json 解析扩展（读 alt_of / alt_name）；⑤ 缓存 + 渲染（名字板/计分板标注「[主号名]的马甲」，复用 warlist 标注布局）；⑥ 配置项 QmAltEnabled/QmAltMainName/QmAltName；⑦ 服务端未就绪时的优雅降级。

注册流程（名字 → qid 转换）：① 用户填主号名 → 客户端在 /qm/users.json 在线名单按名字查主号 qid（m_vLocalServerMarks，qmclient_utils.cpp:126-132）；② 调 POST /qm/alt/register（携带 auth_token + 主号 qid + 马甲名）→ 服务端记录 {alt_qid, main_qid, alt_name}；③ 主号不在线时无法立即注册 → 提示「主号当前不在线，请稍后重试」。

数据流（复用现有 /qm/* 服务）：上报 /qm/report 每个 player 对象增加可选 alt_of 字段（主号 qid，服务端不识别则忽略）；下发 /qm/users.json 每个条目增加可选 alt_of + alt_name；客户端渲染时 GetQ1menGClientQid(ClientId) → 查缓存 → 标注主号名。识别链已闭合：名字 → qid → ClientId（改名不影响绑定）。

优雅降级：服务端未就绪时（HTTP 404/超时）注册按钮提示「服务暂不可用」，不报错、不影响其他功能。基于 qid 而非名字，主号/马甲改名后关系不丢失。

类型 B：私人标注（private_tag）——你标注别人，仅自己可见（类似 warlist）

复用 TClient warlist 机制（CWarList，本地存储 qmclient_warlist.cfg）。推荐新建 CPrivateTag 组件（避免污染「敌对」语义）。UI：右键玩家名添加「标注为 XXX 的马甲」。

验收标准

  1. 类型 A（服务端就绪后）：填主号名 + 马甲名 → 注册成功 → 所有 QmClient 用户在名字板/计分板看到「[主号名]的马甲」。
  2. 类型 A（服务端未就绪）：注册按钮提示「服务暂不可用」，不报错，UI 正常显示，不影响其他功能。
  3. 改名稳定：主号或马甲改名后，因绑定基于 qid 而非名字，关系不丢失。
  4. 类型 B：能给任意玩家打私人标签、仅自己可见、名字板/计分板显示。
  5. 两类标注可共存（同一玩家既有公告马甲标注又有私人标注）。

  • 类型 A 依赖远程仓库主实现服务端——客户端按契约先行，服务端未就绪则优雅降级（设计取舍，非缺陷）。
  • 主号不在线时无法注册（查不到 qid）——可接受限制。
  • 私人标注用名字匹配，改名会失效（类型 A 用 qid 不受影响）。
  • 任何人都能声明是某人的马甲（无主号审批）——用户接受此简化优先于防冒认；如后续需防冒认再加服务端白名单。
