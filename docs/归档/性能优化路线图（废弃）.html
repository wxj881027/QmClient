② 五大判断修正详解

原 v1 基于印象中的代码做判断，v2 基于实际代码调研修正，v3 按 codegraph CLI 再次验证。源自 v2

修正 1：CUI 已具备部分 ImGui 同类优化，不需要 retained node

v1 4.1.4 计划把 CUiV2Tree 扩展为可持久化 node 表（retained-mode）。但实际读代码发现：

  • CUi::RenderQuadContainerBatchable（ui.cpp:599-626codegraph 验证）已实现 draw call 合并
  • CUi::QuadBatchRectContainer（ui.cpp:579-597codegraph 验证）按 (w,h,rounding,corners) 缓存 QuadContainer
  • CUiScopedQuadBatch 提供 RAII batch scope
  • CListBox + CScrollRegion::RectClipped()（ui_listbox.cpp）已实现 list virtualization，且比 ImGui 原生 clipper 更强（支持变高行）
修正后方向：删除 v1 的 retained node 计划。QmUI 真正的三大短板是：(1) hot layout buffer 需要 arena/复用（ComputeChildren 的入参 vector 可由调用点复用，函数内部临时数组仍需 PoC）；(2) DrawCmd header 不统一（没把 ClipRect 纳入 memcmp，跨 clip 不能合并）；(3) 动态文本走"重建容器"（聊天、计时这种每帧变化的文本应该先做局部 PoC，再决定是否扩展到 ITextRender 公共契约）。

修正 2：纯英文卡顿首要嫌疑不在字符集

v1 把文本渲染卡顿主因归咎于"中文图集扩容"，建议"sparse atlas 化"。但 6/19 fresh log 显示 frameMsP99=299ms 时 backend/upload/glyph 各项全为 0，且纯英文 UI 也会卡顿。基于业界经验（ImGui FONTS.md、Hypersect 博客、Unreal Slate、Qt QTextLayout）锁定真因：

  • 最高嫌疑 每帧重建 text container / quad buffer（CPU 侧 alloc + memcpy）
  • 高匹配 Paragraph layout / wrap / word-break 每帧重算
  • 次要 Per-frame TextWidth 调用累积
  • 排除 GPU upload 同步阻塞（log 中 upload=0）；字形 atlas 全量重传（这是中文次因，不是英文主因）
修正后方向：放弃"sparse atlas 是答案"的预设。文本优化先按 ImGui 持久 buffer + Unreal dirty-cache 路线做 profiling/PoC：(1) text container 加 dirty 标记 + (string,font,size,wrap) 缓存；(2) 持久 arena 分配器消除每帧 malloc/free；(3) 验证每帧 per-label TextWidth 调用是否累积。CJK 可借鉴 ImGui 1.92 动态字体系统的"按需增量扩展 atlas + 仅对新增 glyph 上传"机制，但必须先解决旧 text container UV 失效、跨 backend texture update 和 frame 内上传预算。

修正 3：scheduler 已 service 化，但同步渲染路径覆盖仍不足

v1 ⑧.7.3 提出 scheduler_coverage 口径。2026-06-20 codegraph 复核当前 HEAD 后确认 Phase A 的 service 化子项已落地：codegraph 验证

  • IFrameScheduler（frame_scheduler.h:26）已是 kernel service，CFrameScheduler 实现在 frame_scheduler.cpp:9。
  • CGameClient 通过 FrameScheduler()（gameclient.h:444）暴露。
  • CGameClient::OnRender 已在帧入口/出口调用 BeginFrame / EndFrame。
  • 旧 CMenus 独立 state 字段已合并到 service 内部 per-consumer state。
  • SettingsText、DemoBrowser、Assets、IngameServerInfo 等 consumer 已有生产调用。

当前核心边界：RenderServerInfo / ingame runtime 已部分消费 scheduler token。同步渲染路径 DoIngameMenuLabel（menus.cpp:4598codegraph 验证）系列保留首帧可见 fallback，但当 stable container 未命中且执行实时 Ui()->DoLabel 时，已显式计入 fallback_immediate 和 scheduler_coverage=uncovered。

当前结论：Phase A 可按当前口径收口。service 化、frame scope、per-consumer state、Reset 生命周期、guard 栈式语义、4px bucket、同步 fallback telemetry 和 perf gate 结构测试已落地；后续进入 Phase B，聚焦更细的 budgeted_work_ms、immediate_render_ms、scenario 和阈值。

修正 4：图形后端优化方向是 Vulkan 主战场（OpenGL 暂缓）

v1 把图形后端优化放在 Phase F 条件触发。用户判断"长期必然要优化，FPS 的提高需要它"——方向对。代码现状比 v1 假设的好得多，但仍有具体优化空间：

  • CGraphics_Threaded + backend_sdl.cpp:54 真有 graphics thread（ThreadFunc，不是伪线程化，仅 Emscripten 退化）
  • Vulkan backend 5 项基础优化已实现（详见 ⑧）
  • Vulkan 同步原语全在非帧热路径（纠正 6/18 误判）：codegraph 验证
    • vkQueueWaitIdle 包装在行 7653，vkDeviceWaitIdle 包装在行 7662
    • DeviceWaitIdle() 的 4 个调用者（行 1791 内存恢复、6307 RecreateSwapChain、7884 Cmd_Shutdown、9079 WindowDestroyNtf）全在 shutdown / swapchain recreate / surface destroy / 内存恢复路径
    • vkWaitForFences 行 7644 是每帧开始的标准 N-buffer swapchain image fence 等待，是必要同步
    • vkMapMemory（行 1526、1860、1921、7196）是 buffer/stream buffer 创建时调用，非每帧 map/unmap
OpenGL backend 严重落后（暂缓）：backend_opengl.cpp（2344 行）无 PBO、无 glMapBufferRange、无 persistent mapping、无 staging buffer、无内存子分配器。用户决策：OpenGL 放放，先优化 Vulkan 和其他方向。
修正后方向：图形后端从 Phase F 提前到 Phase D 并行。Vulkan 是主战场，Phase D 优先级：
  1. 暴露 Vulkan 内置 frame profiler到 perf report——所有后续优化的前置基线
  2. UI 渲染路径 telemetry（QuadsBegin/End vs RenderQuadContainer 调用频次 + 各自耗时）
  3. 基于 profile 数据决定后续优化
暂缓：AMD GPU 多线程 fallback（无 AMD 测试环境）、OpenGL backend 补 staging/PBO。

修正 5：粒子 budget 简化，不做完整优先级系统

v1 FR-3 列了 4 层 budget（spawn/update/render/碰撞）。用户反馈："DDNet 粒子和拖尾，实际游戏中就是一个视觉的效果，所以一般而言不会引入物理检测"。代码复核补充：粒子语义仍以视觉为主，但 m_Collides 粒子会调用 Collision()->MovePoint，因此不能把 update/collision 成本从观测口径中删除。

修正后方向：不做完整 per-particle priority / 玩法级碰撞预算系统，简化为 spawn budget + viewport culling + group render budget；但必须增加 update/collision telemetry，确认 m_Collides 粒子占比和 MovePoint 时间后再决定是否需要更细 budget。

③ 六根支柱

基于四份调研，原 v1 的"四支柱 + 文本 + 图形后端"重构为六个独立支柱。每个支柱都标注：现状、真问题、优化方向、代码指针。源自 v2

Pillar 1：CUI/QmUI 优化（借鉴 ImGui，不 retained）

现状

  • CUI 已实现 QuadBatch + QuadContainer 缓存 + 变高行 clipper（v1 误判为"裸 immediate-mode"）
  • QmUi 是新写的 declarative-style，但大量用 std::vector，无 frame-local arena

真问题

  1. QmUi hot layout buffer 需要 arena/复用策略：ComputeChildren（QmLayout.cpp:84codegraph 验证）入参 std::vector<SUiLayoutChild> 可由调用点复用，但函数内部仍有临时 std::vector<float>，应先在高频页面 PoC。
  2. DrawCmd header 不统一：UiPlanQuadBatchSubmission 基于 color/containerIndex 判断，没把 ClipRect 纳入 memcmp，跨 clip 不能合并
  3. 动态文本走"重建容器"：聊天、滚动数字、计时器每帧变化的文本走 CreateTextContainer 全量重建，应该走 ImGui 风格 inline reserve/unreserve
  4. 潜在退化点：CUi::m_vQuadBatchSprites.clear()（ui.cpp:643codegraph 验证）需确认是否释放 capacity

优化方向

  • P0 在 QmUi layout 临时 buffer / 高频页面 PoC CQmFrameArena（bump allocator）+ std::pmr::vector，只替换已 profile 证明的热路径。
  • P0 引入 SDrawCmdHeader POD，把 (ClipRect, TextureHandle, QuadContainerIndex, Color) 塞成连续 32 字节做 memcmp
  • P1 先在菜单/HUD 适配层 PoC 动态文本 inline 路径；只有 PoC 证明收益和旧 container 失效模型清晰后，才考虑扩展 ITextRender 公共接口。
  • P1 CQmUiStorage（有序 vector + 二分）替代散落的 std::unordered_map

明确不做

  • ❌ retained node 表（v1 4.1.4 删除）
  • ❌ ImGuiListClipper 等高假设（QmClient 变高行 clipper 已经更好）
  • ❌ 直接搬 ImFontAtlas（DDNet textrender 已有等价机制）
  • ❌ Docking/multi-viewport（单窗口游戏 UI 不适用）

Pillar 2：粒子简化 budget

现状

  • CParticles::RenderGroup()（particles.cpp:209codegraph 验证）已有 ParticleIsVisibleOnScreen 和 RenderQuadContainerAsSpriteMultiple
  • DDNet 粒子以视觉效果为主；部分 m_Collides 粒子 update 会调用 collision 查询，不能从 telemetry 中忽略。

优化方向（三层 budget + update/collision telemetry）

  • P0 spawn budget：按 group 限流，同一帧同一组最多新增 N 个
  • P0 viewport culling：扩展现有 ParticleIsVisibleOnScreen，远端粒子降低更新频率（2-4 帧更新一次）
  • P1 group render budget：按 group 限制最大渲染数，超了降采样（优先保留爆炸、命中、玩家附近粒子）

明确不做

  • ❌ 玩法级碰撞预算系统（但必须保留 MovePoint 成本观测）
  • ❌ 优先级丢弃系统（DDNet 粒子无 per-particle priority 概念，强加等于重写）

  2. Paragraph layout / wrap / word-break 每帧重算

Pillar 3.5：QmRuntime 资源系统（整合方向）

结论：QmClient 需要一套 runtime resource facade，但不应一次性新增大而全的 QmRuntime/QmScheduler/QmWarmupManager/QmTextCache/QmPoolRegistry/QmJobSystem/QmThreadSystem/QmRuntimeMetrics 平行体系。正确路线是先收敛现有 ad-hoc 调度、文本池、monitoring 和 job 能力，再抽出固定 consumer 的 runtime facade。

核心不变量

  • Render/UI 可见路径只消费，不生产重资源：可见帧不做 glyph 栅格化、atlas 扩容、完整 text container 首建、慢系统指标采样、无预算 job completion。
  • 预热是 runtime 调度问题，不是 text.cpp 内部小功能：启动、ESC、settings、monitoring、语言/字体/UI scale 变化都必须走同一套有状态、有预算、有取消、有 telemetry 的入口。
  • 复用 6/14 设置页工作流：loading/prewarm → plan collection → prebuild → visible guard → background jobs → telemetry → report；不要另起一套绕过 m_MenuTextPool / visible guard 的缓存系统。
  • CPU/GPU 未吃满不等于没有性能问题：无限制帧率下总体 CPU/GPU 利用率不满、平均 FPS 很高，但仍有瞬时卡顿，通常说明瓶颈在 frame pacing、主线程长尾、同步 fallback、无预算 completion 或 scheduler coverage 缺口，而不是硬件算力不足。
调度器判定原则：如果 CPU/GPU utilization 都不高、backend/upload 指标也不高，但 frame_ms_p99/max 仍然爆炸，应优先判定为调度失败：重活没有被预算化，或者预算化 work 与 immediate render work 没有进入同一套 frame pressure 模型。此时继续堆 GPU/字体技术通常只会掩盖问题，不能替代 scheduler coverage 收口。

Pillar 3.6：SDF/MSDF 与 Vulkan GPU text 调研报告

2026-07-01 补充。用户提供的 ChatGPT share 链接当前只能访问到登录页，未能读取正文；本节只基于当前仓库代码、CodeGraph 和源码核对。

当前代码事实

  • 当前文字是 FreeType bitmap atlas：RenderGlyph 调 FT_Load_Glyph(... FT_LOAD_RENDER ...) 得到灰度 bitmap，CPU 生成 fill/outline，随后 UploadGlyph 更新 text texture。
  • 当前 shader 是 bitmap alpha 合成：data/shader/vulkan/text.frag 采样 gTextSampler 和 gTextOutlineSampler 的 .r 作为 alpha，没有 distance field 计算。
  • 当前 Vulkan text 是独立 pipeline：Vulkan backend 通过 CreateTextGraphicsPipeline("shader/vulkan/text.vert.spv", "shader/vulkan/text.frag.spv") 创建 text pipeline；Cmd_RenderText 绑定 text pipeline、descriptor set、vertex/index buffer 后 draw。
  • 当前 text command 只表达 bitmap text：SCommand_RenderText 只带 buffer container、texture size、fill texture、outline texture、draw count、颜色；没有 render mode、distance range、MSDF median 参数或 glyph instance buffer。
  • 当前已有两套 icon 基础：Font Awesome icon font 走 EFontPreset::ICON_FONT 和普通 text renderer；QmClient 自己的 CQmIconManager 走 build-time SVG→PNG 多倍率 atlas，runtime 直接 PNG UV 绘制。
  • 当前仓库没有现成 SDF/MSDF 管线：源码和资源中未发现 SDF/MSDF shader、distance field atlas manifest 或 runtime SDF icon/text renderer。

Vulkan-only 策略

新鲜文本渲染功能优先只做 Vulkan：OpenGL 保留现有 bitmap atlas 兼容路径，不阻塞 Vulkan-only SDF/MSDF/GPU text 实验。文档和配置上必须把这类能力标成 renderer=vulkan，并提供 bitmap fallback，避免把兼容后端拖进长期架构实验。

推荐 PoC 顺序

  1. Icon SDF/MSDF PoC：以 CQmIconManager 为入口，把现有 PNG atlas manifest 扩展为 kind=bitmap|sdf|msdf、px_range、em_size。新增 Vulkan-only icon distance shader；OpenGL/旧 renderer 继续用 PNG atlas。
  2. Large-text SDF PoC：只覆盖 HUD 数字、nameplate 超大字号、缩放后明显发糊的稳定文本。仍由主线程预算 tick 生成/上传 atlas，不允许可见帧同步生成。
  3. Vulkan GPU text container PoC：新增 Vulkan text render mode 和 command，不替换现有 SCommand_RenderText。目标是把稳定文本实例数据常驻 GPU，减少重复 container/quad buffer 生产；layout 仍先保留 CPU 侧。

验收标准

  • 质量：ingame 高缩放下大字号文本/图标边缘明显优于 bitmap；小字号中文不得比现有 FreeType bitmap 更糊。
  • 性能：PoC 不能增加首帧同步工作；所有 atlas 生成、上传、pipeline/descriptor 创建必须受 runtime budget 或 loading 阶段约束。
  • 调度：即使启用 SDF/MSDF/GPU text，scheduler_coverage 仍必须能解释 target window 中的 covered/uncovered work。
  • 后端：Vulkan-only 功能必须有 bitmap fallback；OpenGL 不实现新功能也不能破坏现有渲染。
  • 可维护：不能把 Font Awesome icon font、Qm PNG icon atlas、未来 SDF/MSDF icon atlas 三套入口继续无限分叉；PoC 成功后需要收敛到统一 Qm icon API。

4.1 Vulkan pipeline cache 与启动预热

2026-07-01 codegraph + 源码核对补充。结论：Vulkan shader 已在构建期编译为 SPIR-V，但 QmClient 当前没有自有的持久化 VkPipelineCache；启动/重建 swapchain 时仍需要驱动创建 graphics pipeline。

  • 不是运行时 GLSL 编译问题：cmake/BuildVulkanShaders.cmake:83 调 glslangValidator 输出 .spv，text.frag/text.vert 也在构建期生成 data/shader/vulkan/text.*.spv（行 115-117）。
  • 运行时读取的是 SPIR-V：backend_vulkan.cpp:5274-5294 的 LoadShader 从 storage 读取 shader/vulkan/*.spv，随后 CreateShaderModule 调 vkCreateShaderModule。
  • 当前 pipeline 创建未用 cache：backend_vulkan.cpp:5484 调 vkCreateGraphicsPipelines(m_VKDevice, VK_NULL_HANDLE, ...)；仓库源码未发现 vkCreatePipelineCache / vkGetPipelineCacheData / vkDestroyPipelineCache 接入。
  • pipeline 创建集中在启动/重建路径：InitVulkanSwapChain（backend_vulkan.cpp:6911）在 render pass/framebuffer 后连续创建 prim、text、tile、quad、sprite 等 pipeline（行 6940-7000）。

架构方向：新增 Vulkan-only 的 CQmVulkanPipelineCache，由 Vulkan backend 拥有，不放进 OpenGL 兼容路径。它在 device 创建后、pipeline 创建前读取本机 cache blob；所有 vkCreateGraphicsPipelines 改为传入 cache handle；pipeline 创建后和 shutdown/device destroy 前用 vkGetPipelineCacheData 保存。

启动顺序：
Vulkan device ready
  -> LoadPipelineCache(qmclient/cache/vulkan_pipeline/*.bin)
  -> CreateGraphicsPipelines(cache_handle)
  -> Publish pipeline_create_ms / cache_hit / cache_bytes
  -> QmRuntime::RequestWarmup(Startup)
  -> QmWarmupManager 按预算推进 glyph/page/text/icon warmup

cache key 必须保守：至少包含 QmClient build/cache version、renderer backend、vendorID、deviceID、driverVersion、pipelineCacheUUID、SPIR-V manifest/hash、MSAA/render pass format、pipeline layout schema、clip/dynamic mode、相关图形配置。缓存损坏、驱动变更或 key mismatch 时直接丢弃并重建，不能阻塞启动。

和预热系统的关系：pipeline cache 只加速 graphics backend init，不缓存 UI page/glyph/text container 本身。cache miss 时，启动阶段不要同时把页面预热塞满主线程；应先完成 pipeline 创建并记录耗时，再让 QmWarmupManager 用较低 startup budget 推进。cache hit 时，warmup 可以按正常启动预算更早开始。

用户反馈的核心不是"某个特效能不能关"，而是：游戏内应保持流畅、输入延迟可控、画面不撕裂，同时粒子、拖尾、HUD、提示、QmClient/TClient 增强功能仍然可用。当前代码已有局部能力，但缺少统一的游戏内性能产品面、统一 optimizer 状态、和能解释"这一帧为什么慢"的后端/组件级归因。

用户问题当前体验产品目标
DDNet/QmClient 画面撕裂常见，开 VSync 又感觉延迟高 用户只能在撕裂和延迟之间手动取舍 提供可理解的 frame pacing 模式：低延迟、平衡、抗撕裂，并用 telemetry 解释 swap/sleep/vsync 成本。
粒子、拖尾、HUD 是体验，不希望靠关闭解决 部分功能高峰期可能造成帧时间尖峰 默认保留视觉效果，通过预算化、LOD、裁剪、分组批处理降低尖峰。
游戏内 FPS 和设置页首帧优化混在一起 report 容易只看到总桶或 UI 桶 分离 perf/game_render、perf/render_backend、perf/effects、perf/hud，明确是 CPU 渲染、GPU upload、后端 swap 还是文本问题。
Windows 高优先级是否有效不清楚 QmClient 当前只在启动时可选设置 high priority 升级为可开关、可恢复、可观测的 optimizer 子功能，并标注其收益边界。

5.2 PRD：目标与非目标

目标

  • 在不默认关闭粒子、拖尾、HUD、提示、增强渲染的前提下，降低游戏内 frame time p95/p99/max。
  • 把 CGameClient::OnRender() 下的主要组件拆成可解释的阶段：map layers、particles、trails、HUD、nameplates、TClient/QmClient overlays、backend swap。
  • 建立游戏内 optimizer：优先级、frame pacing、效果预算、可见区域裁剪、HUD 文本缓存都由统一状态和 telemetry 管理。
  • 参考 BestClient 的已验证思路，但不直接照搬用户可见语义；只吸收"预算、上限、可见性裁剪、恢复机制"的工程模式。

非目标

  • 不要求用户关闭粒子或 HUD 作为默认性能方案。
  • 不改变 DDNet 协议、物理、预测、地图语义、rank 可达性。
  • 不把 Vulkan/OpenGL 后端作为第一步大重构；后端改动必须由 telemetry 证明。
  • 不把进程高优先级宣传为"FPS 优化主方案"；它只是调度辅助。

5.5 功能需求（FR-1 ~ FR-6）

FR-1：Runtime Optimizer 状态机

  • 新增统一 optimizer 状态，不直接把每个优化散落在各组件开关里。
  • 状态包含：enabled、profile=quality|balanced|low_latency|performance、frame_pressure、backend_mode、effects_budget_scale。
  • Windows 高优先级：开启时记录旧 priority，关闭时恢复；调用失败必须日志和 telemetry 可见；默认关闭。
  • 禁止在 render hot path 每帧枚举系统进程；类似 BestClient 的 Discord 降优先级如果未来要做，必须节流到秒级并默认关闭。

FR-2：游戏内组件级 perf stage

  • CGameClient::OnRender() 对主要组件输出稳定 stage：component_particles_update、component_particles_render_group、component_hud、component_tclient、component_qmclient_overlay、component_nameplates、component_trails、component_map_layers。
  • 每个 stage 附带 state、spectating、particles_visible、draw_calls_delta、texture_binds_delta 等可选字段。
  • report 必须把游戏内 FPS 归因从 components_total 拆到具体组件，否则不能声称定位完成。

FR-3：粒子/拖尾保体验预算化（简化版，参见修正 5）

  • 按 group 设置预算：general、extra、trail、explosion、background 等分别统计和限流。
  • spawn budget：同一帧同一组最多新增 N 个；超过后按优先级丢弃低影响粒子或合并为更少粒子。
  • update budget：视口外粒子降低更新频率；远端粒子可按 2–4 帧更新一次，但生命周期视觉上连续。
  • render budget：超过 budget 时优先保留爆炸、命中、玩家附近粒子；背景/低 alpha/远端粒子优先降采样。
  • 不做玩法级碰撞预算系统，但必须保留 m_Collides 粒子的 Collision()->MovePoint 成本观测。

FR-4：HUD / TClient 文本与图元缓存

  • 稳定标签：FPS、Ping、Velocity、Position 等 label 部分使用 text container 或 width cache。
  • 动态值：按值变化或采样周期更新，例如网络统计、监控面板可 5–10Hz 更新，玩家坐标/速度仍按需要实时。
  • HUD icon/shape：优先使用已有 QuadContainer，减少每帧 QuadsBegin/End。
  • 监控 overlay 默认不应成为 FPS 测试噪声；开启时单独输出 perf/hud_monitoring。

FR-5：Frame pacing 与抗撕裂模式

  • 保留 DDNet 现有 gfx_vsync，但新增用户可理解的建议模式文案：低延迟、平衡、抗撕裂。
  • 低延迟模式：VSync off，支持 FPS cap 建议值（例如显示器刷新率的 2x/3x 或略高于刷新率），重点减少输入延迟。
  • 平衡模式：VSync off + 稳定 frame cap + frame pacing 观测，目标降低撕裂感和 sleep 抖动。
  • 抗撕裂模式：VSync on 或后续支持 adaptive vsync/late swap；明确提示可能增加输入延迟。
  • telemetry 必须区分：render CPU 时间、sleep wait、swap/vsync wait、GPU upload wait。

FR-6：图形后端统计与条件优化

  • 新增后端统计：每帧 draw calls、texture binds、quad container renders、buffer uploads、text texture updates、swap 耗时。
  • OpenGL/Vulkan 分别输出 backend name 和 capability：quad_container_buffering、text_buffering、tile_buffering。
  • 只有当 report 显示 backend-bound 时，才进入 UI atlas、ring buffer、scissor batching、async upload 等后端优化。

6.1 ESC 首帧：可以复用文本池缓存，但不能首帧补齐缓存

6.2 文本池命中率：不要把 fallback 当优化成果

  • 普通 settings 文本：cache miss 只入队，不能扩大 immediate fallback。
  • ingame 关键 chrome：tab、按钮、标题允许极小范围 fallback，避免不可读。
  • 动态文本：服务器名、玩家名、资源标题应走 snapshot/LRU 类缓存，不纳入 static stable 文本命中率分母。
  • 验收口径：planCollectionComplete=true、unplannedVisibleCount 下降、fallbackImmediate 只保留在白名单 chrome。

7.1 Scheduler 架构问题

7.1.1 当前工作模型：纯 opt-in，不是自动发现

当前调度器已经是 IFrameScheduler kernel service（frame_scheduler.h:26codegraph 验证），CFrameScheduler 实现在 frame_scheduler.cpp:9。CGameClient::OnRender 已调用 BeginFrame / EndFrame，不再是 CMenus 私有 state。但 consumer 仍是显式 opt-in：只有调用 GameClient()->FrameScheduler()->ComputeBudget(...) 的路径才受控，未接入的 immediate-mode fallback 不会自动限流。

7.1.2 不通用的具体表现（代码事实）

  1. consumer 仍需手动接入：service 已统一 state，但没有自动发现机制；新路径必须明确选择 EFrameSchedulerConsumer 并调用 ComputeBudget。
  2. 覆盖语义仍需继续细化：demos/assets/settings/ingame server info 已有部分 consumer；但这不等于所有 text/layout work 都被 budget 约束。
  3. 同步 fallback 已显式归类：DoIngameMenuLabel（menus.cpp:4598codegraph 验证）系列保留首帧可见 fallback，但已通过 fallback_immediate / scheduler_coverage=uncovered 进入 perf gate。
  4. 跨场景继承策略未定义：service 内部已有 per-consumer state，但 settings / ingame / assets / demo 的 HealthyFrames/Window 是否应该继承或隔离仍需 profile 决定。
  5. fallback 语义已可观测但仍需压低：RequestMenuTextContainerBuild 当 token ≤ 0 直接返回 false，drain 队列可能堆积；当前先把用户实际看到的同步 fallback 计入 uncovered，Phase B 再按场景量化阈值和耗时。

7.2 Stable Text Pool 架构问题

7.2.1 key mismatch 的剩余风险（设计层面，不只是 bucket bug）

mismatch 的判定是 HasDescriptor && !KeyPlanned。历史根因之一是 plan 收集时算的 Rect 用 MenuTextSettingsContentView(Screen)（重放路径），visible 渲染时算的 Rect 用真实 MainView，两者亚像素差异再被过细 MaxWidthBucket 放大。当前 BuildMenuTextStyleKey（menus.cpp:287codegraph 验证）已改为 4px bucket，亚像素抖动已缓解；剩余风险是 plan collection 重放路径本身仍可能和 visible 路径分歧。

这是设计层面问题：plan collection 试图"重放渲染"但重放路径不可能和真实路径完全一致（UI 状态、time-based 动画、scroll position、tab 切换瞬间都不一样）。

7.2.2 双重记账根因（设计 bug + 实现 bug 组合）

  • 历史问题：guard 曾假设全帧只有一次 guard，违反 RAII 可组合性。
  • 当前状态：guard（CScopedMenuTextVisibleGuard，构造 menus.cpp:4975 / 析构 menus.cpp:5009codegraph 验证）已保存 previous 状态，最外层负责清零/输出，析构恢复 previous，具备栈式语义。
  • 剩余风险：后续新增 guard 时必须保持同样的栈式契约，并用行为测试锁住 nested guard 语义。

7.3 三个改造方向

方向 A（当前短期）：收口已 service 化 scheduler 的覆盖语义

  • 工程量：小-中（service 已存在，主要是补覆盖、telemetry 和测试）
  • 收益：让 5-8 个固定 consumer 的覆盖范围可解释，避免"token 算了但同步 fallback 照跑"。
  • 风险：当前魔法数（threshold 1.35x、HealthyFrames=2 等）需重新调参
  • 关键边界：5-8 个固定 consumer，service 内部硬编码 list，不要完全动态注册（避免 microservice 反模式）

方向 B（长期）：删除 plan collection 双路径

  • 工程量：中-大（删除约 15+ 个 m_SettingsMenuTextPlan* 成员，但代码净减）
  • 收益：自动消除 key mismatch（不再有两套 key 路径）；自动消除双重记账（不再需要 visible guard 区分）；新加 tab/页面零接入成本
  • 风险：失去"planned vs unplanned"区分能力；失去对"invisible-but-planned"的预热能力
  • 前置 PoC：临时短路 BuildVisibleSettingsMenuTextPlan / PrebuildSettingsMenuTextPool，跑 perf benchmark；如果差异 <5%，方向 B 可直接执行

方向 C（短期止痛）：局部修复

  • MaxWidthBucket：已改为 4 像素粒度；后续只需继续观测 key mismatch 是否接近 0。
  • guard 栈式语义：已具备 previous/restore 语义；后续用测试防止退化。
  • 工程量：小（1-2 天）
  • 风险：这些局部修复治标不治本，plan collection 双路径复杂度仍在

7.4 综合建议

推荐 C 短期止痛 → A 中期重构 → B 长期简化 的组合路径。

不要为了"通用"把 scheduler 设计成完全动态注册式 microservice。QmClient 是单线程游戏 client，过度抽象（generic token consumer 注册）反而引入间接调用成本和调试难度。方向 A 的边界应该是"5-8 个固定 consumer，service 内部硬编码 list"。
方向 B 不是"完全 ImGui 化"——DDNet 的 CUi/CUIElement 是 retained-mode（CUIElement 跨帧存活），完全 ImGui 化需要重写 UI 框架，工作量超出 QmClient 范围。方向 B 是"保留 CUIElement 但删除 plan collection 这层"。

9.2.3 预算规则

  • 预热计划必须绑定 language、font face / variant、font size bucket；语言或字体变体变化后计划失效。

  • 空闲预热只允许低预算，例如每帧 4–16 个 glyph，并在 frame time 高于阈值时暂停。

⑭ 风险与边界

14.1 scheduler 改造边界

  • 不要做完全动态注册 microservice：5-8 个固定 consumer，service 内部硬编码 list。完全动态注册会引入间接调用成本和调试难度。
  • QmRuntime 是 facade，不是平行引擎：第一版只收敛 metrics、warmup、job wrapper 和 pool stats；不要一次性新增并强行迁移所有线程、资源、文本、对象池所有权。
  • 方向 B 不是完全 ImGui 化：保留 CUIElement 跨帧存活（retained-mode），只删除 plan collection 这层。
  • 魔法数调参风险：当前 state machine 是手工调参的（threshold 1.35x、1.60x、HealthyFrames=2 等），重构后需要重新调参，可能短期回归。

14.2 图形后端改造边界

  • Vulkan 不要大改：已有 staging、stream buffer、frame profiler 等基础设施；先暴露 telemetry 和判断 GPU/CPU-bound，再决定是否做 descriptor/scissor/glyph memcpy 等小修。
  • Vulkan pipeline cache 是本机缓存，不是可发布资源：VkPipelineCache blob 依赖驱动、GPU、pipeline schema 和 shader 内容，只能存在用户 storage；失效、损坏、驱动升级都必须 fail-open 重建。
  • pipeline cache 不替代 runtime warmup：它只降低 graphics pipeline 创建成本，不能缓存 glyph atlas、text container、页面资源或 UI layout；首帧卡顿仍必须由 scheduler coverage、dirty cache 和 budgeted warmup 收口。
  • OpenGL PBO/staging 不是低风险通用升级：PBO 对上传收益依赖驱动和 workload，persistent mapped 需要 OpenGL 4.4+/扩展；必须绑定最低 GL 版本、驱动矩阵和 OpenGL 用户占比。
  • 图形后端提前可能与 CPU 侧优化竞争资源：6/19 log 显示当前卡顿是 CPU 侧，图形后端优化短期内不解决眼前问题，是长期方向。

14.3 文本渲染边界

  • 不预设答案：纯英文卡顿真因必须先 profile 验证（per-label TextWidth 调用次数、text container 每帧 alloc/free、layout/wrap 重算次数）。
  • ImGui 1.92 动态字体系统是 CJK 长期可借鉴方案，但不是可直接搬运的实现；需要 PoC 证明 atlas 增长、旧 container UV、backend texture update、上传预算都可控。
  • ITextRender 是 engine-wide API：直接新增公共接口会影响 chat、HUD、demo browser、menus、QmUI、map render、editor。优先在菜单/HUD 适配层验证。
  • SDF/MSDF/GPU text 不是当前 Phase 的主修复：它们可以作为 Phase E 后的独立技术路线 PoC，但不能绕过当前必须完成的 scheduler coverage、dirty cache、warmup budget 和 runtime metrics。
  • 新鲜文本渲染功能优先 Vulkan-only：OpenGL 是兼容后端，保持 bitmap fallback；不要为了 OpenGL 同步实现而阻塞 Vulkan SDF/MSDF/GPU text PoC。
  • GPU text PoC 必须证明端到端收益：不仅看 glyph 渲染质量或 GPU 利用率，还要证明 frame tail、fallback 字体、CJK、旧 container UV、OpenGL/Vulkan 行为、截图/录制一致性都可控。

14.4 QmUI/CUI 改造边界

  • QmUI 不要变成 retained-mode 大框架：保留 immediate-mode 的灵活性，只在必要处叠加缓存；node 生命周期必须可预测，避免 dangling 状态。
  • CUI 基础路径谨慎改动：涉及 DoLabel、DoButtonLogic、CScrollRegion 等高频上游 API 时，默认走外围适配，确需改动时要有更小补丁、更强测试和 rollback 方案。

14.5 上游 cherry-pick 边界

用户已确认 QmClient 已偏离 DDNet 上游太远，现在是 cherry-pick 模式。因此：

  • ✅ 不需要追求整仓 rebase 友好；不以"是否方便回上游"作为性能路线的主要约束。
  • ⚠️ 这里的"不考虑上游兼容性"只指源码同步/贡献回官方层面，不等于可以无审批改变用户可见运行时契约。
  • ⚠️ 若某项优化会触碰协议、demo/skin/map/config 格式、物理、预测、snapshot、输入、时序或回放语义，需要单独批准和专门验证。
  • ⚠️ 碰 ITextRender / graphics backend / CUI 公共接口时，不需要为上游贡献让路，但仍需要 feature flag、跨 backend/平台验证和回退路径。

14.6 测试深化边界

  • visual regression gate 不能替代功能测试：PSNR/SSIM 只能 catch 视觉回归，不能 catch 行为 bug。
  • 重审现有测试时不要一刀切：先识别"形式主义"测试（断言字符串存在），逐个改造为行为断言。
  • 每个测试加 intent 文档：说明它 catch 什么 bug，方便后续 Agent 判断测试是否还有价值。

14.7 内存预算约束

  • 所有缓存（layout cache、text LRU、texture atlas）都会增加内存占用
  • 每个新增缓存的内存上限必须显式声明，超过预算时降级或 evict
  • 建议内存预算：PC 上 1-2GB（含游戏纹理+UI+font atlas+缓存）

14.8 telemetry 字段膨胀

  • 每个新增 stage 必须按 frame pressure 节流，不能让 perf logging 本身成为 hot path
  • 当前 6/19 log 已经 694425 行，再加新 stage 需要谨慎
  • 建议：低优先级 stage（如 glyph_warmup）用阈值触发输出，不每帧输出

14.9 通用原则

  • 性能优化不绑定视觉重设计：每轮保持显示、输入、滚动、选择、资源 fallback 语义不变。
  • 避免过度工程：每引入一层缓存，必须同时引入命中率/成本/收益 telemetry；证明收益为负时立即回退。

15.1 scheduler/text pool 相关

15.2 文本渲染相关

  • 纯英文卡顿真因的 A/B profile：准备两份 fresh log（纯英文 UI 切换 + 纯中文 UI 切换），对比 text_container_create_ms、glyph_rasterize_ms、glyph_upload_ms、paragraph_layout_ms 在两份 log 里的占比。
  • per-label TextWidth 调用次数：当前是否每个 label 每帧都调？是否随 hash 缓存？
  • text container 每帧 alloc/free 次数：是否走 std::vector 默认分配器？是否可改为 arena？
  • WarmGlyph API 边界：应暴露在 ITextRender 还是仅作为 IEngineTextRender / QmClient 适配层接口，需要先做 blast-radius 评估。
  • layout cache 后台化边界：当前 text layout 是否能完全脱离 graphics/text renderer state；如果不能，后台线程只能产出 manifest/plan，不能产出最终 layout/container。
  • SDF/MSDF/GPU text 技术路线：是否值得做取决于 Phase E 前置数据；PoC 至少要比较现有 atlas/container、SDF/MSDF atlas、Vulkan GPU-resident text 三种路线在质量、内存、上传、CPU tail、跨 backend fallback 复杂度上的真实成本。
  • 图标库渲染统一：现有 Font Awesome icon font 与 Qm PNG icon atlas 并存；SDF/MSDF icon PoC 成功后，需要决定是否统一到 CQmIconManager，还是继续保留两套入口。

15.3 图形后端相关

  • OpenGL 用户的实际占比和卡顿数据：DDNet 默认 OpenGL 还是 Vulkan？QmClient 是否改了默认？如果 OpenGL 用户占比小，OpenGL 后端优化收益有限。
  • Vulkan StreamBuffer / staging 行为已基本确认：后续重点是把 frame profiler 暴露到 QmClient perf report，而不是重查是否存在。
  • m_FrameProfileStats 输出路径：当前主要是 backend verbose/profile 信息，仍需接入 QmClient perf report 和 gate scenario。
  • Vulkan pipeline cache 收益量化：需要 fresh profile 对比首次启动、第二次启动、删除 cache 后启动、损坏 cache 启动四种场景，确认 pipeline_create_ms 降幅和 fallback 行为。
  • OpenGL program binary cache 是否值得做：用户已明确新功能优先 Vulkan；OpenGL 可作为后续兼容优化，但要先看 OpenGL 用户占比和启动耗时，避免为兼容后端扩大维护面。

15.4 CUI 相关
