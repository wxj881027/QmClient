DDNet 鸿蒙观战端适配方案

把 QmClient 的纯观战能力带到 HarmonyOS 7：侧载分发、GLES 先行、按白名单瘦身，并以 SDL 3.6 正式版作为开工门禁。本文给出架构、界面取舍、裁剪清单、路线图与验收方式。

目标 HarmonyOS 7 · API 26 兼容 6.0+ · API 20 图形 GLES 3.0 分发 侧载 · 不上架 门禁 SDL 3.6.0 正式版
§0

摘要

三句话能说完的判断，后面每一节都是在补它的证据。

判断一

不必重写引擎

C++ 内核与 GLES 路径在 Android 上已经跑通，鸿蒙侧真正从零的只有 ArkTS 外壳、构建链与依赖库。

判断二

UI 分层，不是全量重写

世界层（地图 / HUD / 聊天 / 旁观控件）必须留在 C++；页面层（服务器列表 / 好友 / 设置）可以交给 ArkTS，但放在 P2。

判断三

门禁是 SDL 3.6.0

官方最新正式版仍是 3.4.18，鸿蒙后端 2026-09-15 才进 main。等正式版，现在只做不依赖它的部分。

一句话

这不是「从零移植一个游戏引擎」，而是「给一套已有的 C++ 客户端换一层壳、砍掉三分之二的模块、再补一条新的构建与分发链」。真正的未知数不在 DDNet，在 SDL 3.6 的鸿蒙后端还够不够稳。

前置条件（未满足前不动主线）

① SDL 官方发布包含鸿蒙后端的 3.6.0；② 拿到一台 API 26 与一台 API 23 设备（你的平板）；③ 确认侧载签名方式（DevEco 自动签名 / 自签名 Profile）。

2）XComponent 的 surface 会随前后台销毁重建，渲染上下文必须可重建且幂等。
3）SDL 只允许一个窗口，且默认占满屏幕——横竖屏与安全区要自己算。

§3

架构

四层结构：ArkTS 管系统与页面，NAPI 管过界，C++ 管世界，SDL3 管平台。

关键决策

ADR-01

混合界面

系统与页面用 ArkTS，世界与 HUD 用 C++ 自绘。理由：每帧变化的内容不适合声明式 UI。

ADR-02

SDL 3.6 门禁

只等正式版，不接受 main 分支进主线。理由：3.6 之前没有任何发布版包含鸿蒙后端，pin 一个移动分支等于替上游做 QA。

ADR-03

GLES 优先

只编 GLES 3.0；Vulkan 不编译。理由：Android 已证明 GLES 路径稳定，鸿蒙 Vulkan 需专用 surface 扩展，收益不确定。

ADR-04

单仓 + 编译期白名单

不 fork、不另起仓库，用 QM_SPECTATOR_ONLY 裁模块。理由：共享内核与修 bug 的成本最低，但裁剪必须覆盖构建、资源和入口。

ADR-05

候选：把 HTTP 上移到 ArkTS，砍掉 curl + boringssl

curl 与 boringssl 是整套依赖里最难交叉编译的两个。鸿蒙的 @ohos.net.http 可以直接发请求，若在 T0 阶段这两个库的移植超出预算，就把 CHttp 的传输层换成 NAPI 回调（对外接口不变），代价约 5–8 人日。

触发条件：T0 结束时 curl 仍不可用，或 boringssl 编译失败超过 3 人日。

§4

界面方案：要不要用 ArkTS 重写

这是本次讨论里最值得展开的一条。答案是「能写，但只该写其中一层」。

4.1 先看这三层界面

层内容刷新频率建议归属理由
L1 系统外壳启动、权限申请、文件选择、分享、剪贴板、窗口模式、后台策略一次性必须 ArkTS这些能力只暴露在 ArkTS / ArkUI 侧，native 拿不到
L2 页面层服务器列表、好友列表、设置、Demo 列表、回放选择秒级 / 交互驱动可 ArkTS（P2）天然是「页面」：滚动、输入法、无障碍、动效都免费；但要付桥接与双份本地化的成本
L3 世界层地图、实体、HUD、计分板、聊天、旁观控件、捏合缩放每帧必须 C++与渲染管线同帧合成；交给 ArkUI 会产生每帧跨语言更新与布局开销

4.2 为什么 L3 不能交给 ArkTS

  • 同帧合成：HUD 必须和世界画面在同一缓冲里绘制，否则会出现一帧延迟与对齐误差；ArkUI 叠加层跑在另一条时间线上。
  • 状态量太大：计分板一次要渲染上百名玩家的名称、分数、队伍色，聊天每帧可能追加行。声明式 UI 的优势在「少变更」，这里的特征是「全变更」。
  • 字体与美术一致：现有文本渲染自带描边、渐变、图标混排，迁到 ArkTS 等于重做一套排版。
  • 输入归属：旁观摇杆、捏合缩放需要和游戏相机在同一帧采样，跨语言会引入抖动。

4.3 为什么 L2 值得单独考虑

收益

列表滚动、惯性、软键盘、无障碍、折叠屏断点、深色模式都由 ArkUI 提供。现有 CScrollRegion 连触控滚动都还没有（代码里没有任何触摸路径），在 ArkTS 里这是零成本。

成本

需要一套双向桥（状态同步 + 事件回调）、两套本地化、两套交互规范；服务器列表还要处理「连上了但场景还没加载」这类状态机跨语言传递。

建议

P1 不重写：直接复用现有原生菜单，先把「能看」跑通，代价最小。P2 再评估：如果移动端体验是重点，把 L2 搬到一个 ArkTS 页面栈上，世界页保持全屏 XComponent，两者用 NAPI 通信（约 +40–60 人日）。这个顺序的好处是：任何一步停下来，产品都是可用的。

4.4 逐屏归属速查

屏幕 / 界面P1P2备注
服务器列表（含好友分组）原生菜单ArkTS数据来自 HTTP + UDP ping，桥接面最宽，收益也最大

4.5 NAPI 契约（P1 最小集）

不管 P2 做不做，这条桥都要先定下来；定得早，P2 只是加页面，不是重构。

// ArkTS → C++
init(width, height, density, locale, safeArea): void
start(): void            stop(): void
touch(type, id, x, y, pressure): void
key(code, down, mods): void
textInput(action): void  // 拉起 / 收起软键盘

// C++ → ArkTS（回调）
onFrameStats(fps, frameMs): void

原则：跨语言只传「意图与结果」，不传每帧数据；每帧数据留在 C++ 内部。

5.5 字体策略：不裁剪，另议读系统字体

字体先按「全部保留」处理。data/fonts 里 21 套字体（49 MB，含 SourceHanSans 的 CJK、emoji、数学与符号、以及装饰字体）是游戏内排版的基础；观战端要看聊天、名牌、告示牌和被观战者的皮肤名，缺一套就掉字形。

路线做法可行性代价
A · 自带字体（默认）FreeType 直接读 data/fonts，保持现状确定可行体积已计入，0 人日
B · 用户导入字体ArkTS 文件选择 → 复制进沙箱 fonts/ → 注册进字体列表 → FreeType 加载可行+3–5 人日
C · 直接读系统字体文件枚举系统字体并拿到文件路径交给 FreeType第三方应用拿不到需先实测 /system/fonts 可读性
D · 用系统字体渲染ArkUI UIContext.getFont().registerFont 或 Drawing OH_Drawing_CreateSharedFontCollection只对 ArkUI / Drawing 生效等于换掉现有文本管线
系统字体的真实边界

@ohos.fontManager 的 getSystemFontList / installFont 是系统接口：需要 ohos.permission.UPDATE_FONT，非系统应用调用直接返回 202（Non-system application）。侧载应用能做的只有两件——按家族名使用系统字体（ArkUI / Drawing 侧），以及在本应用内注册字体文件。所以「读取系统已安装字体」不是一个开关，而是一个待验证项：/system/fonts 在沙箱里可不可读，决定走 B（用户导入）还是 D（换渲染）。

决策：P1 用 A；C 在 T0 花 1–2 人日验证；B 作为 T2 的小功能，D 不作为目标。

合计屏蔽约 9.4 万行 C++（不含第三方库），构建时间会明显下降；包体主要仍由 data/ 与字体决定。

5.3 裁剪不是加个 -D 开关

踩坑点

编辑器不是独立目标，它被拼进了客户端源列表：CLIENT_SRC = ENGINE_CLIENT + PLATFORM_CLIENT + GAME_CLIENT + GAME_EDITOR + ...（CMakeLists.txt:4071）。所以「砍编辑器」= 改源列表 + 摘掉所有引用它的入口与菜单，而不是关一个 option。白名单要从 CMake、入口、资源三条线一起收。

# cmake/ohos.cmake（示意）

两个硬性约束

① 必须用 SDK 自带的 CMake（$SDK/native/build-tools/cmake/bin/cmake），系统 CMake 不认识 OHOS；② 产物必须是 libmain.so，不能是可执行文件。

§8

风险

按「会不会让项目停下来」排序。

风险影响为什么会出现应对
SDL 3.6 迟迟不发高鸿蒙后端只在 main 分支，没进任何正式版T0 先做不依赖部分；超过 6 个月则 pin 一个 3.6-dev commit 做原型
鸿蒙后端成熟度高2026-09 才合入，缺 messagebox / dialog，长尾 bug 未知把崩溃与卡死纳入常规流程（§9），前两周不上新功能只修
FFmpeg 交叉编译高要整套 av* + x264 静态库，鸿蒙没有任何现成产物，工具链得自己搭先在 T0 末尾做一次工具链验证；失败则视频导出代码保留、功能标为「未启用」，不阻塞观战链路
curl / boringssl 编译不过中依赖 OpenSSL 生态，交叉编译链陌生ADR-05：HTTP 上移 ArkTS，直接绕开
XComponent 生命周期中前后台切换会销毁并重建 surface渲染上下文与资源管理器做幂等重建，切后台主动暂停
主循环形态中客户端用 SDL_main，鸿蒙把它放进后台线程（官方称可用但有风险）评估迁到 main callbacks；至少在 T1-a 加启动自检
触控与输入法中Android 上已经踩过一轮（键盘弹出、首帧命中、光标定位）复用 mobile_spectator 与已知修法，逐项回归
系统字体拿不到文件低fontManager 是系统接口，第三方应用无权枚举；/system/fonts 可读性未验P1 直接用自带字体，不受影响；「导入字体」走用户自选文件，绕开系统 API
包体积低data 96 MB，字体独占 49 MB字体裁剪 + 首启解包进度提示
签名过期低侧载依赖调试证书 / Profile脚本里记录签发日期，过期重签；文档写明这是固定成本
