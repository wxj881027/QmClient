# Vulkan 崩溃诊断与审查

## 范围与已确认行为

用户在正常游玩时遇到 Vulkan 崩溃，已有报告但内容不足以定位。此前报告来自基线 `9dfb56ef46e89233f9b204c753779b9011b0bac0`，实际后端为 Vulkan、显卡为 RX 6650 XT，错误详情只有 `(not reported by the backend)`。

本次只完善报告落盘，不增加自动弹窗。保留已有图形设置和 AUTO 增强渲染回退策略，不新增后端自动切换策略。

审查沿运行期故障链展开：错误消费、录制工作线程、帧获取与提交、Qm 中间提交与读回、缓冲创建和内存分配失败、退出接入。没有进行全量 shader 或设备兼容性审计。

## 确认的问题与修复

| 严重度 | 位置（修复后行号） | 触发与影响 | 处理 |
| --- | --- | --- | --- |
| 重要 | `src/engine/client/backend_threaded.cpp:211`，`TakeFatalError` | 主循环在下一次提交前消费故障时，直接清除处理器错误，未调用 `ProcessError` 保存诊断。报告读到空字符串，且提交停止标志没有置位。影响所有使用此线程后端的图形实现。 | 先保存首份诊断并停止提交，再清除待消费标记；重复处理不覆盖首份故障。重建处理器时清除旧诊断。 |
| 严重 | `src/engine/client/backend/vulkan/backend_vulkan.cpp:2790`，`WaitFrame`；`src/engine/client/backend_sdl.cpp:234` | 录制线程失败后，帧提交没有检查该故障；错误提前返回时也未等录制线程完成再复制诊断。可能执行仍处于录制状态的 secondary 缓冲，并并发读取错误容器。 | 原子发布失败标记，收拢线程后再读取诊断；停止未启动的录制批次；帧提交与外部渲染切换发现故障即返回。 |
| 严重 | `src/engine/client/backend/vulkan/backend_vulkan_qm_render_targets_impl.h:134`、`:145`、`:194`、`:199`、`:409` | Qm 中间提交和读回忽略部分命令缓冲结束、重置、开始操作的返回值，可能提交无效缓冲；部分失败只返回 false，不记录具体原因。 | 检查返回值，记录 API 名称与数值结果，失败时停止该路径。同步补充主帧、secondary、内存缓冲和资源失败路径的诊断。 |
| 重要 | `src/engine/client/client.cpp`，`HandleQmGraphicsFatalError`；`src/engine/client/qm_graphics_diagnostics.h:12` | 报告把固定头部、全部错误详情和 GPU 信息拼入 2048 字节缓冲。详情较长时会截掉错误尾部或 GPU 信息；原实现不检查写入和同步结果。 | 分段写入，保留完整详情和 GPU 信息；检查写入、同步和关闭结果。记录回退前增强模式、配置线程数及故障时实际录制线程数。 |

Vulkan 规范指出，`vkEndCommandBuffer` 失败会让命令缓冲进入 invalid 状态，因此不能继续把它作为可执行缓冲提交。[Khronos：vkEndCommandBuffer](https://docs.vulkan.org/refpages/latest/refpages/source/vkEndCommandBuffer.html)

错误码保留在报告中，示例为 `vkQueueSubmit (frame) failed.` 与 `device lost (VkResult -4)`。无法提供 API 详情的命令失败仍记录命令 ID 和录制线程，避免只有通用摘要。内存分配失败另记录请求字节数和内存类型。

## 仍待设备证据的问题

空报告是确定的诊断链缺陷，但旧报告无法反推出最初失败的 Vulkan 操作或驱动原因，不能据此认定显存耗尽或 AMD 驱动故障。

现有代码会在 AMD 上强制单线程录制，因此本次发现的多录制线程失败风险不能直接视为 RX 6650 XT 这次事件的根因。录制线程修复没有真实 GPU 故障注入证据。

下一次授权构建并复测后，应先确认新报告保留具体操作、`VkResult`、实际录制线程数及 GPU 信息，再据此选择设备丢失、资源分配或录制失败的针对性复现。报告目录继续使用配置目录下的 `dumps/QmClient_Crash`。
